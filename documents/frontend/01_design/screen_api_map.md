## 3. 必要な API の一覧

論理的な機能単位で並べる。**1行が1エンドポイントになるとは限らない。**

API ID の接頭辞は分類を表す。**画面 ID（S-01〜S-16）と紛れないよう、API ID に S は使わない。**

| 接頭辞 | 分類 |
|---|---|
| A | 認証・ユーザー |
| P | プロフィール |
| C | 企業情報 |
| I | 面接セッション（会話） |
| V | 音声認識 |
| E | 評価 |
| T | 練習モード |

状態欄の意味は次のとおり。

- **実装済** — `backend/` に実装がある
- **記載済** — [必要api .md](<../../必要api .md>) にあるが未実装
- **不足** — [必要api .md](<../../必要api .md>) に記載がなく、画面から必要と分かったもの

| API ID | API | 主な入力 | 主な出力 | 状態 |

| V-1 | 音声認識（文字起こし + 話し方分析） | 音声データ | 文字起こし、抑揚、フィラー、声の大きさ、スピード | **記載済** |

### 3.6 練習モード

**採点は本番モードと同じ V-1・E-1 を使い回す。** 練習モード固有で要るのは課題の供給だけである。

| API ID | API | 主な入力 | 主な出力 | 状態 |
|---|---|---|---|---|
| T-1 | 練習課題の取得 | 練習の種類（音読 / 滑舌 / スピード） | 課題文、課題フレーズ | **不足**（未決事項 #3） |
| T-2 | 一問一答の質問取得 | 企業 ID | 質問文 | **不足**（未決事項 #4） |

**練習モードには I-1〜I-3 に相当するセッション管理を置かない。** 1回の録音に対して1回の評価が閉じるため、連続した会話を保持する必要がないからである。ただし評価結果を保存して S-14 に渡す以上、E-1 の入力には**どの練習（モード・練習の種類）の結果かを示す情報**が要る。

### 5.3 記載はあるが定義の見直しが要るもの

| # | 対象 | 論点 |
|---:|---|---|
| 1 | **内容評価 API（E-1）の入力** | 記載は「文字起こし結果、抑揚などの話の情報」のみ。**しかし [ユースケース](../../ユースケース・ユーザーフロー.md) 4.1 が掲げる「志望動機の一貫性」を評価するには、質問文と企業情報（応募書類・志望動機）が要る。** 加えて、結果を保存して S-14 で見せるには、どのモード・どの練習の結果かを示す情報も要る（[3.6](#36-練習モード)） |
| 2 | **内容評価 API（E-1）の出力** | 記載は「評価点数、アドバイス」。画面一覧の S-14 は**総合スコア・項目別スコア・合否判定の参考表示**を出すため、点数の粒度を定義し直す必要がある |
| 3 | **音声認識 API（V-1）の入力** | 記載の input が空欄。音声データの渡し方は [#15](https://github.com/study-basic-hackathon/hanasu/issues/15) の音声送信方式の決定に従う |
| 4 | **音声認識 API の分割**（記載の「分割の可能性あり」） | **画面から見ると文字起こしと話し方分析は常に同時に必要で、分けて呼ぶ契機がない。** 分割するとしてもフロントからは1回の呼び出しに見せるのが望ましい。実装上の分割可否は [#25](https://github.com/study-basic-hackathon/hanasu/issues/25) の判断 |
| 5 | **企業情報の項目** | C-1・C-3 の「企業情報」の中身が未定義。画面一覧 S-07 は企業名（必須）・募集要項 URL・エントリーシート・志望動機・備考を持つ |

### 5.4 API 制約の見直し

[必要api .md](<../../必要api .md>) は「認証ユーザーのみ実行可能」とするが、**A-1 サインインと A-2 会員登録は未認証で実行できなければならない。** 制約に例外を明記する必要がある。

| API | 認証 |
|---|---|
| A-1 サインイン、A-2 会員登録 | **不要**（未認証で実行できる） |
| 上記以外のすべて | 必要 |

## 6. 会話用 API の扱い（[#15](https://github.com/study-basic-hackathon/hanasu/issues/15) 未決）

**I-1〜I-3 は、[#15](https://github.com/study-basic-hackathon/hanasu/issues/15) がどの方式を選んでも必要になる範囲に限って置いたものである。** 画面一覧 S-08 が「チャット形式の連続した会話」と定めている以上、セッションの開始・回答の送信と次の質問の取得・終了という3つの契機は方式によらず生じる。

一方、次の点は **[#15](https://github.com/study-basic-hackathon/hanasu/issues/15) の決定を待たなければ書けない。**

| 決められない点 | [#15](https://github.com/study-basic-hackathon/hanasu/issues/15) のどの決定に依存するか |
|---|---|
| I-2 に音声をどう乗せるか（ファイルとして送る / ストリーミングで流す） | 音声送信方式 |
| V-1 を独立した API としてフロントから呼ぶのか、I-2 の内部処理に含めるのか | 音声取得方式・送信方式（Chime SDK を使う場合、音声はフロントを経由しない可能性がある） |
| 通信プロトコル（HTTP のリクエスト / レスポンスで足りるか、WebSocket 等が要るか） | 音声送信方式 |
| 会話相手が AI か人かによる、質問生成 API の要否 | 会話相手が AI か人か |

**したがって [4. 画面と API の対応表](#4-画面と-api-の対応表) の S-08 の行は、[#15](https://github.com/study-basic-hackathon/hanasu/issues/15) の決定後に見直す。**
