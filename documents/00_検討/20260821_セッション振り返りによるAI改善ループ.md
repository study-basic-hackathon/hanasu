## 背景・きっかけ

1 Issue = 1PR = 1 AI セッションの運用が回り始めた。各セッションには「どういう指示があり、どういう変更をし、どこで手戻りしたか」の一連の流れが残る。**セッション完了後にその学びをどこかへ蓄積し、次のセッション・次のタスクを改善するループを作りたい**、というユーザーからの相談（2026-08-21）。やり方はまだ見えておらず、案がほしい段階。

ヒアリング結果（2026-08-21、確定した前提）:

| 項目 | 回答 |
|---|---|
| 改善したい対象 | **AI の作業品質**（同じ手戻りを繰り返さない）と**運用ルール・スキル自体**（CLAUDE.md・テンプレ・スキルの改訂） |
| 適用範囲 | **まず自分（ytr-33）だけで試す**（Issue テンプレートと同じ先行適用方式） |
| セッション終了時の手間 | **数分の振り返り対話も OK** |
| ナレッジの置き場所 | **リポジトリ内で OK** |

## 論点

1. セッションからナレッジを**どう収集するか**（手動の振り返り / hooks 自動 / PR 本文 / 自動メモリ）
2. **どこに・どんな形式で蓄積するか**（場所・粒度・並行セッションでの衝突回避）
3. **どうやって次のセッションに効かせるか**（AI が自動で読むのは CLAUDE.md だけ、が制約）
4. 蓄積の**肥大化・腐敗**（古くなったルール）をどう防ぐか
5. チーム展開への道筋（個人先行 → 全体、をどう設計しておくか）
6. **何を学びとして抽出し、どう対応するか**（学びの分類・対応の決め方・蓄積しないものの基準）← 2026-08-21 に深掘り。回答は「学びの抽出・蓄積の詳細設計」の節

## 事実確認（出典付き）

- **AI（Claude Code）が毎セッション自動で読み込むのは CLAUDE.md だけ**。それ以外のファイルは、CLAUDE.md か指示で誘導しない限り読まれない（出典: Claude Code の仕様。プロジェクトメモリとして CLAUDE.md をセッション冒頭に読み込む）
- **個人環境では「自動メモリ」が既に稼働しており、このプロジェクトの学びが 9 件蓄積されている**（出典: `~/.claude/projects/<プロジェクト>/memory/MEMORY.md`）。例:「PR 本文の構成（5章構成、検証章は付けない）」「worktree ブランチの push 先」「gh のアカウント切り替え」— まさに今回蓄積したい種類のナレッジであり、**このループが有効なことの実証でもある**。ただし個人ローカルにあり、チーム共有・レビュー・履歴管理ができない
- **スキルは各自の環境（`~/.claude/skills/`）にしかない**（出典: [issue-template.md](../template/issue-template.md) の注記）。一方、Claude Code は**リポジトリ内 `.claude/skills/` のプロジェクトスキルも読み込む**ため、リポジトリ経由でチーム共有できる（出典: Claude Code の仕様）
- **hooks（SessionEnd 等）でセッション終了時に自動処理を仕込める**（出典: Claude Code の仕様。`settings.json` に定義）
- 正本ルール:「作業ログ・実測結果は **PR 本文**が正本」「task-memo は凍結」（出典: [documents/README.md](../README.md) §1）。`documents/` 配下の文書種別は仕様・ADR・検討記録・テンプレートに限られており、**ナレッジログという種別は存在しない**
- **並行セッションが同じファイルを触って競合した実績がある**（出典: 過去セッションでの実体験。複数の PR が同一 `documents/` ファイルを編集）。追記型の単一ファイルは衝突リスクが高い
- Issue テンプレートは「まず ytr-33 の担当分のみ適用、チーム展開は合意待ち」の先行適用方式を採っている（出典: [issue-template.md](../template/issue-template.md) 冒頭）
- 体制は複数人 + 各自 AI、1 タスク = 1PR（出典: [20260808_AI向けタスク運用方針.md](20260808_AI向けタスク運用方針.md) ヒアリング結果）

## 前提となる整理: ループは「収集 → 蓄積 → 反映 → 棚卸し」の4段階

**蓄積するだけでは次のセッションは 1 ミリも良くならない**（AI が自動で読むのは CLAUDE.md だけのため）。したがって本丸は「反映」であり、蓄積はそのための中間バッファと位置付ける。

```
[収集] セッション末に学びを抽出
   ↓
[蓄積] 生ナレッジとして保存（1セッション=1ファイル）
   ↓
[反映] 昇格基準を満たしたものを、AI が実際に読む場所へ移す
        ├─ 全セッションに効く普遍ルール → CLAUDE.md
        ├─ 起票の仕方に関するもの     → issue-template.md
        ├─ 特定作業の手順に関するもの → 該当スキル
        └─ プロジェクト固有でない個人の癖 → 個人メモリ
   ↓
[棚卸し] 定期的に生ナレッジを刈り込み、古いルールを廃止
```

## 選択肢の比較（収集方式）

比較軸: 収集の手間 / ナレッジの質 / 次セッションへの効き方 / チーム展開のしやすさ / 実装コスト

| 観点 | A案: 振り返りスキル（セッション末に対話） | B案: hooks で自動収集 | C案: PR 本文に振り返り章 | D案: 自動メモリ任せ（現状維持） |
|---|---|---|---|---|
| 仕組み | プロジェクトスキル `/retrospect` を作り、PR 作成後に1コマンドで起動。AI がセッションを振り返って学びを抽出し、ユーザーと数分対話して確定 → 蓄積・昇格提案まで行う | SessionEnd hook で transcript を保存し、後でバッチ分析 | PR テンプレートに「振り返り」章を足し、次のセッションが `gh` で過去 PR を読む | 個人の自動メモリが暗黙に学び続けるのに任せる |
| 収集の手間 | 1コマンド + 数分の対話（ヒアリングの許容範囲内） | ゼロ | PR 作成時に AI が書くのでほぼゼロ | ゼロ |
| ナレッジの質 | **高い**。ユーザーの訂正・レビュー指摘という最重要ソースをその場で確認して言語化できる | 低〜中。生ログは巨大でノイズが多く、分析の仕組みが別途要る | 中。PR 本文はレビュー用文書であり、振り返りを混ぜると読み手のノイズになる。過去 PR を毎回検索するのはコスト高 | 中。何が記憶されたか本人に見えず、制御・レビュー不可 |
| 次セッションへの効き方 | **直接的**。昇格先（CLAUDE.md 等）の改訂までワンセットで行う | 間接的。分析 → 反映の別工程が必要 | 弱い。読みに行く動線を毎回作る必要がある | 効くが個人限定・ブラックボックス |
| チーム展開 | **容易**。スキルも蓄積もリポジトリ内なので、PR で見せて合意を取れば全員が同じループを回せる | hooks 設定の配布が必要（`.claude/settings.json` で可能） | 容易だが効き方が弱いまま | **不可能**（個人ローカル） |
| 実装コスト | 小（スキル1つ + 置き場所1つ） | 中（hook + 保存先 + 分析フロー） | 極小（PR テンプレ1章） | ゼロ |

**推奨は A案**。理由:

1. ヒアリングで「数分の対話 OK」だったため、A案の弱点（手間）が問題にならず、強み（ナレッジの質・反映までワンセット）が最大化される
2. 自動メモリに 9 件の学びが自然に貯まっていた事実は、「セッション末の振り返り抽出」というアプローチ自体の有効性を示している。A案はそれを**見える化・リポジトリ化・チーム展開可能化**するもの
3. B案（hooks）は後から A案に追加できる（振り返りコマンドの打ち忘れ対策）。排他ではない
4. D案は併存し続ける（止める必要がない）

## A案の設計骨子（たたき台）

### 収集: プロジェクトスキル `/retrospect`

- 置き場所: `.claude/skills/retrospect/SKILL.md`（リポジトリ内 = チーム展開可能）
- 起動タイミング: PR 作成後、セッションを閉じる前に1コマンド
- 抽出する観点（価値の高い順）:
  1. **ユーザーからの訂正・やり直し指示**（AI が自力では気付けない失敗の最重要ソース）
  2. 規約・ルールに違反して直した点（CLAUDE.md や documents/README.md の読み落とし）
  3. 詰まった箇所と原因（環境・コマンド・依存関係）
  4. うまくいったパターン（次も再現したい手順）
  5. **運用ルール・スキル側の不備**（Issue 本文が曖昧だった、テンプレの項目が足りなかった、スキルの手順が実態と合わない）
- 抽出後、ユーザーと数分対話して「本当にそうか / 一般化できるか」を確認してから書く

### 蓄積: 1 セッション = 1 ファイル

- 置き場所: `.claude/retrospectives/YYYYMMDD-issue-<番号>.md`
- **1 セッション 1 ファイルにする理由: 並行セッションでの衝突回避**（追記型の単一ファイルは、複数 PR が同時に触って必ず衝突する — 実績あり）
- 1 件の学びは「状況 / 学び / 昇格先の提案」の数行で書く。transcript の生ログは入れない（巨大・ノイズ・機密）
- `documents/` 配下には置かない。ナレッジログは仕様でも ADR でも検討記録でもなく、documents/README.md の正本ルールと衝突させないため（AI 運用の作業ファイルとして `.claude/` が適地）

### 反映: 昇格基準と昇格先

- **昇格基準: 同種の学びが 2 回出たら昇格。1 回でも再発コストが高いもの（規約違反・壊れる操作）は即昇格**
- 昇格先の選び方は「前提となる整理」の表のとおり（CLAUDE.md / issue-template / スキル / 個人メモリ）
- **CLAUDE.md は昇格基準を満たしたものだけ**。全セッションが冒頭で読む = 1 行ごとにコンテキスト費用を全セッションが払い続けるため、生ナレッジを直接書かない
- 昇格の編集はそのセッションの PR に同乗させる（振り返りファイルと同じ PR で出る）

### 棚卸し: 定期的な刈り込み

- 振り返りファイルが 10 件程度たまったら、棚卸しを行う（昇格漏れの回収・昇格済み/陳腐化ファイルの整理・CLAUDE.md の肥大チェック）
- 頻度が安定するまでは手動起動。将来はスキル化・定期タスク化も可能

## 学びの抽出・蓄積の詳細設計（2026-08-21 追記）

方式決定後、「具体的に何を抽出し、どう対応し、何を蓄積すべきか」を深掘りした結果。

### 原則: 「事象」ではなく「介入」を蓄積する

AI セッションの品質は入力で決まり、変えられる入力は **CLAUDE.md / Issue 本文 / スキル / 環境（コマンド・hooks・CI）** の4つだけ。学びは「何が起きたか」の記録では不十分で、**この4つのどれをどう変えるかまで書けて初めて学び**とする。蓄積エントリの必須項目を「対応（介入）」に置く。

### 学びの5つの型 → 対応マップ

| 型 | 事象の例（実例ベース） | 対応 | 介入先 |
|---|---|---|---|
| ① 知識ギャップ（AI が知らない事実だった） | gh の active アカウントが違うと Issue 編集が権限エラー | 事実をルール化する | CLAUDE.md / 該当スキル |
| ② ルール読み落とし（ルールはあったのに違反） | 規約があるのに PR 本文の書式を外した | **ルールを増やさない**。配置・表現を直す | ルールの移設・明確化 |
| ③ 判断ズレ（裁量の判断がユーザーの意図と違った） | 頼まれていない範囲まで直した | 判断基準を言語化する | issue-template「やらないこと」/ CLAUDE.md の原則 |
| ④ 環境の罠・手順発見（詰まった / うまくいった手順） | worktree ブランチは refspec で feature/... に push する | 手順化。可能なら機械化 | スキル / スクリプト / hooks |
| ⑤ 仕組み不備（テンプレ・スキル側の穴） | Issue に検証方法が書かれておらず完了判定に迷った | テンプレ・スキルを改訂 | issue-template / 各スキル |

### 原因の切り分け（診断質問:「そのとき、ルールは存在したか?」）

```
事象発生（ユーザーの訂正・手戻り）
 ├─ ルールが無かった            → 作る（①）
 ├─ あったが読む動線に無かった    → 作業の瞬間に読む場所へ移す
 ├─ あったが曖昧だった          → 表現を直す・例を足す
 └─ あって読んだのに守れなかった  → ルールでは直らない。機械化（hook/lint/CI）か人間レビュー観点へ
```

ここを切り分けずに「失敗のたびに CLAUDE.md に1行足す」と、**CLAUDE.md が長くなるほど読み落とし（②）が増える逆説**に陥る。

### ガードレールの階層（「AI の向上」の実体）

```
強  機械的強制（hooks / lint / CI）      ← 読み落としが原理的に起きない
 │  作業動線上の手順（スキルの手順・テンプレの欄）
 │  一般ルール（CLAUDE.md）
弱  生ナレッジ（.claude/retrospectives/）
```

蓄積 → 昇格は下から上への一方通行。**棚卸しの仕事は「増やす」ことではなく「上の階層へ押し上げる・統合する」こと**（例: コミットメッセージ規約は CLAUDE.md の1行より commit-msg hook のほうが確実で、CLAUDE.md から行を消せる）。

### 蓄積しないもの

- **プロダクトの知識**（仕様・設計の事実）— 正本は `documents/`。振り返りで出てきたら retrospect はそちらへルーティングする（仕様の穴なら Issue 起票）。`.claude/` に貯めるのは「このプロジェクトで **AI がうまく働くための**知識」だけ
- **作業ログ** — PR 本文が正本（[documents/README.md](../README.md) §1）
- **1回きりの偶発事象・一般論・感想**（「テストは大事」型のエントリはノイズ）
- **書くことがないセッションでは書かない**（ゼロ件は正常。絞り出した学びは棚卸しの目利きコストを上げる）

### エントリ形式とメタ改善

```markdown
## 学び: <一言>
- 事象: ユーザーに「検証章は不要」と訂正された
- 型: ①知識ギャップ
- 対応: PR 本文の構成ルールを CLAUDE.md 規約節へ追加
- 状態: 反映済み（この PR）/ 様子見（再発 1 回目）
```

- 型タグの統計が取れると、棚卸しで**失敗の分布から仕組みの弱点が分かる**（②が多い → CLAUDE.md 肥大の合図 / ⑤が多い → テンプレが弱い / ③が多い → Issue の「やらないこと」が薄い）。ループの2周目
- 各振り返りファイルに**「このセッションでのユーザー訂正回数」を1行記録**する。ループが効いているかを測れるほぼ唯一の定量シグナルで、コストは1行

### この節の設計判断（2026-08-21 確定）

| 論点 | 決定 | 理由 |
|---|---|---|
| 昇格の判断者 | **AI 提案 + その場でユーザー承認**（retrospect の対話中に昇格案を出し、OK なら同じ PR で反映） | ルールの品質を人が担保しつつ反映が最速。見送った案: 棚卸し時に一括（反映が遅れる）/ AI 単独（肥大化リスク最大） |
| 抽出のバー | **確信のある学びだけ・ゼロ件許容**（precision 重視） | ノイズが混ざらず棚卸しコストが低く、昇格候補の信頼度が保てる。見送った案: 毎セッション必ず書く（絞り出した学びがノイズになる） |

## 結論

**A案（振り返りスキル）を採用する。** 置き場所はスキル・蓄積とも `.claude/` 配下（`documents/` の正本ルールと衝突させない）。

- **決定内容**: 「収集 → 蓄積 → 反映 → 棚卸し」の4段階ループを、次の構成で作る
  - 収集: プロジェクトスキル `.claude/skills/retrospect/`。PR 作成後に1コマンドで起動し、学びを抽出してユーザーと数分対話で確定する。抽出観点の第1位は「ユーザーからの訂正・やり直し指示」
  - 蓄積: `.claude/retrospectives/YYYYMMDD-issue-<番号>.md`（1セッション = 1ファイル。並行セッションの衝突回避）
  - 反映: 昇格基準「同種の学びが2回で昇格。再発コストが高いものは即昇格」。昇格先は CLAUDE.md（普遍ルール）/ issue-template（起票の話）/ 該当スキル（手順の話）で振り分け、昇格の編集は同じセッションの PR に同乗させる
  - 棚卸し: 振り返りファイルが 10 件程度たまったら刈り込み（昇格漏れの回収・陳腐化ルールの廃止・CLAUDE.md の肥大チェック）
- **抽出・蓄積の設計**（詳細は「学びの抽出・蓄積の詳細設計」の節）: 学びは「事象」ではなく**介入**（CLAUDE.md / Issue 本文 / スキル / 環境のどれをどう変えるか）として蓄積する。学びは5型（知識ギャップ / ルール読み落とし / 判断ズレ / 環境の罠・手順発見 / 仕組み不備）に分類し、型ごとに対応を変える。**昇格は AI 提案 + その場でユーザー承認**、**抽出は確信のある学びだけ・ゼロ件許容**。プロダクト知識・作業ログ・一般論は蓄積しない
- **決め手**: ヒアリングで「数分の対話 OK」だったため A案の弱点（手間）が問題にならず、ナレッジの質と反映力（昇格までワンセット）が最大化される。個人の自動メモリに学びが 9 件自然蓄積していた事実がアプローチ自体の有効性を裏付けた
- **見送った案と理由**: B案（hooks 自動収集）= 生ログの分析工程が別途必要で、まず回すには重い。**打ち忘れ対策として後から追加できるため排他ではない**。C案（PR 本文に振り返り章）= PR はレビュー用文書でありノイズになるうえ、次セッションへの効き方が弱い。D案（自動メモリ任せ）= 個人限定・制御不可。ただしどの案でも併存し続ける
- **適用範囲**: まず ytr-33 の担当分のみ（Issue テンプレートと同じ先行適用方式）。ADR は作らない（運用方針は [20260808_AI向けタスク運用方針.md](20260808_AI向けタスク運用方針.md) と同様、検討記録 + 実体で管理する前例に従う）
