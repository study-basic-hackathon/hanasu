## 背景・きっかけ

ユーザーから、完成したテキスト音声化 API をフロントエンドに組み込むときの処理フローを議論したいとの依頼があった。

API と基本的なフロント連携はすでに `main` へマージされている。そのため、本検討では現状を出発点に、再生契機、音声状態の所有者、録音との排他、再生中断、キャッシュの扱いを整理する。

2026-08-25 の第2ラウンドで、ユーザーから**AI から次の質問が来たら自動再生したい**との希望が示された。あわせて、チャットと TTS の2段階呼び出しによる時間ロスと、1 API からテキストと音声を一緒に返す方式が提起された。

期限・予算は未確認。ハッカソン向けであることから、まずはブラウザ間の安定性と実装の小ささを優先する案を仮置きする。

## 論点

### 必須

- 再生状態を各吹き出しが個別に持つか、画面が1つのプレイヤーとして管理するか。
- 面接官音声の再生とユーザーの録音をどのように排他するか。
- 音声生成中・再生中に別の発言を再生したとき、画面離脱時、認証切れ時の中断とリソース解放。

### 任意

- 「読み上げる」操作時に初めて生成するか、質問表示時に自動生成するか。
- 次の質問を自動再生するか、毎回ユーザーが操作するか。
- 同じ発言の再生に、ページ内のメモリキャッシュを使うか。
- ローディング・失敗・再試行の文言と表示時間を現行画面仕様に合わせるか。

## 事実確認（出典付き）

- `POST /interviews/tts` は JWT Bearer 認証を必要とし、`{ "text": "..." }` を受け取って `audio/mpeg` のバイナリを返す。発言全体を1回で音声化し、ストリーミングしない。出典: `documents/backend/API仕様.md` 1章・5.4章。
- API 実装は Amazon Polly の Neural エンジン、既定音声 `Tomoko`、既定リージョン `ap-northeast-1` を使う。入力は1〜3000文字、Polly 失敗は HTTP 503 に変換される。音声は保存しない。出典: [PR #115](https://github.com/study-basic-hackathon/hanasu/pull/115) の `backend/app/schemas/interview.py` / `backend/app/services/tts.py` / `backend/app/routers/interviews.py`。
- 画面仕様は面接官の発言ごとに「読み上げる」を表示し、押下後は生成・再生中を「停止する」とし、失敗時は「読み上げられませんでした」を5秒表示する。出典: `documents/frontend/01_design/screens/S-08_本番モード.md` 5.1章。
- [PR #115](https://github.com/study-basic-hackathon/hanasu/pull/115) 「テキストを音声化する API」は 2026-08-24 に `main` へマージ済み。
- [PR #123](https://github.com/study-basic-hackathon/hanasu/pull/123) 「[frontend] 実API連携を実装する」も 2026-08-24 に `main` へマージ済み。ここで TTS 呼び出しと Blob 再生が追加されている。
- PR #123 の実装は、`synthesizeSpeech(text)` が音声 Blob を受け取り、各 `ChatMessage` 内の `SpeakButton` が `URL.createObjectURL` と `HTMLAudioElement` で再生する。停止・再生終了・コンポーネント破棄で Object URL を解放する。出典: PR #123 の `frontend/src/lib/interview-api.ts` / `frontend/src/components/interview/ChatMessage.tsx`。
- PR #123 の実装では各吹き出しが別々の `HTMLAudioElement` を所有し、録音コンポーネントと再生状態を共有していない。そのため、現状の構造上は複数発言の同時再生と、録音中の面接官音声再生が可能である。出典: 同 `ChatMessage.tsx` と `frontend/src/components/interview/AnswerPanel.tsx`の状態所有関係からの推論。
- 2026-08-25 の調査開始時点では、チェックアウト中のローカル `main` は PR #115 / #123 のマージ後のコミットを取り込んでおらず、作業ツリー上の `frontend/src/components/interview/ChatMessage.tsx` はモックの表示切り替えのままであった。出典: 2026-08-25 の `git log --decorate` / `gh pr list`。
- LLM が次の質問テキストを確定するまで、TTS に渡す入力は存在しない。したがって API を1本にまとめても、サーバー内部の `LLM → TTS` という直列関係は消えない。これは現行の `backend/app/routers/interviews.py` の chat 処理と、PR #115 の TTS 処理の入出力関係からの推論。
- Amazon Polly `SynthesizeSpeech` は、完成したテキストを1回で渡し、音声をストリームとして受け取る request-response API である。一方、`StartSpeechSynthesisStream` はテキストチャンクを送りながら音声チャンクを受け取れるが、Generative エンジンが必要で、Python SDK は対応対象に含まれない。出典: [Amazon Polly: SynthesizeSpeech](https://docs.aws.amazon.com/polly/latest/APIReference/API_SynthesizeSpeech.html) / [Bidirectional streaming](https://docs.aws.amazon.com/polly/latest/dg/bidirectional-streaming.html)。
- 現行の `backend/app/services/tts.py` は Polly の `AudioStream` を `.read()` で最後まで読み、FastAPI の通常の `Response` として返す。そのため、フロントは完成した MP3 Blob を受け取ってから再生している。出典: PR #115 の `backend/app/services/tts.py` / `backend/app/routers/interviews.py`。
- Chrome は音ありの自動再生を原則として制限し、ユーザーがドメインと操作した場合などに許可する。`play()` が制限された場合は `NotAllowedError` で reject される。Safari の許可判定は media element 単位であり、連続再生では element を作り直すより同じ element の source を変えることが WebKit から推奨されている。出典: [Chrome for Developers: Autoplay policy](https://developer.chrome.com/blog/autoplay/) / [WebKit: Auto-Play Policy Changes for macOS](https://webkit.org/blog/7734/auto-play-policy-changes-for-macos/)。

## 採用する処理フロー

v1 では**2 API を分けたまま、チャットを取得してから、返ったテキストを音声化 API へ改めて送る**。テキストと音声を1 API のレスポンスにまとめず、ストリーミングも今回の範囲では採用しない。

AI の質問を自動再生する体験については、チャット取得後に TTS をフロントから自動呼び出しする。音声状態は `InterviewScreen` 側の**画面共通プレイヤー1つ**に集約する。

1. 面接開始前に「質問を自動再生する」を明示し、ユーザーのクリックで面接を開始する。この時点から同じ1つの `HTMLAudioElement` を再利用する。
2. ユーザーの回答後、`POST /interviews/chat` を呼ぶ。
3. 面接官テキストが返ったら、**TTS を待たずに会話ログへ表示**する。これと同じ処理の流れで、JWT Bearer を付けて `POST /interviews/tts` を自動呼び出しする。
4. TTS 生成中は対象発言に「音声を準備しています」を表示する。質問テキストはすでに読めるので、TTS の成否は面接の継続をブロックしない。
5. 成功したら `audio/mpeg` の Blob から Object URL を作り、画面共通の `HTMLAudioElement` の source を入れ替えて `play()` する。
6. `play()` が自動再生制限で reject された場合は、自動再生を無効化せず、対象発言を「読み上げる」に切り替えてユーザー操作で再生できるようにする。
7. 再生中は録音を開始できないようにし、再生終了後に回答を受け付ける。「停止する」で音声を止めた場合も回答できる。
8. TTS 生成中または再生中に別の質問に進む場合は、先の生成を `AbortController` で中断し、先の再生を停止してから次に切り替える。
9. 401 は共通 API クライアントに任せてサインインへ戻す。422 / 503 / ネットワーク失敗 / 再生失敗は会話を止めず、対象発言に再試行可能なエラーを出す。
10. 画面離脱時は生成リクエストを中断し、再生を停止し、Object URL をすべて解放する。Blob は永続化しない。

### 実装時の状態案

`idle` / `loading(turnId)` / `playing(turnId)` / `error(turnId)` を画面で排他的に持つ。各吹き出しは `turnId` とプレイヤー状態から自分のボタン表示を導出する。配列 index はターン追加のみなら使えるが、将来の再試行・挿入・削除に備えるなら安定した `turnId` を持つ方が安全である。

## 選択肢の比較

比較軸は「面接の自然さ」「待ち時間」「Polly 呼び出し量」「ブラウザでの安定性」「実装・状態管理の複雑さ」を仮置きする。

| 観点 | A案: 押下後に生成・再生 | B案: 質問表示時に生成・自動再生 | C案: 質問表示時に先行生成・手動再生 |
|---|---|---|---|
| 面接の自然さ | 再生ごとに操作が必要 | 音声会話に最も近い | 操作は必要だが待ち時間は小さい |
| 初回再生の待ち | ボタン押下後に API 待ち | 質問生成後に TTS 待ち | 先行生成が済んでいれば短い |
| Polly 呼び出し量 | 聞く発言だけ | 全発言 | 全発言 |
| 再生の安定性 | 明示操作が契機 | 自動再生制限を考慮する必要がある | 再生そのものは明示操作が契機 |
| コードの複雑さ | 最小 | 録音開始・応答待ちとの状態連携が必要 | 生成キャッシュと破棄タイミングが増える |
| 現行仕様との整合 | **一致** | 仕様変更が必要 | 操作仕様は維持できる |

**B案を採用。** チャットのテキストを表示した後、TTS を自動呼び出しし、音声の準備ができ次第再生する。面接開始前の明示的な操作、自動再生失敗時の手動再生フォールバック、録音との相互排他を実装条件とする。

### API 構成の比較

| 観点 | I案: chat → TTS の2 API | II案: テキスト+音声を1レスポンス | III案: 統合ストリーミング |
|---|---|---|---|
| サーバー内の処理 | LLM 後に別リクエストで TTS | 1リクエスト内で LLM → TTS | LLM 出力を順次 TTS へ渡す |
| テキスト表示 | **LLM 完了直後に表示可能** | 音声完了まで返さないなら遅くなる | テキストイベントで先に表示可能 |
| 音声開始 | TTS API の往復と生成後 | レスポンス到着時。テキストもその時点 | チャンク到着後に順次再生可能 |
| 短縮できる時間 | — | フロント↔API の追加1往復のみ | 全テキスト・全音声の完成待ちを短縮できる |
| 失敗の分離 | **TTS だけ失敗してもテキストで継続** | TTS 失敗時の部分成功の表現が必要 | 途中切断・再接続の設計が必要 |
| 既存設計との整合 | **一致** | API 契約の変更が必要 | ADR の「ストリーミングしない」と衝突 |
| 実装複雑度 | **低** | 中 | 高 |

**API 構成は I案を採用。** 2段階は必要だが、追加時間は「フロントから TTS API への1往復」であり、LLM → TTS の本質的な直列時間は II案でも同じである。I案はテキストを先に表示でき、TTS の失敗を会話から切り離せる。

「表示と再生を完全に同時」にするだけなら、I案で TTS Blob が返るまでテキスト表示を保留し、その後に表示と `play()` を同時に行える。ただし、これは見た目の同時性の代わりにテキスト表示を遅らせるため、推奨しない。

## 懸念

| 懸念 | 深刻度の感触 | 解消に必要な確認 |
|---|---|---|
| 各吹き出しが独立したプレイヤーを持つと、複数の音声が同時再生できる | 高 | 画面共通の1プレイヤーに集約するか |
| 再生音がマイクへ回り込み、ユーザー回答の文字起こしに混入する | 高 | 再生と録音を相互排他にするか |
| 生成中のリクエストを止められず、停止後に音声が再生される | 中 | `AbortController` と、最新リクエストだけを反映する識別子を持つか |
| 毎回再生するたびに Polly を呼ぶと、同じ発言でも待ち時間と課金が重なる | 中 | 各発言をセッション中だけ Blob/Object URL でキャッシュするか |
| API 失敗で音声は聞けないが、質問テキストは表示済み | 低 | TTS を常に非ブロッキングの補助機能とすることを維持するか |
| 長時間のネットワーク待ち | 中 | フロントのタイムアウトを何秒にするか |
| 現行実装のエラー表示は「再試行する」で残り、画面仕様の「5秒後に通常表示へ戻る」と異なる | 低 | 仕様を実装に合わせるか、実装を仕様に合わせるか |

## 議論ログ

### 2026-08-25 第1ラウンド

- ユーザーから、完成した音声化 API をフロントエンドに組み込むための処理フローを議論したいとの依頼があった。
- 既存の API 仕様、ADR、画面仕様、TTS API のマージ済み PR #115、実 API 連携のマージ済み PR #123 を確認した。
- 現行実装は「発言ごとの手動生成・再生」まで持つが、複数再生と録音との排他がないことを論点とした。
- ハッカソン v1 向けの仮推奨として、手動再生 + 画面共通の1プレイヤー + 録音との相互排他を提示した。
- 未決: 手動再生を維持するか、次の質問を自動再生するか。

### 2026-08-25 第2ラウンド

- ユーザーから、可能であれば AI の次の質問を自動再生したいとの希望が示された。
- 「chat のテキストを TTS に送る2段階」「1 API でテキストと音声を一緒に返す」「2段階のまま表示と音声を同時にする」の可否が質問された。
- API を1本にまとめても LLM → TTS の直列関係は消えず、非ストリーミングの1レスポンスではテキスト表示まで遅れることを確認した。
- 仮推奨を「2 API のまま、テキストを即時表示し、続けて TTS を自動呼び出し」へ更新した。
- ブラウザの音あり自動再生制限を考慮し、面接開始時の明示操作と、`play()` 失敗時の手動再生フォールバックを条件に加えた。
- 未決: v1 で許容できる「テキスト表示から音声開始までの間」と、対応ブラウザ範囲。

### 2026-08-27 第3ラウンド

- ユーザーが、**チャットを取得してから、返ったテキストを音声化 API へ改めて送る**方式を最終結論とした。
- API 構成は I案（`POST /interviews/chat` → `POST /interviews/tts`）で確定した。
- テキストと音声を1 API のレスポンスにまとめる II案と、統合ストリーミングの III案は今回見送った。
- 自動再生のブラウザ差、許容遅延、キャッシュは方式選定をブロックしないため、実装・検証時の確認事項へ移した。

## 結論

### 決定

- `POST /interviews/chat` で次の質問テキストを取得する。
- 返ったテキストを `POST /interviews/tts` へ送り、音声を取得する。
- チャットと TTS の API 契約は統合しない。
- ストリーミングは今回の範囲では採用しない。
- TTS が失敗しても、取得済みのテキストで会話を継続できる構成を保つ。

### 決め手

- LLM がテキストを生成してから TTS を行う直列関係は、API を1本にまとめても変わらない。
- 2 API に分けることで、テキストを先に表示できる。
- TTS の遅延や失敗を、チャットの成功から切り離せる。
- 既存の API 仕様と [ADR-0008](../ADR/0008-会話用APIの構成.md) に整合し、バックエンドの API 契約を変更せずに実現できる。

### 見送った案

- **テキスト+音声を1レスポンスで返す案**: LLM → TTS の直列処理は消えず、音声完了までテキスト表示も遅らせるため。
- **統合ストリーミング案**: 遅延改善の余地はあるが、現行 ADR と衝突し、バックエンド・フロントエンドの両方の実装複雑度が大きいため。
