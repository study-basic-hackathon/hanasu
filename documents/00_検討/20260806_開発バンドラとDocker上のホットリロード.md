# 検討: 開発バンドラと Docker 上のホットリロード(Turbopack / webpack)

- ステータス: 検討中
- 開始日: 2026-08-06
- 最終更新: 2026-08-06
- 関連: [ADR-0001](../ADR/0001-フロントエンド実行環境.md)(ローカル開発は Docker 上で `next dev`)、[タスクメモ: 0805-Frontend動作検証用初期構築](../task-memo/0805-Frontend動作検証用初期構築.md)、[検討: create-next-app の生成オプション](20260806_create-next-appの生成オプション.md)、[検討: Docker 開発用ベースイメージ](20260806_フロントエンド開発用Dockerベースイメージ.md)

## 背景・きっかけ

ADR-0001 で「ローカル開発は Docker 上で `next dev` を実行する」と決定している。タスクメモ フェーズ1 には「ホットリロードが効くことを確認する(効かない場合は `WATCHPACK_POLLING=true` 等で対応)」というタスクがあるが、**この記述は webpack を前提としたもの**であり、Next.js 16 の既定であるバンドラでは前提が変わっている。

Docker の bind mount 越しにファイル変更を検知できるかは開発体験を大きく左右するため、着手前に前提と回避策を整理する。

## 論点

1. **開発時のバンドラを Turbopack のままにするか、webpack にフォールバックするか**
2. **Docker 上でホットリロードが効かなかった場合の回避策をどうするか**

## 事実確認(出典付き)

**Next.js 16 系のバンドラ:**

- **Next.js 16.0 から Turbopack がデフォルトバンドラ**になった。webpack を使うには `next dev --webpack` / `next build --webpack` でオプトインする(出典: [Next.js Docs: Turbopack](https://nextjs.org/docs/app/api-reference/turbopack)、ページ更新日 2026-08-03)
- Turbopack のネイティブバインディング対応プラットフォームは macOS(x64/ARM64)、Windows(x64/ARM64)、**Linux glibc(x64/ARM64)**、**Linux musl(x64/ARM64)**。非対応プラットフォームでは WASM にフォールバックし、その場合 Turbopack は使えない(出典: 同上)
- **Turbopack 公式ドキュメントに、ファイル監視(watcher)のポーリング設定に関する記載はない。** 設定できるのは `rules` / `resolveAlias` / `resolveExtensions` / `ignoreIssue` と `experimental.turbopack*` 系のオプションのみで、いずれも監視方式には関係しない(出典: 同上のページを通読して確認)
- Next.js 16.3 で Turbopack の dev サーバーはメモリ使用量が最大 90% 削減された(ディスクキャッシュとメモリエビクションが既定で有効化)(出典: [Next.js 16.3 リリースブログ](https://nextjs.org/blog/next-16-3))

**Docker 環境でのファイル監視の問題:**

- Docker / WSL コンテナ内で Turbopack がファイル変更を検知しないという問題が、**未解決の issue として複数残っている**
  - [#80665 Docs: how to enable turbopack's polling feature for the file watcher?](https://github.com/vercel/next.js/issues/80665)(**Open**。Docker + WSL2 で `next dev --turbopack` がファイル変更を検知しないという報告)
  - [#68255 Turbopack Watch does not see changes when running in Docker Container](https://github.com/vercel/next.js/issues/68255)
  - [#90825 Turbopack file watcher broken in Podman on macOS](https://github.com/vercel/next.js/issues/90825)
- 回避策として `--webpack` + `WATCHPACK_POLLING=true` へのフォールバックが報告されている(出典: 上記 issue、[DEV Community: Enabling Hot Reloading for Next.js in Docker](https://dev.to/yuvraajsj18/enabling-hot-reloading-for-nextjs-in-docker-4k39))
- `WATCHPACK_POLLING=true` は **webpack(watchpack)向けの環境変数**であり、Turbopack には作用しない

**本番ビルドへの影響:**

- ADR-0001 のとおり本番ビルドは Vercel 側で実行されるため、ローカルの開発コマンドをどちらにしても本番の成果物には影響しない

## 選択肢の比較

比較軸: **Docker 上での動作確実性**、**開発体験**、**本番との整合**。

| 観点 | **A案: Turbopack のまま(デフォルト)** | B案: 開発時のみ `next dev --webpack` |
|---|---|---|
| Docker bind mount でのホットリロード | **未解決 issue あり**。macOS の Docker Desktop で検知しない可能性がある | `WATCHPACK_POLLING=true` が効くという報告が多数 |
| 公式のポーリング設定 | **ドキュメントに記載なし** | `WATCHPACK_POLLING` / `NEXT_WEBPACK_USEPOLLING`(いずれも公式ドキュメント外の情報) |
| 開発体験(速度・メモリ) | **16.3 でメモリ使用量が最大 90% 削減**、ビルドも高速 | 従来どおり(Turbopack より遅い) |
| CPU 負荷 | 低(イベント駆動) | ポーリング有効時は常時ファイルを走査するため高くなる |
| Vercel 本番ビルドへの影響 | なし(Vercel 側でビルド) | なし(開発コマンドのみ切り替えるため) |
| 将来の保守性 | **公式デフォルトに追従できる** | webpack はオプトイン扱いで、いずれ非推奨になる可能性 |

**推奨: A案(Turbopack のまま)で開始し、実測して効かなければ B案を開発時のみのフォールバックとする。**

具体的な段取り:

1. `docker compose up` で `next dev`(Turbopack)を起動し、ホストでファイルを編集してホットリロードが効くか実測する
2. 効かない場合、まず Docker Desktop のファイル共有方式(VirtioFS など)を確認する
3. それでも効かない場合、開発用スクリプトを `next dev --webpack` に切り替え、`WATCHPACK_POLLING=true` を compose の環境変数に追加する
4. どの段階で解決したかをタスクメモの作業ログに記録する

B案に切り替える場合も、**開発コマンドのみを webpack にし、`next build` は Turbopack のままにする**(本番は Vercel 側でビルドされるため)。

## 懸念

| 懸念 | 深刻度の感触 | 解消に必要な確認 |
|---|---|---|
| Turbopack が Docker bind mount のファイル変更を検知せず、ホットリロードが効かない | **中**(開発体験に直結。ただし回避策はある) | フェーズ1 のタスクで実測する。NG なら上記の段取りでフォールバックする |
| タスクメモの「`WATCHPACK_POLLING=true` 等で対応」をそのまま実行しても、Turbopack では効かず原因調査に時間を溶かす | 中 | タスクメモの記述を修正済み(バンドラの切り替えが必要な旨を追記) |
| 開発だけ webpack、Vercel のビルドは Turbopack という差異により、ローカルで再現しない不具合が出る | 低 | Turbopack と webpack の既知の差異(CSS Modules の順序、Lightning CSS の小数精度など)を把握しておく。問題が出たらローカルでも `next build` で確認する |
| ポーリングを有効にすると CPU 使用率が上がり、ノート PC のバッテリー消費が増える | 低 | `node_modules` を監視対象から除外する。そもそも A案で済めば発生しない |

## 議論ログ

- **2026-08-06 ラウンド1**: Next.js 16.3 の Turbopack 公式ドキュメントを通読し、**ファイル監視のポーリング設定が公式には存在しない**ことを確認。GitHub issue #80665(Open)ほかで Docker 内のファイル検知問題が未解決であることを確認した。この結果、タスクメモに書かれていた「効かない場合は `WATCHPACK_POLLING=true` 等で対応」は webpack 前提の記述であり、Next.js 16 のデフォルト(Turbopack)では環境変数を足すだけでは効かないと判明。タスクメモの当該タスクを修正済み。まず Turbopack で実測する段取りを推奨として提示。ユーザーの最終決定待ち。

未確定(ステータス: 検討中)。

**推奨案**: 開発バンドラは **Turbopack(デフォルト)で開始**する。Docker 上でホットリロードが効かないことが実測で確認できた場合に限り、**開発コマンドのみ `next dev --webpack` + `WATCHPACK_POLLING=true`** にフォールバックする。
