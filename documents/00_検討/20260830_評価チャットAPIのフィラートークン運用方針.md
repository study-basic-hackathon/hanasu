# 検討: 評価API・チャットAPIでフィラートークンをLLMに見せるかどうかの運用方針

## 背景・きっかけ

ユーザーから「チャット画面のフィラーあり/なし表示トグルが評価APIへの送信内容に影響しているか」という質問を受けて調査したところ、次が判明した。

- 表示トグル（`TranscriptDisplayMode`、画面上のラベルは「フィラーあり」「フィラーなし」）は画面表示だけに使う状態で、送信データには影響していない。
- 評価API（`POST /evaluations`）へは、フロントエンドが常に `raw_content ?? content`（= フィラートークン付きの文字起こしがあれば優先）を送っている（[evaluation-api.ts:104](../../frontend/src/lib/evaluation-api.ts)）。
- バックエンドの構成・内容評価（`evaluate_interview()`）は、フィラートークンを「言い淀み」として明示的にLLMへ解釈させるプロンプトを持っている（[llm.py:87](../../backend/app/services/llm.py)）。これは意図的な設計であり、単純なバグではない。

ユーザーは「表示トグルの状態によらず常にフィラーなしの生データを評価APIへ送りたい」という要望を出し、これを実現する実装Issueとして [#218](https://github.com/study-basic-hackathon/hanasu/issues/218)（フロントエンド）・[#219](https://github.com/study-basic-hackathon/hanasu/issues/219)（バックエンドのプロンプト・API仕様書）を先行登録した。

その調査の過程で、チャットAPI（`/interviews/chat`、次の質問生成）にも全く同じ `raw_content ?? content` のロジックがあることが分かった（[interview-api.ts:63](../../frontend/src/lib/interview-api.ts)）。ただし、こちらのバックエンドプロンプト（`_build_system_prompt()` / `generate_reply()`）にはフィラーへの言及が一切なく、フィラートークン付きの生データが「LLMにどう解釈させるかの指示のないまま」次の質問生成のコンテキストに混入している状態だった。

評価APIとチャットAPIで実装（送信ロジック）は同じなのに、バックエンド側の扱い（意図の有無）が食い違っているため、ユーザーは「どちらかに寄せた方がよい」と考えており、その方針をこの検討記録に残すことにした。

## 論点

1. 構成・内容の評価（評価API）で、フィラートークンをLLMに「言い淀み」として解釈させ、評価コメント・アドバイスの材料にする価値があるか。それとも除去済みテキストだけで評価すべきか
2. 次の質問生成（チャットAPI）で、フィラートークンを含む生データをLLMに見せるべきか。見せるなら意図を明示したプロンプト設計に直す必要があり、見せないならフロントの送信ロジックを `content` 優先に変更する必要がある
3. 論点1・2の結論は同じ方針（両方とも除去する／両方とも見せて解釈させる）に揃えるべきか、それとも用途が違う（定性評価 vs 質問生成）ので別々の結論でよいか

## 事実確認（出典付き）

- **ADR-0009 は「定量指標（話速・フィラー数・間）はクライアントが算出し、`scores` として渡す。DB に保存するだけで LLM には渡さない」と定めている**（[0009-評価方式.md:21](../ADR/0009-評価方式.md)）。ただしこれは「フィラー数などの**数値**をLLMに渡さない」という意味に読め、「会話テキストにフィラートークン（`%えー%`）を含めるかどうか」を直接は決めていない。両者の関係はADR上では明示されていない。
- **評価仕様は「構成・内容はLLMが、定量の実測値・スコアを受け取らず、会話内容だけを定性評価する」とだけ定めている**（[評価仕様.md:26](../評価仕様.md)）。「会話内容」にフィラートークンをそのまま含めるかどうかへの言及はない。
- AmiVoiceは `keepFillerToken=1` によりフィラーを `%えー%` 形式でテキストに残す（[ADR-0010:41](../ADR/0010-音声認識とLLMの基盤選定.md)）。これはフィラー**数**を正規表現で数えるための選定理由であり、フィラートークンをLLMの入力として使うことを目的にした決定ではない。
- 実装（`backend/app/services/llm.py:87`）は、評価API向けのプロンプトにのみ「%で囲まれた語（例: %えー%）は文字起こしが検出したフィラー（言い淀み）です」という一文を持つ。この一文がいつ・どんな経緯で追加されたかを裏付ける検討記録・ADR・Issueは見当たらない。
- チャットAPI向けのプロンプト（`backend/app/routers/interviews.py` の `_build_system_prompt()`）にはフィラーへの言及が一切ない。
- `documents/backend/API仕様.md` の `turns[].content` 例・`history[].content` 例は、いずれもフィラートークン付き文字列（`"%えー% 田中と申します。..."`）になっている。
- フロントエンドの送信ロジックは評価API・チャットAPIとも `turn.raw_content ?? turn.content`（フィラーあり優先）で完全に同一（[evaluation-api.ts:104](../../frontend/src/lib/evaluation-api.ts) / [interview-api.ts:63](../../frontend/src/lib/interview-api.ts)）。
- 画面の表示トグル（`TranscriptDisplayMode`）はどちらのAPI送信にも影響しない。表示専用の状態であることは [#154](https://github.com/study-basic-hackathon/hanasu/issues/154) の完了条件にも明記されている（「文字入力の回答と面接官の発言は切り替えの影響を受けず、会話 API・評価 API へ渡す値、フィラー数、話速の算出も変わらない」）。

## 選択肢の比較

| 観点 | A案: 両APIとも常に除去（`content`優先） | B案: 両APIともフィラーを見せ、意図を明示する | C案: 用途で使い分ける（評価API=見せる／チャットAPI=見せない） |
|---|---|---|---|
| 評価APIの構成・内容評価 | フィラー言及プロンプトを削除。純粋に話の中身・論理構成だけを評価 | 現状維持。「言い淀みが多い」という文脈をコメント・アドバイスに反映し続ける | 現状維持（Bと同じ） |
| チャットAPIの質問生成 | 現状の実装（フィラーが紛れ込む）を修正し、`content`優先に変更 | プロンプトに「%で囲まれた語は言い淀みです。面接官として参考にしてよい」等の指示を新規に追加 | 現状の実装のまま追認（フィラーは見せない設計として明文化するだけ） |
| ADR-0009との整合 | 「LLMにはフィラー由来の情報を一切渡さない」という読み方に寄せられ、最も整合的 | 「フィラー数（数値）は渡さない」の範囲を超えてテキストで間接的に渡すため、ADRの意図を拡大解釈することになる | チャットAPI側はA案と同じ整合性、評価API側はB案と同じ拡大解釈が残る |
| 実装コスト | 小（[#218](https://github.com/study-basic-hackathon/hanasu/issues/218)・[#219](https://github.com/study-basic-hackathon/hanasu/issues/219)をそのまま実施し、チャットAPI側にも同種の1行修正を追加） | 中（チャットAPI側に新規プロンプト設計・検証が必要。評価APIは現状維持のため[#218](https://github.com/study-basic-hackathon/hanasu/issues/218)・[#219](https://github.com/study-basic-hackathon/hanasu/issues/219)を取り下げる） | 小〜中（評価APIは現状維持、チャットAPI側だけ[#218](https://github.com/study-basic-hackathon/hanasu/issues/218)相当の修正） |
| 評価コメントの質への影響 | 「言い淀みが多い」という切り口が評価コメントから消える。構成・内容スコアやアドバイス文がやや無機質になる可能性 | 現状の挙動を維持できるが、実際にコメント・アドバイスの質に効いているかは未検証（AB比較などの効果測定はしていない） | 評価APIはBと同じ |
| 次の質問生成への影響 | 記号ノイズが消え、質問生成の入力がクリーンになる | 面接官が「言い淀みに配慮した質問」をする可能性があるが、プロンプト次第で質問文に`%`が紛れ込むリスクや、効果が未検証な点はB案と同じ課題を持つ | Aと同じ（ノイズが消える） |
| 一貫性・説明のしやすさ | 高い（両API共通の方針で説明しやすい） | 高い（両API共通の方針で説明しやすい） | 低い（「なぜ評価APIだけフィラーを見せるのか」を説明する必要がある） |

## 懸念

| 懸念 | 深刻度の感触 | 解消に必要な確認 |
|---|---|---|
| A案（除去）にすると、構成・内容の評価コメントから「言い淀みへの言及」が失われ、評価の質が下がって見える可能性がある | 中（体感の話で定量評価できていない） | フィラー言及プロンプトの有無で実際に評価コメントの質がどう変わるか、サンプル回答で比較する |
| B案（チャットAPI側にもフィラー解釈を追加）にすると、質問生成LLMの出力に`%`付き記号が紛れ込む、または不自然な質問（「言い淀みが多いですね」等、面接官として不適切な言及）を生成するリスクがある | 中〜高（未検証のプロンプト変更のため） | プロンプト案を作った上で、実際に生成される質問文をレビューする |
| ADR-0009の「LLMにはフィラー由来の情報を渡さない」という原則を厳密に解釈すると、現状の評価API実装（フィラートークンをテキストで見せている）自体がすでに原則から逸脱している | 中（ADRの文言の解釈次第で評価が変わる） | ADR-0009をどう解釈するか、あるいは実態に合わせてADRを補足・改定するかを合わせて決める必要がある |

| 確認事項 | 回答が決定にどう効くか |
|---|---|
| 構成・内容の評価で「言い淀みの多さ」をコメント・アドバイスの材料にする価値を重視するか、それとも話の中身・論理構成だけに絞った評価を重視するか | A案（除去）かB/C案（評価APIは維持）かを分ける決め手になる |
| 次の質問生成で、面接官が「言い淀みに配慮した質問」をする振る舞いを新たに作り込みたいか、それとも今は手を付けず現状のノイズだけを取り除きたいか | チャットAPI側をB案（新規プロンプト設計）にするかA/C案（除去のみ）にするかを分ける決め手になる |
| ADR-0009の「LLMにはフィラー由来の情報を渡さない」という記述を、現状の評価API実装（テキストとしてフィラーを見せる）とどう整合させるか。ADRを補足・改定する必要があるか | 結論が出た後、ADR更新の要否が決まる |
