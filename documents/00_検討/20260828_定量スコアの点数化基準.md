## 背景・きっかけ

[Issue #57](https://github.com/study-basic-hackathon/hanasu/issues/57) で、話す速さとフィラーの実測値を 0〜100 点へ変換する基準点が提示された。基準点の間は線形補間し、最終的な点数を四捨五入した 0〜100 の整数とすることも提示済みである。

一方、現行仕様と暫定実装を照合すると、実測値を点数化する前の丸め、音声時間を取得できない回答や文字入力を含む場合の扱い、総合スコアへ含める項目、仕様の正本の置き場所は確定していなかった。これらは同じ入力から同じ結果を再現するために必要なため、本記録で選択肢と影響を整理する。

本 Issue は検討タスクであり、スコア計算コードは変更しない。ユーザー判断が揃うまでは ADR と仕様へ決定として反映せず、ドキュメント差分のユーザーレビューが終わるまでは Issue を完了扱いにしない。

## 論点

### 必須

1. **解消（2026-08-28）:** 線形補間には丸め前の実測値を使い、点数だけを最後に四捨五入する。
2. **解消（2026-08-28）:** 話速とフィラーは、それぞれの指標に必要な値を計測できた音声回答だけを集計する。文字入力と必要な値が欠測した音声回答は除外する。
3. **解消（2026-08-28）:** 「1回答あたり」の基準は採用しない。フィラーは計測できた音声回答のフィラー合計と音声時間合計から1分あたりを求め、Issue #57 の毎分基準で採点する。対象回答がなければフィラースコアを作らない。
4. **解消（2026-08-28）:** バックエンドが、話速・フィラー・構成内容のうち存在する項目を同じ重みで平均し、四捨五入する。任意の「間」は含めない。
5. **解消（2026-08-28）:** 全体共通の [評価仕様](../評価仕様.md) を計算規則の正本とし、ADR、API仕様、画面仕様から参照する。
6. **解消（2026-08-28）:** ADR-0009 内の矛盾を解消し、LLM には会話内容だけを渡して、定量の実測値・スコアは渡さない。

## 事実確認（出典付き）

- Issue #57 は、次の基準点、基準点間の線形補間、点数の四捨五入、上下限を提示している。出典: [Issue #57](https://github.com/study-basic-hackathon/hanasu/issues/57)。

| 指標 | 実測値 | 点数 |
|---|---:|---:|
| フィラー（1分あたり） | 2回以下 / 5回 / 10回 / 15回以上 | 100 / 50 / 20 / 0 |
| 話す速さ（1分あたり） | 0文字 / 100文字 / 200〜250文字 / 350文字 / 400文字 / 500文字以上 | 0 / 50 / 100 / 70 / 40 / 10 |

- ADR-0009 は、話速を「文字数 ÷ 発話時間」とし、話速・フィラー数をクライアントが点数化して `POST /evaluations` に渡すと決定している。テキスト入力のターンでは話速もフィラーも原理的に測れないことを理由に、取得可否の管理もクライアントの責務としている。点数化基準はフォローアップとして残っている。出典: [ADR-0009](../ADR/0009-評価方式.md)。
- 画面仕様は、文字入力で答えたターンでも入力文字列からフィラーを数えるとしている。回答方式は面接中に切り替えられる。出典: [S-08 本番モード](../frontend/01_design/screens/S-08_本番モード.md) 5章・6章。
- 比較時点の `origin/main`（`97445b8`）では、話速の表示上の適正域が S-14 と S-12 で `280〜320 文字/分` となっている。Issue #57 の満点域 `200〜250 文字/分` と不整合である。出典: 同コミットの [S-14 評価](../frontend/01_design/screens/S-14_評価.md) 更新前の4.3章 / [S-09〜S-13 練習モード](../frontend/01_design/screens/S-09-S-13_練習モード.md) 更新前の7章。
- 比較時点の `origin/main`（`97445b8`）の画面共通仕様、S-14、画面と API の対応、API仕様には、定量スコアの点数化基準が未決と残っている。出典: [画面共通仕様](../frontend/01_design/screen_common.md) 更新前の12章 / [S-14 評価](../frontend/01_design/screens/S-14_評価.md) 更新前の8章 / [画面と API の対応](../frontend/01_design/screen_api_map.md) 更新前の5章 / [API仕様](../backend/API仕様.md) 更新前の7章。
- 現行 STT 実装は、AmiVoice のフィラートークンを除去して前後の空白を取り除いた `clean_transcript` の文字数を数える。発話時間は AmiVoice 結果の最大 `endtime` とし、話速を整数、フィラー数/分を小数第1位へ丸めて返す。内部の空白や句読点は文字数に含まれる。出典: `backend/app/services/stt.py`。
- 現行フロント実装は、時間と文字数がともに有効な音声回答を合算して話速を求める。すべての回答に有効な時間がある場合だけフィラー数/分で採点し、文字入力または時間欠測が1件でもある場合は、全回答のフィラー合計を全回答数で割った「1回答あたり」へ切り替える。文字入力だけの場合は話速スコアを作らない。出典: `frontend/src/lib/evaluation-score.ts`。
- 現行の暫定基準は、話速を `280〜320 文字/分` で100点、フィラー数/分を1回ごとに15点減点する。1回答あたりのフォールバックは1回ごとに20点減点し、0〜100へ固定する。出典: `frontend/src/lib/score.ts`。
- 現行バックエンド実装は、`scores` 内にある整数の項目別スコアをすべて等しい重みで平均し、Python の `round` で整数にした値を `total_score` とする。算出者はバックエンドである。任意の `pause` が送られた場合も平均へ入る一方、話速がない場合は残った項目だけの平均になる。出典: `backend/app/routers/evaluations.py`。
- 比較時点の `origin/main`（`97445b8`）の ADR-0009 は「数値は LLM に渡すが採点はさせない」と「`scores` は DB に保存するだけで LLM には渡さない」を同じ決定内に記載しており、定量値を LLM の入力に含めるかが一意でない。一方、同時点の API仕様は、LLM が `turns` だけを見て定性評価するとしている。出典: [ADR-0009](../ADR/0009-評価方式.md) 更新前の2章 / [API仕様](../backend/API仕様.md) 更新前の5.5章。
- 比較時点の `origin/main`（`97445b8`）の API仕様は `total_score` を返すことを定めるが、合成方法と算出者は明記していない。また、例にある `284文字/分 = 80点` は Issue #57 の線形補間では90点となり、更新後の基準と不整合になる。出典: [API仕様](../backend/API仕様.md) 更新前の5.5章・5.6章。
- 現行のドキュメント規約では、決まっている仕様の正本は仕様ドキュメント、意思決定と理由は ADR、検討経緯は検討記録とする。Issue #57 の触る範囲には全体共通の評価仕様書が含まれていないため、基準値を ADR だけに置くとこの規約と不整合になる。出典: [ドキュメントの書き方](../README.md) 1章・2章。

## 選択肢の比較

### 1. 線形補間へ渡す実測値

| 観点 | A案: 丸め前の値で補間 | B案: 表示用に丸めた値で補間 |
|---|---|---|
| 算出 | 合算した文字数・フィラー数と時間から得た小数を、そのまま補間する。点数だけを最後に四捨五入する | 話速は整数、フィラー数/分は小数第1位へ丸めてから補間する |
| Issue 文言との整合 | 「最終的な点数は四捨五入」に最も素直 | 中間値も丸めることを追加で決める必要がある |
| 説明しやすさ | 表示値と点数の境界がまれに一致しない | 画面に出した実測値から点数を再計算しやすい |
| 現行実装との差 | 先に丸める処理の変更が後続実装で必要 | 現行の丸め順を維持できる |

**A案を採用（2026-08-28 ユーザー判断）。** 点数の再現性に必要な丸め箇所を1か所に限定し、線形補間による情報損失を避ける。

どちらの案でも、文字数は現行どおりフィラートークンを除いた `clean_transcript`、時間は AmiVoice が返す回答単位の `duration_ms` を合算する前提とする。これを変更する場合は、点数化ではなく実測値の定義から再検討する必要がある。

### 2. 時間欠測・文字入力混在時の対象回答

| 観点 | A案: 現行のセッション単位フォールバック | B案: 計測可能な音声だけで毎分評価 | C案: 欠測があれば定量項目を出さない |
|---|---|---|---|
| 話速 | 有効な時間と文字数がある音声回答だけで算出。1件もなければ省略 | A案と同じ | 全回答を計測できた場合だけ算出 |
| フィラー | 全回答を毎分評価できる場合だけ毎分基準。1件でも文字入力・時間欠測があれば、全回答を1回答あたり基準で評価 | 計測可能な音声回答だけを毎分基準で評価。その他の回答のフィラーは除外 | 1件でも文字入力・時間欠測があれば省略 |
| 利点 | 現行実装と Issue の推奨に一致し、文字入力のフィラーも評価できる | 毎分基準を使い続けられる | 異なる単位の基準を混ぜずに済む |
| 影響 | 1件の欠測でフィラーの評価尺度がセッション全体で変わる | 文字入力や欠測回答のフィラーが点数に反映されず、入力方式で有利になりうる | 項目別表示と総合スコアが欠けやすい |

**B案を採用し、指標ごとに必要な値が揃う回答を判定する（2026-08-28 ユーザー判断）。**

- 話速は `duration_ms > 0` と文字数を取得できた音声回答だけを対象とし、文字数合計と時間合計から1分あたりの文字数を求める。
- フィラーは `duration_ms > 0` とフィラー数を取得できた音声回答だけを対象とし、フィラー合計と時間合計から1分あたりの回数を求める。
- 文字入力と、対象指標に必要な値が欠測した音声回答は、その指標の分子・分母のどちらにも含めない。
- 対象回答が1件もなければ、その指標のスコアを作らない。

たとえば、30秒の対象音声でフィラーが2回なら4回/分となり、Issue #57 の線形補間により67点となる。60秒で2回なら2回/分で100点となる。

### 3. 1回答あたりフィラーの基準

| 観点 | A案: 現行基準を正式採用 | B案: 毎分基準を換算して新設 | C案: 1回答あたり基準を使わない |
|---|---|---|---|
| 基準 | `100 - 20 × 1回答あたりフィラー数` を最後に四捨五入し、0〜100へ固定 | 想定回答時間を決め、Issue #57 の毎分基準を1回答あたりへ換算する | 計測できた音声回答だけを集計し、Issue #57 の毎分基準を使う。対象回答がなければスコアなし |
| 利点 | 追加の仮定が不要で、現行実装を維持できる | 毎分基準との意味を揃えやすい | フィラーの評価尺度を常に回/分へ統一できる |
| 影響 | 毎分基準とは点数の傾きが異なる | 想定回答時間という新しい基準が必要になり、その妥当性を別途決める必要がある | 文字入力や時間・フィラー数が欠測した音声回答は評価対象外になり、フィラースコア自体がない結果も生じる |

**C案を採用（2026-08-28 ユーザー判断）。** フィラーは1分あたりの平均回数だけで評価し、「1回答あたり」のフォールバックは正式仕様にしない。

### 4. 総合スコア

算出者は、定性スコアが確定した後に評価結果を保存する**バックエンド**とするのが自然である。クライアント算出にすると、LLM の定性スコアを受け取った後に再度保存する API 契約が必要になる。

| 観点 | A案: 基本3項目のうち存在する項目を等価平均 | B案: 基本3項目が揃った場合だけ等価平均 | C案: `scores` に存在する全項目を等価平均 |
|---|---|---|---|
| 対象 | 話速・フィラー・構成内容。欠測項目は分母から除外。任意の「間」は含めない | 話速・フィラー・構成内容。1つでも欠けたら総合スコアなし | `pause` を含め、その時点で存在する全項目 |
| 現行実装との距離 | 通常時と欠測時は一致。`pause` がある場合だけ異なる | 文字入力だけの面接では変更が必要 | 一致 |
| 比較可能性 | 欠測有無で分母は変わるが、現在の画面を維持できる | 常に同じ3項目だが、総合スコアを表示できない結果が増える | 「間」の実装有無でも分母が変わる |

各案とも、平均値は**四捨五入した 0〜100 の整数**とする。Python の `round` は 0.5 が常に切り上がる四捨五入ではないため、採用後の実装 Issue で差異を解消する必要がある。

**A案を採用し、算出者をバックエンドとする（2026-08-28 ユーザー判断）。** 文字入力だけの面接でも総合スコアを返しつつ、任意指標の追加で総合スコアの意味が変わることを防ぐ。

### 5. 仕様の正本

| 観点 | A案: 全体共通の評価仕様書を新設 | B案: ADR を仕様の正本とする | C案: 画面仕様を仕様の正本とする |
|---|---|---|---|
| 配置 | `documents/評価仕様.md` に基準と計算規則を置き、ADR と画面仕様から参照する | 新しい ADR に基準と理由をまとめる | S-14 などに基準を置く |
| ドキュメント規約 | 一致 | 「仕様の正本は仕様ドキュメント」と不整合 | 全体共通・バックエンドにも効く基準が画面領域に閉じる |
| Issue の触る範囲 | 全体仕様書と API仕様の整合更新が追加になる | 記載された範囲内 | 記載された範囲内だが情報が複数画面へ重複しやすい |

**A案を採用（2026-08-28 ユーザー判断）。** [評価仕様](../評価仕様.md) を新設して計算規則の正本とし、ADR は選択理由を記録する。API仕様も整合対象に加える。

### 6. 定量値を LLM に渡すか

| 観点 | A案: LLM には渡さない | B案: 助言用に実測値だけを渡す |
|---|---|---|
| LLM の入力 | `turns` の会話内容だけ。`scores` と実測値は渡さない | 会話内容に加え、話速・フィラーの実測値を渡す。点数は渡さず、採点もさせない |
| 既存仕様との整合 | API仕様と ADR-0009 の「`scores` は LLM に渡さない」に一致 | ADR-0009 の「数値は LLM に渡す」に一致するが、API仕様の LLM 入力契約を変更する必要がある |
| 影響 | 定量の評価と定性評価を完全に分離できる。定量値を踏まえた助言はコードまたは別処理が必要 | LLM が話速・フィラーを踏まえた助言を作れるが、入力構築とプロンプトの後続実装が増え、助言の再現性にも影響しうる |

**A案を採用（2026-08-28 ユーザー判断）。** LLM の入力を会話内容だけに限定し、定量の実測値・スコアは渡さない。ADR-0009 の矛盾する文を整理し、API仕様と一致させる。本 Issue ではコードを変更しない。

## 結論

### 決定

- Issue #57 の基準点間を、丸め前の実測値で線形補間し、点数だけを最後に四捨五入する。
- 指標に必要な値を計測できた音声回答だけを合算し、文字入力と欠測回答は除外する。対象回答がなければ、その項目のスコアを作らない。
- フィラーは常に1分あたりの回数で評価し、「1回答あたり」のフォールバックは採用しない。
- 総合スコアはバックエンドが、話速・フィラー・構成内容のうち存在する項目を同じ重みで平均して四捨五入する。任意の「間」は含めない。
- 計算規則の正本を [評価仕様](../評価仕様.md)、決定理由の正本を [ADR-0020](../ADR/0020-定量スコアの点数化基準.md) とする。
- LLM には会話内容だけを渡し、定量の実測値・スコアは渡さない。

### 決め手

- 評価尺度を回/分に統一し、文字入力や欠測の有無で切り替えないこと。
- 中間丸めによる境界付近の点数差を避けること。
- 計測できる音声が一部でもあれば、その情報を評価に使えること。
- 任意指標の実装有無で総合スコアの意味を変えないこと。
- 仕様、決定理由、検討経緯の正本を分離する文書管理ルールに従うこと。

### 見送った案

- 表示用に丸めた実測値で補間する案。
- 文字入力・欠測があればフィラーを1回答あたりで評価する案。
- 欠測が1件でもあれば定量スコアをすべて作らない案。
- 総合スコアを基本3項目が揃った場合だけ作る案と、任意項目を含む全 `scores` の平均にする案。
- ADR または画面仕様だけを計算規則の正本にする案。
