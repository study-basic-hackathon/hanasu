## 背景・きっかけ

タスクメモ フェーズ1 で開発用 Dockerfile を作成し、フェーズ2 でそれを Dev Container として再利用する計画になっている。ベースイメージの選択は、フェーズ2 での開発ツール導入のしやすさに影響するため、Dockerfile 作成前に決めておく。

なお本イメージは**開発専用**である。ADR-0001 のとおり本番ビルド・実行は Vercel 側で行われるため、本番イメージのサイズ最適化は論点にならない。

## 論点

1. **開発用コンテナのベースイメージをどれにするか**(`node:24-bookworm-slim` / `node:24-alpine` / その他)

## 事実確認(出典付き)

- Turbopack のネイティブバインディング対応プラットフォームに **Linux glibc(x64/ARM64)と Linux musl(x64/ARM64)の両方**が含まれる。したがって Debian 系(glibc)でも Alpine(musl)でも Turbopack は動作する(出典: [Next.js Docs: Turbopack](https://nextjs.org/docs/app/api-reference/turbopack)、ページ更新日 2026-08-03)
- Next.js 16.3 の動作要件は Node.js 20.9 以上(出典: [Next.js Docs: Installation](https://nextjs.org/docs/app/getting-started/installation)、ページ更新日 2026-07-21)
- 本番ビルド・実行は Vercel 側で行われる(出典: [ADR-0001](../ADR/0001-フロントエンド実行環境.md))
- タスクメモ フェーズ2 に「`.devcontainer/devcontainer.json` を作成する(フェーズ1の compose / サービスを再利用する構成)」「コンテナ内の開発ツールを整備する(VSCode 拡張: ESLint・Prettier 等、git が使えること)」とある(出典: `documents/task-memo/0805-Frontend動作検証用初期構築.md`)

## 選択肢の比較

比較軸: **Dev Container 化(フェーズ2)との相性**、**環境の素直さ**、**イメージサイズ**。開発専用のため、サイズの優先度は低く置く。

| 観点 | **A案: `node:24-bookworm-slim`** | B案: `node:24-alpine` | C案: `node:24`(フル) |
|---|---|---|---|
| libc | glibc | musl | glibc |
| Turbopack 対応 | 対応 | 対応(Linux musl はサポート対象) | 対応 |
| イメージサイズ | 中 | **小** | 大 |
| Dev Container との相性 | **良い**(git・各種 CLI の導入が素直、VSCode Server の実績が多い) | ツール追加時に musl 由来の差異を踏むことがある | 良い(ただし冗長) |
| ネイティブモジュールのビルド | 素直(prebuilt binary が見つかりやすい) | musl 向け prebuilt が無く、ソースビルドになる場合がある | 素直 |
| 同梱ツール | 最小限(git は別途インストール) | 最小限(git は別途インストール) | git・build-essential 等を同梱 |
| AI ツール導入(フェーズ2 の任意タスク) | 素直 | musl 非対応のバイナリを踏む可能性 | 素直 |

**推奨: A案 `node:24-bookworm-slim`。** 理由:

1. **フェーズ2 の Dev Container 化まで一気に進める前提では、環境の素直さがサイズより重要。** VSCode Server や各種 CLI ツールは glibc 前提のビルドが多く、musl 固有の問題に時間を取られるリスクを避けられる
2. **開発専用のため、イメージサイズの利点が効かない。** 本番は Vercel 上でビルド・実行されるので、Alpine の小ささが本番のコールドスタートやレジストリ費用に効く場面がない
3. **フル版(C案)ほどの同梱ツールは不要。** git 等は Dockerfile で必要なものだけ追加すればよい

Node のメジャーバージョン `24` は [Node.js バージョンの選定と固定方法](20260806_Nodeバージョンの選定と固定方法.md) の推奨に従う。その決定が変われば、本イメージのタグも合わせて変更する。

## 懸念

| 懸念 | 深刻度の感触 | 解消に必要な確認 |
|---|---|---|
| ベースイメージのタグと `package.json` の `engines.node` がずれ、ローカルと Vercel で Node バージョンが食い違う | 中 | Dockerfile のタグと `engines.node` を同じメジャーバージョンに揃える。ずれ防止のため、両方をタスクメモの「決定事項」に明記する |
| Apple Silicon(ARM64)と Intel(x64)でメンバーの環境が混在する | 低 | `node:24-bookworm-slim` はマルチアーキテクチャ対応。Turbopack も ARM64 をサポートしているため、通常は問題にならない |
| `node_modules` をコンテナ側の named volume に分離する構成で、ホストとコンテナのアーキテクチャ差によりネイティブモジュールが不整合になる | 低 | ホスト側に `node_modules` を作らない運用にする(bind mount から除外) |
| Dev Container 化で必要なツール(git 等)が slim には入っていない | 低 | Dockerfile で明示的にインストールする。フェーズ2 のタスクに含まれている |

## 結論

**決定内容(2026-08-06)**:

| 項目 | 決定 |
|---|---|
| ベースイメージ | **`node:24-bookworm-slim`** |
| 公開ポート | **3000** |
| `node_modules` | **コンテナ側の named volume に分離**(ホスト側には作らない) |

**決め手**:

1. **Dev Container 化(フェーズ2)まで進める前提では、環境の素直さがサイズより重要。** VSCode Server や各種 CLI ツールは glibc 前提のビルドが多く、Alpine(musl)固有の問題に時間を取られるリスクを避けられる
2. **開発専用のためイメージサイズの利点が効かない。** 本番は Vercel 上でビルド・実行されるので、Alpine の小ささが本番のコールドスタートやレジストリ費用に効く場面がない
3. **メジャーバージョン `24` は [ADR-0002](../ADR/0002-Nodeバージョン.md) の決定に従う。**

**見送った案とその理由**:

- **`node:24-alpine`**: Turbopack は Linux musl をサポートしており動作自体は問題ないが、Dev Container での開発ツール導入時に musl 由来の差異を踏む可能性がある
- **`node:24`(フル)**: git・build-essential 等を同梱するが、必要なものを Dockerfile で明示的に足せば足りるため冗長

**残る注意点**:

- **ベースイメージのタグと `package.json` の `engines.node` を必ず同じメジャーバージョンに揃える。** 片方だけ更新するとローカルと Vercel で Node バージョンが食い違う
- slim には git が入っていないため、Dev Container で使うツールは Dockerfile で明示的にインストールする(フェーズ2 のタスク)
