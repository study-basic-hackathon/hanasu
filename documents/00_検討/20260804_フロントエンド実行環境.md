## 背景・きっかけ

Frontend 仕様書作成の一環として、フロントエンドの実行環境を検討する。

- フレームワークは Next.js を第一候補(React 単体も選択肢)
- ローカル開発は Docker 上で動かす方針
- 本番は AWS ECS または Amplify を想定していたが、既存の技術スタック.md では「デプロイ先: Vercel」と記載されているため、**ECS / Amplify / Vercel の3案比較**とする(2026-08-04 ユーザー回答)
- 比較で重視する軸は**コスト**(2026-08-04 ユーザー回答)

## 論点

1. **SSR やサーバー側機能(API Routes / Server Components)は必要か?** → 回答(2026-08-04、分析による見込み): 不要の見込み。全画面が認証後のため SEO 不要、データ取得は Go バックエンド API 経由で CSR 完結可能。画面仕様確定時に最終確認する。
2. **本番の実行環境はどれにするか?(ECS / Amplify / Vercel)** → 回答(2026-08-05): **C案 Vercel に決定**(詳細は「結論」参照)。
3. **ローカル Docker 開発と本番環境の整合(dev/prod parity)をどう考えるか?** → 各案の比較表に記載。完全一致するのは ECS のみ。
4. (派生)決定後に技術スタック.md の更新が必要。

## 事実確認(出典付き)

**リポジトリの現状:**

- フロントは TypeScript / Next.js、デプロイ先は Vercel と記載(出典: `documents/技術スタック.md`)
- インフラは AWS: ECS、ECR、Lambda、Chime SDK、RDS、Bedrock。Cognito と S3 は使わない想定(出典: `documents/技術スタック.md`)
- 必要 API は 認証 / 企業情報 CRUD / 音声認識 / 内容評価 / 会話用 の5種。API は認証ユーザーのみ実行可能(出典: `documents/必要api .md`)
- `backend/` `frontend/` `infra/` はすべて空(`.gitkeep` のみ)でコード未実装(出典: 2026-08-04 の `find` 結果)

**料金(2026-08 時点の Web 調査。参考値であり、正式見積り時は AWS Pricing Calculator / 公式ページで要再確認):**

- **Amplify Hosting**: ビルド $0.01/分、配信 $0.15/GB、ストレージ $0.023/GB/月、SSR リクエスト $0.30/100万件 + $0.20/GB-時。無料枠: ビルド 1,000分/月、配信 15GB/月、ストレージ 5GB、SSR 50万リクエスト/月(出典: [AWS Amplify 料金](https://aws.amazon.com/amplify/pricing/)、[u11d: Vercel vs Amplify 比較](https://u11d.com/blog/vercel-vs-aws-amplify-pricing-nextjs/))
- **ECS on Fargate**: $0.04048/vCPU-時 + $0.00444/GB-時(us-east-1。東京は1〜2割高)。最小構成 0.25vCPU / 0.5GB を常時起動で月 $9〜11 程度。加えて ALB が月 $17〜25 程度 + ECR ストレージ(出典: [AWS Fargate 料金](https://aws.amazon.com/fargate/pricing/)、[fortem.dev: Fargate 実コスト](https://fortem.dev/blog/aws-fargate-pricing-real-costs/))
- **Vercel**: Hobby プランは無料だが**個人・非商用利用に限定**。商用は Pro $20/ユーザー/月(出典: [Vercel Pricing](https://vercel.com/pricing)、[Vercel Hobby Plan ドキュメント](https://vercel.com/docs/plans/hobby))

## SSR 要否の整理(分析。事実ではなく必要 API 一覧からの推測)

必要 API から想定される画面: ログイン / 企業情報の一覧・登録・編集 / 会話(録音)画面 / 分析・評価結果表示。

- すべて認証後の画面 → 検索エンジンに載せる必要がなく **SEO 目的の SSR は不要**
- データ取得はすべて Go バックエンド API → **API Routes(BFF)も必須ではない**(必要になれば Go 側に寄せられる)
- 録音・Chime SDK 連携はブラウザ API / クライアント SDK で行うため **クライアント側処理**

→ **CSR 中心で十分、SSR なし(静的配信)で成立する見込み。** この場合3案とも実行可能で、静的ホスティングが使える Amplify / Vercel が構成として軽くなる。画面仕様の確定時に最終確認すること。

## 選択肢の比較

比較軸: **コスト(ユーザー指定の重視軸)** を主軸に、判断に必要な副軸を併記。

| 観点 | A案: ECS (Fargate) | B案: Amplify Hosting | C案: Vercel |
|---|---|---|---|
| **月額コスト(ハッカソン規模)** | **$25〜40 程度の常時課金**(Fargate + ALB + ECR) | **ほぼ $0**(無料枠内に収まる見込み) | Hobby: $0(ただし非商用限定)/ Pro: $20/ユーザー |
| 構築の手間 | 大(Dockerfile、ECR、クラスタ、ALB、デプロイパイプラインが必要) | 小(Git リポジトリ連携で CI/CD 込みの自動デプロイ) | 最小(Git 連携のみ) |
| ローカル Docker との一致 | ◎ 同じイメージを本番でも実行(完全一致) | △ 開発は Docker 可、ビルド・実行は Amplify 側(Node バージョンを揃える必要) | △ 同左(Vercel 側ビルド) |
| SSR が必要になった場合 | ◎ Node ランタイムを自由に構成可 | ○ 対応あり(内部的に Lambda。無料枠 50万リクエスト/月) | ◎ ネイティブ対応(最も相性が良い) |
| AWS 内完結(バックエンドとの一元管理) | ◎ | ○(AWS サービス) | ×(別プラットフォーム) |
| 既存ドキュメントとの整合 | 技術スタック.md の変更が必要 | 同左 | 整合(現行記載どおり) |
| 消し忘れリスク | あり(常時課金リソース) | ほぼなし(従量課金のみ) | なし |

### 推奨(決定はユーザー/チーム)

**B案: Amplify Hosting を推奨。** 理由:

1. 重視軸のコストで最優位: ハッカソン規模なら無料枠内でほぼ $0。ECS は使わなくても月 $25〜40 の常時課金が発生する
2. AWS 利用という当初想定(ECS or Amplify)を満たしつつ、構築の手間が最小。フロントに時間を使わず本体(音声分析)に注力できる
3. SSR 不要見込みの静的配信にも、後から SSR が必要になった場合にも対応できる
4. C案 Vercel は機能面で最良だが、Hobby プランの非商用限定が会社ドメインでの利用と衝突する懸念があり、Pro($20/月)にするとコスト軸で B案に劣る
5. A案 ECS は dev/prod parity(Docker 完全一致)と学習価値が強みだが、今回の重視軸はコストのため見送りが妥当。**バックエンド(Go)の ECS 方針には影響しない**

**ローカル開発(どの案でも共通):** `frontend/` に Dockerfile + compose を置き、`node` コンテナ内で `next dev` を実行する構成で成立する。B案/C案の場合、本番ビルドはプラットフォーム側で行われるため、コンテナの Node バージョンをプラットフォーム設定と揃えることだけ注意。

## 懸念

| 懸念 | 深刻度の感触 | 解消に必要な確認 |
|---|---|---|
| Vercel Hobby は非商用限定。会社ドメイン(techtical.co.jp)での利用が規約に抵触する可能性 | 中(C案採用時のみ) | 利用規約と社内判断。学習目的ハッカソンが「非商用」に収まるかの判定 |
| Amplify の Next.js 新メジャーバージョン対応が遅れることがある | 低〜中 | 採用する Next.js バージョンが Amplify サポート対象か、着手時に公式ドキュメントで確認 |
| Amplify ではビルド環境がローカル Docker と別系統になり、Node バージョン差異で「ローカルでは動くのにビルドが落ちる」が起こり得る | 低 | `.nvmrc` / compose / Amplify ビルド設定で Node バージョンを固定・統一 |
| ECS 案の場合、ALB 等の常時課金とハッカソン後の消し忘れ | 中(A案採用時のみ) | 撤収手順の用意 |
| 技術スタック.md が「デプロイ先: Vercel」のまま | 低 | 決定後に更新(未更新のままだと後続の仕様書と矛盾する) |

## 結論

**決定内容(2026-08-05): 本番のフロントエンド実行環境は C案 Vercel とする。**

- **決め手**: 今回は「Vercel を使って簡単にデプロイする」こと自体をやりたいというチーム方針。Git 連携のみでデプロイでき構築の手間が最小で、Next.js との相性も3案中最良。既存の `documents/技術スタック.md` の記載(デプロイ先: Vercel)とも整合するためドキュメント修正が不要。
- **見送った案とその理由**:
  - **A案 ECS (Fargate)**: 月 $25〜40 の常時課金と構築の手間(Dockerfile / ECR / ALB / パイプライン)がハッカソン期間には重い。重視軸のコストで最も不利。
  - **B案 Amplify Hosting**: コスト軸ではほぼ $0 で最優位として推奨したが、「Vercel で簡単にデプロイする」というチーム方針を優先し見送り。
- **残る注意点**: Vercel Hobby プランは個人・非商用利用限定。会社ドメインでの利用が規約に抵触しないか(学習目的ハッカソンが「非商用」に収まるか)は未確認のまま。抵触する場合は Pro($20/ユーザー/月)または B案 Amplify への切り替えを再検討する。
- **ローカル開発**: 方針どおり Docker 上で `next dev` を実行する構成とする。Vercel 側ビルドとの Node バージョン統一(`.nvmrc` 等)に注意。
