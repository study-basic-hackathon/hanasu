## 背景・きっかけ

Issue #86 により、後続のフロントエンドテスト実装を作り直さずに進めるため、単体テスト・コンポーネントテスト・E2E テストの責任範囲、各レベルのツール、Docker ローカル環境と将来の CI での実行方法を決める。今回の範囲では、テストライブラリの導入・テストコード・GitHub Actions は実装しない。

## 論点

1. **UT ランナーに Vitest / Jest のどちらを採用するか**（必須）
2. **React Testing Library をコンポーネントテストの共通ライブラリとして採用するか**（必須。ランナー選定と合わせて決める）
3. **Playwright を今回導入し、ローカル疎通確認から E2E を実施するか**（必須）
4. **UT・コンポーネント・E2E の責任範囲をどう分けるか**（必須）
5. **Docker ローカル環境と将来の CI の実行コマンドをどう定めるか**（必須）
6. **初回導入時からカバレッジ閾値を必須化するか**（任意）

| 2 | ローカル開発は `node:24-bookworm-slim` を用いる Docker Compose の `web` サービスで行う。依存追加後はイメージの再ビルドが必要で、lint / build は `docker compose run --rm web npm run <script>` で実行する | `frontend/Dockerfile`、`frontend/compose.yaml`、`CLAUDE.md`「フロントエンドの開発コマンド」 |
| 3 | コンポーネントと同期のページに加え、動的パラメータを受け取る async Server Component のページが 3 件存在する | `frontend/src/app/(with-header)/companies/[id]/edit/page.tsx`、`frontend/src/app/(with-header)/companies/new/page.tsx`、`frontend/src/app/(with-header)/evaluations/[id]/page.tsx` |

## 選択肢の比較

### 論点1・2: UT ランナーとコンポーネントテスト

比較軸は、Next.js 16.3 との適合、既存の App Router 構成での設定量、Docker / CI での実行容易性、後続の保守性とする。

| 観点 | A案: Vitest + React Testing Library | B案: Jest + React Testing Library |
|---|---|---|
| Next.js 16.3 との適合 | Next.js 公式に手順がある（事実4・5） | Next.js 公式に手順があり、`next/jest` が Next 固有の設定を提供する（事実4・6） |
| 同期の関数・Client Component | 対象にできる | 対象にできる |
| async Server Component | **対象外。E2E で担保する必要がある**（事実4） | **対象外。E2E で担保する必要がある**（事実4） |
| 導入時の設定 | Vite プラグイン / jsdom / パス解決設定を持つ（事実5） | `next/jest` を基盤に jsdom 等を設定する（事実6） |
| コンポーネントの検証方法 | React Testing Library で画面表示・ユーザー操作を検証する（事実7） | 同左（事実7） |
| 現時点の判断 | **採用** | 見送り |

### 論点3: Playwright の導入時期

| 観点 | A案: 今回導入し、ローカル疎通から E2E を実施する | B案: 今回は導入せず、UT / コンポーネントテストの定着後に再検討する |
|---|---|---|
| async Server Component の検証 | E2E で対象にできる（事実4） | テスト自動化では未カバーのまま残る |
| 実ユーザーフローの確認 | ブラウザ上の遷移・入力・表示を確認できる（事実8） | 手動確認のみ |
| ローカル導入コスト | ブラウザバイナリと依存を Docker / CI に用意する必要がある（事実8・9） | 追加コストはない |
| CI の前提 | `build` / `start` とブラウザ依存の準備が必要（事実8） | UT の実行だけで開始できる |
| 現時点の判断 | **採用** | 見送り |

### 論点4〜6: テスト範囲・実行・カバレッジ

| 論点 | たたき台 | 未決の理由 |
|---|---|---|
| UT | `src/lib/` の純粋関数、データ変換、境界値、バリデーションを Vitest で検証する | 決定済み（ADR-0015） |
| コンポーネントテスト | UI 部品と Client Component の表示、props、ユーザー操作・入力エラーを Vitest + React Testing Library で検証する | 決定済み（ADR-0015） |
| E2E | サインイン、応募企業情報の登録・編集、練習・面接・評価の主要遷移など、実ブラウザでしか保証できない利用者フローを Playwright で検証する | 決定済み。実装は #88 の対象外 |
| ローカル / CI のコマンド | UT は Docker の `web` サービス内、E2E はブラウザ依存を含む `e2e` サービスで行う。具体的なコマンドは ADR-0015 に定める | 決定済み（ADR-0015） |
| カバレッジ | 初回はレポート出力のみとし、実測値から閾値を決める | 決定済み（ADR-0015） |

## 懸念

| 懸念 | 深刻度の感触 | 解消に必要な確認 |
|---|---|---|
| async Server Component を UT / コンポーネントテストの対象と誤認する | 高 | 対象外をテスト方針に明記し、E2E の導入可否と対象フローを決める |
| Playwright を Docker 開発イメージに追加すると、ブラウザ依存とイメージサイズが開発ループに影響する | 中 | E2E を `web` に同居させるか専用イメージ / CI ジョブに分離するかを、導入 Issue で最小構成を検証する |
| カバレッジ閾値を実測前に固定して、立ち上げを妨げる | 中 | 初回にレポートのみを出し、対象・計測値を確認してから別 Issue で閾値を決めるか判断する |
| スナップショット中心のテストで、利用者の操作や意味的な表示を保証できない | 中 | React Testing Library の role / label 等を基本とし、スナップショットの採否を方針で限定する |

## 議論ログ

### 2026-08-22

- Issue #86 を起点に検討を開始した。リポジトリの現状と、Next.js / React Testing Library / Playwright の公式ドキュメントを確認した（事実1〜9）。
- ユーザーが **Vitest + React Testing Library を UT・コンポーネントテストに、Playwright を E2E に使い、初回のカバレッジはレポートのみとする**方針を承認した。
- 実行コマンドと実装の責務を ADR-0015 に昇格した。#88 は Vitest と React Testing Library による UT・コンポーネントテストのみを実装し、Playwright の E2E 実装は別 Issue とする。

## 結論

| 論点 | 決定 |
|---|---|
| UT ランナー | **Vitest** |
| コンポーネントテスト | **Vitest + React Testing Library** |
| E2E | **Playwright** |
| 責任範囲 | UT は純粋関数等、コンポーネントテストは UI 部品・Client Component、E2E は async Server Component と主要な利用者フロー |
| ローカル / CI | UT は `web` サービス、E2E は Playwright 用の `e2e` サービス。コマンドは ADR-0015 が正本 |
| カバレッジ | **初回はレポート出力のみ**。閾値は実測後に別 Issue で再検討 |

詳細な決定、理由、トレードオフ、フォローアップは [ADR-0015](../ADR/0015-フロントエンドのテスト方針.md) が正本である。
