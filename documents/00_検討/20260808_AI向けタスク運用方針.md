## 論点

1. Issue と task-memo の二重管理をどう解消するか（どちらが「正」か）
2. 「1タスク = 1PR」を、着手前に判定できる基準に落とすとどうなるか
3. Issue に何を書けば、AI が追加質問なしで着手し、自分で完了判定できるか
4. 複数人 + 各自 AI の並行実行で、コンフリクトと手戻りをどう防ぐか

## 選択肢の比較

### 論点1: Issue と task-memo の役割分担

比較軸: 二重管理の起きにくさ / AI からの読み取りやすさ / 他メンバーからの進捗の見えやすさ / 移行コスト

| 観点 | A案: Issue 一本化（task-memo 廃止） | B案: 役割分離（推奨） | C案: 現状維持（両方に書く） |
|---|---|---|---|
| 作業単位の正 | Issue | Issue | 曖昧 |
| 決定・作業ログの置き場 | Issue コメント / PR 本文 | **task-memo は新規作成せず、決定は ADR、経緯は 00_検討/、作業ログは PR 本文に集約** | 両方 |
| 二重管理 | 起きない | 起きない（住み分けが明確） | **既に発生中** |
| AI からの読み取り | `gh issue view` が必須。コメント欄は履歴が長くなると読みにくい | Issue（何を作るか）+ ADR/検討記録（なぜ）でリポジトリ内から根拠を辿れる | 情報が分散し、どちらが最新か不明 |
| 進捗の可視性 | 高い | 高い | 低い（メモはローカルブランチに埋もれる） |
| 移行コスト | 既存メモ4件の内容を Issue へ転記 | **既存メモはそのまま残し、Issue からリンクするだけ** | ゼロ |
| リスク | 0805 メモのような濃い作業ログを Issue コメントに書くと流れる | 「どこに書くか」の判断が1つ増える | 差分が開き続ける |

**推奨は B案。** 理由: 既に ADR / 検討記録の2層が機能しており、task-memo の固有価値（決定事項・作業ログ）はその2層 + PR 本文で吸収できる。一方 `ステータス` `優先度` `タスク一覧` は Issue の標準機能と重複しており、Issue に寄せた時点で task-memo に残す意味が薄い。既存4件は削除せず、対応する Issue に相互リンクを張って凍結する。

### 論点2: 「1タスク = 1PR」の判定基準（案）

着手前に Issue 1件を見て判定できる形にする。

**1件に収める条件（すべて満たすこと）**

- 完了条件がチェックボックス **3〜5個以内**で書ける
- 触る範囲が **`frontend/` `backend/` `infra/` のいずれか1つに収まる**（複数人並行のため、領域をまたぐタスクは分割が前提）
- 検証手段が1つに定まる（画面が表示される / テストが通る / API が 200 を返す、など）
- AI の 1〜2 セッションで実装から検証まで到達する見込み（目安: 新規 300 行 / 変更 200 行程度）

**分割の合図**

| 合図 | 分割の仕方 |
|---|---|
| タイトルに「〜と〜」が入る | 2件に割る |
| 未決事項がある（ライブラリ選定・方式選定など） | 「決める」Issue（調査・検討）と「作る」Issue に割り、後者の前提に前者を書く。`decompose-task` の**事前決定(必須/任意)**の考え方をそのまま使う |
| フロントとバックの両方を触る | **API 契約（リクエスト/レスポンスのスキーマ）を決める Issue を先に立て**、frontend 実装 / backend 実装を別 Issue にする |
| 完了条件に「〜など」「一通り」が入る | 条件が書けていない = 粒度以前に仕様が未確定。仕様起案の Issue に格下げする |

**細かすぎる合図**（分割しすぎ）

- 1ファイル / 1関数単位。レビュー単位として意味を成さず、依存順の管理コストが実装コストを上回る
- 「〜を確認する」だけの Issue。検証は実装 Issue の完了条件に内包させる（`decompose-task` の「検証タスクを独立させる」は**メモ内のチェック項目レベル**の話であり、Issue レベルでは分けない）

### 論点3: Issue に書く項目（案）

AI が **追加質問なしで着手でき、自分で完了を判定できる**ことを基準に絞り込む。

| # | 項目 | 必須 | なぜ必要か（AI 視点） |
|---|---|:---:|---|
| 1 | **目的** — 1〜2行で「なぜやるか」 | ◯ | 実装中の判断の分岐で拠り所になる。無いと AI が過剰実装に倒れる |
| 2 | **完了条件（受け入れ基準）** — チェックボックス、観測可能な形 | ◯ | AI が自分で完了判定するための唯一の根拠。「ログイン画面ができる」ではなく「`/login` にアクセスするとメール・パスワード入力欄が表示される」 |
| 3 | **やらないこと（スコープ外）** | ◯ | **AI は放っておくと広げる。** 明示的な禁止が最も効く項目 |
| 4 | **触る範囲** — ディレクトリ / ファイル | ◯ | 複数人並行のコンフリクト回避に直結 |
| 5 | **検証方法** — 実行するコマンド | ◯ | 例: `docker compose run --rm web npm run lint`。AI が自己検証できないと、動かないコードで PR が出る |
| 6 | **前提・依存** — 依存 Issue 番号、適用される ADR | ◯ | 決定済みの方針を無視した実装を防ぐ |
| 7 | **参考リンク** — CLAUDE.md / ADR / 検討記録 / 既存コード | △ | 6 と重なる場合は省略可 |
| 8 | **未決事項** — 事前決定（必須 / 任意）の区分付き | △ | 未決があるなら、AI が勝手にデフォルトで埋めないための歯止め。`decompose-task` の規則を踏襲 |
| 9 | 実装方針のヒント | △ | 書けるなら書く程度 |

現行 task-memo の `ステータス` `優先度` は **Issue の open/closed・ラベル・マイルストーンに置き換える**（項目としては持たない）。

### 論点4: 並行実行のルール（案）

- **1 Issue = 1 assignee = 1 ブランチ = 1 PR。** assignee 未設定の Issue は着手しない
- **領域（frontend / backend / infra）をまたぐ Issue を作らない。** またぐ場合は論点2の分割ルールで割る
- **共有ファイル（CLAUDE.md・README・`documents/template/`）の編集は、原則その Issue の「仕上げ」でのみ行う。** 複数 PR が同時に CLAUDE.md を触ると必ず衝突する
- 着手前に `git pull origin main` してからブランチを切る

### 論点5: 命名の統一（案）

| 対象 | 案 | 現状との差 |
|---|---|---|
| ブランチ | `feature/issue-<N>-<英語スラッグ>` 例: `feature/issue-2-login-page` | 4通りに割れている。CLAUDE.md の `feature/<内容>` を改訂する必要あり |
| Issue タイトル | `[<領域>]<日本語の要約>`（現行どおり） | **既に統一されている。変更不要** |
| PR タイトル | `<prefix>: <日本語の要約>`（prefix はコミット規約と同じ `add:` `fix:` 等） | #13 に prefix なし、#12 が `feat:`（規約は `add:`）。prefix 語彙の確定が必要 |
| PR 本文 | `Closes #<N>` を必ず含める | 未確認・未徹底 |

### 論点6: 決まりの置き場所（案）

| 何を | どこに | 理由 |
|---|---|---|
| Issue の記載項目 | `.github/ISSUE_TEMPLATE/task.yml` | 起票時に強制でき、空 Issue（現状の主要因）を防げる |
| PR の記載項目 | `.github/pull_request_template.md` | `Closes #N` と検証結果の記載漏れを防ぐ |
| 粒度・並行実行・命名の規約 | `CLAUDE.md` | **AI が毎回読む唯一の場所。** ここに書かないと AI は従わない |
| Issue 起点の作業手順（`gh issue view` → 完了条件を TodoWrite に展開 → 実装 → 検証 → PR） | `CLAUDE.md` | 「Issue #N を実装して」だけで通るようにするため |
| タスク分解の出力先変更 | `decompose-task` スキル | 現在は task-memo に書き込む仕様。Issue に書く / Issue 本文案を提示する、に変える必要がある |

## 懸念

| 懸念 | 深刻度の感触 | 解消に必要な確認 |
|---|:---:|---|
| **既存 Issue 9件の本文が空のまま。** テンプレートを作っても、既存分は AI が着手できない | 高 | 着手直前に起票者が埋める運用にするか、AI に本文の草案を書かせて起票者が承認するか（後者は「タスク分解を AI に任せる」というヒアリング結果と整合的） |
| CLAUDE.md の記述が実態から遅れている（backend/infra を「未実装」と記載） | 中 | AI は CLAUDE.md を前提に動くため、誤った前提で判断する。本方針の適用と同時に更新すべき |
| ルールを増やしすぎるとハッカソンの速度を落とす | 中 | 必須項目を論点3の 1〜6 に絞る。任意項目は空欄可とする |
| `decompose-task` はユーザー個人のスキル（`~/.claude/skills/`）で、他メンバーの環境には無い | 中 | 他メンバーも同じ運用にするなら、規約は CLAUDE.md 側に書く必要がある（スキルに依存させない） |
| PR レビューを誰がするか未確認。AI 実装の PR をノーレビューでマージすると品質が読めない | 中 | チーム内の合意事項。`/code-review` を PR 前に回す運用にするかも含めて |

## 結論

### 決定内容（2026-08-08）

| # | 決定 | 決め手 |
|---|---|---|
| 1 | **タスク管理の器は GitHub Issue。** task-memo は**新規作成を停止**し、既存4件は削除せず対応 Issue から相互リンクして凍結する | 決定 = ADR、経緯 = `00_検討/` の2層が既に機能しており、task-memo の固有価値（決定事項・作業ログ）はその2層 + PR 本文で吸収できる。一方 `ステータス` `優先度` `タスク一覧` は Issue の標準機能と完全に重複する |

### 適用範囲の限定に伴う設計の修正（論点6の差し替え）

「まず自分の作業だけ」という制約により、**リポジトリ共有物の変更は先行させない**。当初案から次のとおり置き場所を変更する。

| 何を | 当初案 | 修正後 | 理由 |
|---|---|---|---|
| Issue の記載項目 | `.github/ISSUE_TEMPLATE/task.yml` | **`documents/template/issue-template.md`** を作り、自分が起票・更新する Issue に手でコピーして使う | `.github/ISSUE_TEMPLATE/` は**全メンバーの起票画面を変えてしまう**ため合意が要る。`documents/template/` へのファイル追加なら他メンバーの作業に影響しない |
| PR の記載項目 | `.github/pull_request_template.md` | **保留**（自分の PR 本文に手で書く） | 同上。PR テンプレートは全員の PR 作成画面に出る |
| 粒度・命名の規約 | CLAUDE.md | **保留**（本検討記録を参照先とする） | CLAUDE.md のブランチ命名規約（`feature/<内容>`）の改訂はチーム合意が要る。自分は `feature/issue-<N>-<slug>` で運用し、実績を作ってから提案する |
| Issue 起点の AI 作業手順 | CLAUDE.md | **要確認**（ユーザー判断） | 他メンバーのワークフローを壊さない追記だが、共有ファイルの変更にあたるため確認する |

**この修正のトレードオフ**: CLAUDE.md に書かない以上、AI は運用ルールを自動では読まない。**Issue 本文そのものが AI への指示になる**ため、本文の記載品質（決定内容3の6項目）が唯一の担保となる。

### `decompose-task` スキルの扱い（未決）

現状の `decompose-task` は **task-memo の `## タスク` セクションに書き込む**仕様（出典: `~/.claude/skills/decompose-task/SKILL.md` 大原則1・「置き場所・書式」）。task-memo の新規作成を停止した本決定と噛み合わなくなった。

さらに、単なる出力先の切り替えでは済まない**粒度の差**がある:

- 現状スキルの出力 = 1つのメモ内の「フェーズ付きチェックリスト」
- 本決定での対応物 = **複数の Issue（1タスク = 1PR）への分割**、必要なら親トラッキング Issue を伴う

| 案 | 内容 | 備考 |
|---|---|---|
| A | スキルを「Issue 群への分解」に拡張 | 本決定と整合的だが、task-memo 運用の他プロジェクトが使えなくなる |
| B | 出力先だけ切り替え可能にする | 改修が小さいが、1つのスキルに2つの運用が同居して読みにくい |
| C | 現状維持 | スキルが死蔵する |

**決定（2026-08-08）: A〜C のいずれでもなく、スキルを2つに分けた。** 粒度の考え方は両者で同一文言とする（ユーザー判断）。

| スキル | 用途 | 変更内容 |
|---|---|---|
| `decompose-task`（既存） | Markdown のタスクメモに分解する | 「タスクの粒度」セクションを追加。description に住み分けを明記 |
| `decompose-issue`（**新設**） | GitHub Issue に分解する | 新規作成 |

**共通化した粒度の定義（2階層）**

- **階層1: 作業単位（Issue 1件 / タスクメモ 1件）= 1PR** — 完了条件3〜5個以内 / 触る範囲が1領域 / 検証手段が1つ / AI 1〜2セッション。分割の合図・細かすぎる合図も共通
- **階層2: 単位の中の項目 = 1作業** — 作成・設定・確認のいずれか1つ。検証項目を独立させる。完了条件は観測可能な形で書く

`decompose-issue` だけが持つ要素（Issue が共有物であることに由来する）:

- `gh issue create` / `edit` の実行前に**必ず案を提示して承認を得る**
- **他人がアサインされた Issue を勝手に書き換えない**
- 親トラッキング Issue の扱い
- **Issue 本文では相対リンクが機能しない**ため完全 URL を使う
- `gh` はリポジトリ内から実行する（外だと `not a git repository` で失敗する）

### 未決事項の Issue 化（2026-08-08 実施）

「決める作業もタスク化すべきか」という論点に対し、次の判定基準を定めた（`decompose-issue` と [issue-template.md](../template/issue-template.md) の両方に記載）。

| 条件（いずれかに該当） | 扱い |
|---|---|
| **複数の Issue をブロックする** | **独立した「決める Issue」にする** |
| **後から変えるとやり直しコストが高い** | 同上 |
| どちらにも該当しない | 実装 Issue の「未決事項（事前決定・任意）」に推奨案付きで残す |

**「決める Issue」の完了条件は「決定が記録されたこと」**であり、実装ではない。
