## 選択肢の比較

### 論点1: UI ライブラリの範囲

比較軸は「ハッカソン期間内に画面モック11本を作り切れるか」を中心に置いた。

| 観点 | **A案: Tailwind CSS のみ** | B案: Tailwind + shadcn/ui | C案: Tailwind + ヘッドレス UI（Radix / Headless UI） |
|---|---|---|---|
| 導入コスト | **ゼロ**（導入済み・事実1） | CLI 実行と設定ファイルの追加。依存も増える | 依存の追加のみ |
| 必要部品との適合 | **十分。** 必要なのは素朴な部品だけ（事実7） | **過剰。** 強みであるモーダル・コンボボックス等が1つも登場しない（事実7） | **過剰。** フォーカス管理が要る箇所が確認2つだけ（事実7） |
| デザイン原本の再現 | 原本の値をそのまま書ける | **既定テーマを独自値で上書きする手間が乗る**（事実5）。上書き漏れがあると原本とズレる | 見た目を持たないため、結局すべて自分で書く |
| Next.js 16 での不確実性 | **なし** | **公式に対応の明記がなく、自分たちで検証することになる**（事実10） | 同左（Next.js 16 前提の情報は少ない） |
| 部品実装の手間 | **自作が要る**（ボタン・カード・入力欄など） | 生成コマンドで済む | 見た目は自作、挙動のみ任せられる |
| アクセシビリティ | 自分たちで担保する | **既定で配慮が入る** | **既定で配慮が入る** |
| 後から変更する容易性 | **足すのは容易**（Tailwind の上に載る） | 外すのはコンポーネントの書き直しになる | 同左 |

**A案を推奨する。** 決め手は事実7 — shadcn/ui やヘッドレス UI が引き受けてくれる複雑さ（フォーカストラップ・キーボード操作・重ね合わせ）が、**この画面群にはそもそも発生しない**。加えて事実5により、入れても原本に合わせる上書き作業が別途必要になる。**後から足すのは容易**なため、部品の作り込みが負担になった時点で再検討すればよい。

### 論点2: デザイントークンの持ち方

| 観点 | **A案: `@theme` でトークン化** | B案: 任意値を都度書く（`bg-[#0f766e]`） | C案: `:root` の CSS 変数を任意値から参照 |
|---|---|---|---|
| 書き方の統一 | **クラス名が語彙になり、Issue をまたいでも揃う** | **揃わない。** 同じ色に別の書き方が生まれる | 変数名で揃うが、`bg-[var(--accent)]` と冗長 |
| 原本を直す時の追従 | **定義1箇所で全画面に効く** | **全画面を grep して直す** | 定義1箇所で効く |
| Tailwind v4 との整合 | **v4 の標準機能**（`@theme`） | 標準の書き方ではあるが、値が散る | v4 では `@theme` があるため回りくどい |
| 導入の手間 | **色12種・文字7種・寸法3種を書き写すだけ**（事実4） | ゼロ | A案とほぼ同じ |
| 慣れていない人の書きやすさ | 語彙を覚える必要がある | **原本の値をそのまま貼れる** | 変数名を覚える必要がある |

**A案を推奨する。** 決め手は事実8 — **画面モック Issue が11本あり、書き方が割れると後からの統一コストが大きい**。かつ事実4のとおりトークン化する値は有限（22個）で、写す手間は一度きりで済む。

### 論点3: 共通部品の切り出し基準

| 観点 | A案: 先に一式を作り切る | B案: 2回目に出たら切り出す | **C案: 全画面で確実に使うものだけ先に作り、残りは B案** |
|---|---|---|---|
| #51 の作業量 | **大きい**（使うか分からない部品まで作る） | **最小** | 中 |
| 画面モック11本の重複 | 起きにくい | **起きる**（先行する Issue が各自で書く） | **主要な部品では起きない** |
| 未使用部品 | **生まれやすい** | 生まれない | 生まれにくい |
| 画面モック Issue の並行実施 | しやすい | **しにくい**（先行 Issue の切り出し結果を待つ） | しやすい |

**C案を推奨する。** #51 では**全画面に確実に出るもの**（グローバルヘッダー・カード・ボタン・入力欄・チップ・スコアバー）に限って作り、それ以外は各画面 Issue で書いたうえで2度目に必要になった時点で切り出す。事実8のとおり画面モック Issue が11本あり並行させたいため、B案単独では先行 Issue 待ちが発生する。

**置き場所**は `frontend/src/components/ui/`（画面をまたぐ汎用部品）と `frontend/src/components/layout/`（ヘッダーなど骨格）に分け、**1画面でしか使わないものは切り出さずその画面の中に置く。**

## 結論

**UI ライブラリは Tailwind CSS のみとする。** shadcn/ui 等のコンポーネント集・ヘッドレス UI・チャートライブラリを追加しない。

| 論点 | 決定 | 決め手 |
|---|---|---|
| UI ライブラリ | **Tailwind CSS のみ**（追加なし） | 設計書に現れる部品が素朴で、コンポーネント集の強みが発揮される場面がない（事実7）。配色が独自値のため入れても上書き作業が乗る（事実5）。**後から足すのは容易** |
| デザイントークン | **`globals.css` の `@theme` に定義**し、ユーティリティクラスとして使う | 画面モック Issue が11本あり書き方の割れを防ぐ必要がある（事実8）。トークン化する値は有限（事実4） |
| 共通部品 | **全画面で確実に使うものだけ #51 で先に作り、残りは2度目に必要になった時点で切り出す。** 置き場所は `src/components/ui/` と `src/components/layout/`、1画面限りのものは切り出さない | 画面モック Issue を並行させたい一方、未使用部品を作りたくない（事実8） |

### 見送った案と理由

- **shadcn/ui の追加**: 引き受けてくれる複雑さがこの画面群に発生しない（事実7）。加えて Next.js 16 での動作が公式に明記されておらず（事実10）、検証の手間が乗る。**部品の自作が負担になった時点で再検討する。**
- **ヘッドレス UI（Radix / Headless UI）の追加**: フォーカス管理が要る確認は S-06 の削除と S-08 の面接終了の2箇所だけで、依存を足す割に効果が薄い。
- **デザイントークンを任意値で都度書く**: 原本の値を直したときに全画面を追う必要があり、11本の Issue で書き方が割れる。
- **共通部品を先に一式作り切る**: 使うか分からない部品まで作ることになり、#51 が重くなる。
