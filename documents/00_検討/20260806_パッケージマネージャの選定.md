## 背景・きっかけ

`frontend/` に Next.js プロジェクトを作成する前に、パッケージマネージャを決める必要がある。決定は次の3か所に影響する。

- **Vercel のビルド**: lockfile からパッケージマネージャが自動検出される(ADR-0001 でデプロイ先は Vercel に決定済み)
- **Docker 開発環境**: `node_modules` をコンテナ側に分離する構成(タスクメモ フェーズ1)での挙動
- **create-next-app の実行コマンド**: 生成時に lockfile の種類が決まる

タスクメモの選択肢は npm / pnpm の2つ。

## 事実確認(出典付き)

**Vercel 側の挙動:**

- Vercel は **lockfile を見てパッケージマネージャを自動検出**する。`package-lock.json` → npm、`pnpm-lock.yaml` → pnpm、`yarn.lock` → Yarn、`bun.lock(b)` → Bun。**lockfile が無い場合のデフォルトは npm**(出典: [Vercel Docs: Package Managers](https://vercel.com/docs/package-managers)、ページ更新日 2026-07-01)
- Corepack を使う場合のみ、lockfile より `package.json` の `packageManager` フィールドが優先される(出典: 同上)
- npm のバージョンは Node のバージョンに連動する(Node 20 / 22 → npm 10)(出典: 同上)
- pnpm のバージョンは `pnpm-lock.yaml` の `lockfileVersion` で決まる。**`lockfileVersion: 9.0` の場合は pnpm 9 か 10 のどちらかで、新しいプロジェクトは 10 が優先される。どちらが使われたかはビルドログで確認する必要がある**(出典: 同上)
- Project Settings の Override で `pnpm install` を指定した場合、**ビルドコンテナ内で最も古い pnpm(pnpm 6)が使われる**という注意書きがある(出典: 同上)

**create-next-app 側:**

- `--use-npm` / `--use-pnpm` / `--use-yarn` / `--use-bun` で明示指定できる(出典: [Next.js Docs: create-next-app](https://nextjs.org/docs/app/api-reference/cli/create-next-app)、v16.3.0)
- `npx create-next-app@latest` で実行した場合は npm、`pnpm create next-app` なら pnpm がそれぞれ既定になる(出典: 同上)

## 選択肢の比較

比較軸: **Vercel との整合**、**Docker / Dev Container での構築の手間**、**性能面の利点**。

| 観点 | **A案: npm** | B案: pnpm |
|---|---|---|
| Vercel での検出 | `package-lock.json` → npm 10。lockfile が無い場合のデフォルトも npm | `pnpm-lock.yaml` → pnpm。`lockfileVersion 9.0` は **pnpm 9 か 10 のどちらか**(ビルドログで要確認) |
| コンテナ内の準備 | **node 公式イメージに同梱、追加作業なし** | `corepack enable` 等のセットアップが1手増える |
| Docker で `node_modules` を named volume に分離 | **フラットな構造で素直** | シンボリックリンク + `.pnpm` ストア構造のため、volume 分離時の挙動確認が必要 |
| インストール速度・ディスク使用量 | 標準 | **高速・省ディスク**(複数プロジェクトを持つと効く) |
| モノレポ対応 | workspaces あり | **workspaces が強力** |
| create-next-app | `npx create-next-app@latest` がそのまま npm | `pnpm create next-app` または `--use-pnpm` |

**推奨: A案 npm。** 理由:

1. **今回の構成では pnpm の利点が効きにくい。** 速度・省ディスクの恩恵は依存の重複が多い複数プロジェクト環境で大きいが、本リポジトリのフロントエンドは単一プロジェクト。モノレポ予定も現時点ではない
2. **Vercel・Docker 双方で追加設定がゼロになる。** pnpm は corepack のセットアップが必要で、Vercel 側もバージョンが 9 か 10 か確定しない
3. **フェーズ2 の Dev Container 化まで一気に進める工程で、ハマりどころを1つ減らせる。** `node_modules` を named volume に分離する構成と pnpm のシンボリックリンク構造の組み合わせは、動作確認が必要な未知数になる

pnpm を採用する場合は、Corepack + `packageManager` フィールドでバージョンを固定し、Vercel のビルドログで実際に使われた pnpm バージョンを確認すること。

## 懸念

| 懸念 | 深刻度の感触 | 解消に必要な確認 |
|---|---|---|
| pnpm を選んだ場合、Vercel が pnpm 9 と 10 のどちらを使うか lockfile だけでは確定しない | 低(npm 採用なら発生しない) | ビルドログで確認、または Corepack + `packageManager` フィールドで固定する |
| pnpm を選んだ場合、Project Settings の Override で `pnpm install` を指定すると pnpm 6 が使われる | 低(npm 採用なら発生しない) | Override を使わず lockfile 検出に任せる |
| lockfile をコミットし忘れると Vercel が npm にフォールバックする | 低 | `package-lock.json` / `pnpm-lock.yaml` を必ずコミットする(`.gitignore` に入れない) |
