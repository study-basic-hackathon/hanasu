# 検討: Issue の種別と種別ごとの AI 作業フロー

- ステータス: 結論
- 区分: **必須と任意が混在**（種別の定義とフローは**必須** = AI に渡す手順が種別ごとに変わり、決めないと毎回チャットで補足することになる。ラベルの色・名称の細部は**任意**）
- 開始日: 2026-08-08
- 最終更新: 2026-08-08
- 関連: [検討: AI に実装させるためのタスク運用方針](20260808_AI向けタスク運用方針.md)（**本検討の親。粒度・記載項目・未決事項の扱いを決めた**）、[issue-template.md](../template/issue-template.md)

## 背景・きっかけ

[前検討](20260808_AI向けタスク運用方針.md)で Issue の粒度と必須記載項目を決めたが、**すべての Issue を同じ形で書く前提になっている。**

実際には「決める Issue」（#14〜#17）と「実装 Issue」（#2 / #4）では、成果物も検証方法も AI がたどる手順も違う。前検討で #14〜#17 の本文に `> **これは「決める Issue」です。**` というバナーを手で書いたのは、この差を埋めるための場当たり的な対応だった。

種別を定義し、種別ごとに AI の作業フローを決めたい（ユーザーからの相談、2026-08-08）。

## 論点

1. 種別として何を用意するか（いくつに割るか）
2. 種別をどう表現するか（ラベル / タイトル / 本文）
3. 種別ごとの AI 作業フローをどう定義するか
4. フローの定義をどこに置くか

## 選択肢の比較

### 論点1: 種別の設計（案）

| 種別 | 何をするか | 成果物 | 完了条件の形 | 該当する既存 Issue |
|---|---|---|---|---|
| **検討** | 選択肢を比較して選ぶ | 検討記録 + ADR | 決定が記録されている | #15 #16 |
| **仕様** | 決まっていることを書き下す | 仕様ドキュメント | ドキュメントが存在しレビュー済み | #9 #14 #17 |
| **実装** | アプリのコードを書く | コード + PR | 動作が観測できる（画面が出る / API が 200 を返す） | #2 #4 #7 #11 |
| **環境** | 開発環境・インフラを作る | 設定ファイル + PR | 起動する / `terraform plan` が通る | #10 #5 #8 |
| **不具合** | 既存の不具合を直す | 修正 + PR | 再現手順で再現しなくなる | （現状なし） |
| **統括** | 子 Issue を束ねる | なし（**PR を持たない**） | 子がすべて閉じる | #1 |
| **運営** | 非技術タスク | 任意 | 個別 | #6 |

**分けた根拠**

- **検討 / 仕様を分ける** — 手順と成果物が違う。検討は「選択肢の比較 → 決定 → ADR」、仕様は「決まっていることを書き下す → レビュー → **仕様から実装 Issue を起票**」
- **実装 / 環境を分ける** — 検証方法が違う（`lint` / `build` / テスト vs 起動確認・`terraform plan`）。また環境は **CLAUDE.md / README の更新が仕上げに必須**で、共有ファイルを触るためコンフリクトの注意が要る
- **不具合を分ける** — **最初に「再現すること」を確認する手順が要る。** これがないと AI は直したつもりで直っていない PR を出す
- **統括を分ける** — AI が実装を始めてしまわないように、明示的に「PR を持たない」と宣言する必要がある

**絞る場合の案**: 検討 / 実装 / その他 の3種別。ただし「仕様」と「環境」が実装に混ざると、完了条件の書き方（観測可能な形 vs レビュー）が種別内でぶれる。

### 論点2: 種別の表現方法

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A: GitHub ラベル | `種別: 実装` 等のラベルを作る | 一覧でフィルタできる（`gh issue list --label`）。GitHub の標準機能 | **AI が本文だけ読むと種別が分からない**（`--json labels` を明示的に取得する必要がある） |
| B: タイトルにプレフィックス | `[frontend][実装]ログイン画面作成` | 一覧で見える | 既存のタイトル規約（`[<領域>]<要約>`）が冗長になる。既存13件の改名が必要 |
| C: 本文冒頭のバナー | `> **種別: 実装**` を本文1行目に置く | **AI が本文を読むだけで分かる**。既に #14〜#17 で実践済み | 一覧・フィルタで見えない |
| **D: A + C の併用（推奨）** | ラベルで管理し、本文冒頭にも明示する | 人はラベルで絞れ、AI は本文だけで判断できる | 2か所の同期が要る（起票時に両方書く運用） |

### 論点3: 種別ごとの AI 作業フロー（案）

**すべての種別に共通する前後の手続き**

着手前:
1. `gh issue view <N>` で本文を読み、**完了条件を TodoWrite に展開する**
2. **assignee が自分か確認する。** 他人の Issue には着手しない
3. **「前提・依存」の Issue がすべて閉じているか確認する。** 開いていれば着手せず、その旨を報告して止まる
4. **「未決事項（事前決定・必須）」が残っていないか確認する。** 残っていれば着手せず報告する
5. `feature/issue-<N>-<スラッグ>` でブランチを切る

完了時:
1. Issue の完了条件をチェック（`- [x]`）に更新する
2. PR 本文に `Closes #<N>` と**検証結果**（実行したコマンドと結果）を書く

---

**種別: 検討**

1. `CLAUDE.md`・関連 ADR・既存コード・公式ドキュメントに接地する。**事実には出典を付け、推測と区別する**
2. `documents/00_検討/` に検討記録を作成する（`YYYYMMDD_<トピック>.md`）→ `discuss-proposal`
3. 選択肢を比較し、ユーザーと議論して決定する。**AI が単独で決めない**
4. `documents/ADR/` に ADR を作成する（`NNNN-<トピック>.md`、連番）→ `add-adr`
5. **この決定にブロックされていた Issue の本文を更新する**（未決事項を消し、決定内容と ADR リンクを反映）← 忘れやすい
6. ドキュメントのみの PR を出す

**種別: 仕様**

1. 依存する ADR・検討記録を読み、決定済みの方針を確認する
2. 仕様ドキュメントを作成する → `add-specification`
3. ユーザーのレビューを受ける（**コマンドによる検証はできないため、レビューが唯一の検証手段**）
4. **仕様から実装 Issue を起票する** → `decompose-issue` ← 仕様を書いて終わりにしない
5. ドキュメントのみの PR を出す

**種別: 実装**

1. 適用 ADR と、**既存コードの書き方（命名・構成・コメントの粒度）**を読む
2. 実装する。**「やらないこと」に書かれた範囲に手を出さない**
3. Issue の「検証方法」のコマンドを実行する
4. 完了条件を1つずつ確認する。**満たせない条件があれば、隠さず報告する**
5. PR を出す

**種別: 環境**

1. 対応するスキルがあれば使う（Dev Container → `devcontainer-ai-setup`、Terraform → `iac-development` → `iac-security-check`）
2. 実装する
3. 検証する。**「起動して動く」ことの確認が中心**（`docker compose up` → 応答確認、`terraform plan` が通る）
4. **仕上げに CLAUDE.md / README を更新する。** 共有ファイルのためコンフリクトしやすく、**この Issue の最後にまとめて触る**
5. PR を出す

**種別: 不具合**

1. **再現手順どおりに操作し、再現することを先に確認する。** 再現しなければ、そこで止まって報告する ← ここを飛ばさない
2. 原因を特定し、Issue にコメントで残す
3. 修正する
4. **同じ再現手順で再現しなくなったことを確認する**
5. PR を出す

**種別: 統括**

- **実装しない。PR も出さない。** 子 Issue の状態を確認し、次に着手すべき子とブロッカーを報告する
- 子がすべて閉じたら、統括 Issue 自身を閉じる

**種別: 運営**

- AI に渡す前提を置かない。渡す場合は Issue 本文に手順を個別に書く

### 論点4: フローの置き場所

| 案 | 内容 | 備考 |
|---|---|---|
| A: `CLAUDE.md` | AI が毎回読む唯一の場所 | **本来ここが正しいが、前検討でチーム合意待ちとして保留中** |
| B: [issue-template.md](../template/issue-template.md) | 前検討で作成済み。他メンバーの作業を変えない | AI は自動では読まない。Issue 本文かチャットで参照させる必要がある |
| C: 種別ごとにテンプレートを分ける | `documents/template/issue-<種別>.md` | 起票時にフローも一緒にコピーされる。ファイルが増える |

## 懸念

| 懸念 | 深刻度の感触 | 解消に必要な確認 |
|---|:---:|---|
| **種別を増やすと起票時の判断が増え、ハッカソンの速度を落とす** | 中 | 迷ったら「実装」に倒す、等の既定を決めておく |
| **フローをスキル前提で書くと他メンバーが再現できない**（スキルは個人環境） | 中 | フローは道具なしでも追える手順で書き、スキルは「あれば使う」補足に留める |
| ラベルと本文バナーの二重管理（案D） | 低 | 起票時に両方書く運用。ずれても実害は小さい（AI は本文を、人はラベルを見る） |
| ラベル作成は GitHub 全体に影響する共有リソースの変更 | 低 | 追加のみで既存を壊さないが、チームに一声かけるか要確認 |
| **#14 / #17 を「決める Issue」として起票済み**だが、本検討の分類では「仕様」にあたる | 低 | 種別確定後に本文のバナーを修正する |

### 前検討からの変更点

前検討で #14〜#17 に手で書いた `> **これは「決める Issue」です。**` というバナーは、**種別バナーに置き換えた**。「決める Issue」という括りは本検討で **検討（選択肢を比較する）** と **仕様（書き下す）** に分解されたため、役目を終えている。

### 見送った案とその理由

- **7種別（統括・運営を含む）** — 起票時の判断が重くなるため見送り。統括は親トラッキング Issue の本文記述で、運営は種別なしで代替する
- **3種別（検討 / 実装 / その他）** — 「仕様」と「環境」が実装に混ざると、完了条件の書き方（観測可能な形 vs レビュー）が種別内でぶれるため見送り
- **タイトルにプレフィックスを足す**（`[frontend][実装]…`）— 既存タイトル規約が冗長になり、既存13件の改名が必要になるため見送り
- **ラベルのみ / バナーのみ** — 前者は AI が本文だけでは判断できず、後者は一覧で絞り込めないため、併用を選んだ

### 残課題

- **#18 の種別は「検討」としたが、実態は「チームで決定済みの内容を ADR に記録する + 依存 ADR の再検討」** であり、バナーの「選択肢を比較して決め」とは厳密には一致しない。運用上の実害はないが、同種の Issue が増えるようなら「記録」種別の要否を再検討する
- CLAUDE.md への反映（チーム合意待ち。前検討の残論点と同じ）
- ラベル運用を他メンバーに広げるか（チーム合意待ち）
