## 背景・きっかけ

既存の `codex-session-orchestrator` は、Codex プロジェクト内の既存タスクについて、依存順、再開・停止、検証・記録の完了、タスク名の完了表示を管理する。ユーザーから、これに加えて「ブロックが外れた Issue のセッションを始める」「次の優先度のタスクをユーザーに確認する」など、どこまでを役割に含めるべきか検討したいとの相談があった。

本検討では、オーケストレーターを実装担当やプロダクト責任者にせず、複数タスクを安全に前進させるための役割を整理する。

## 論点

### 必須

1. 既存タスクの再開と、新規 Codex タスクの作成をどう区別するか
2. 既存の優先度に従う進行判断と、新たな優先度を決める価値判断をどう区別するか
3. Issue、Codex タスク、ブランチ、PR の状態不一致をどこまで整合させるか
4. オーケストレーターが自動で行える操作と、ユーザー確認を要する操作の境界をどこに置くか

### 任意

5. Ready なタスクが複数ある場合の既定の並べ方を持つか
6. 停滞、CI 完了、レビュー要求、依存解除など、どのイベントを再開契機として監視するか
7. 進捗報告をどの粒度・頻度・形式で行うか
8. 完了後に振り返り記録の候補を提示するか
9. プロジェクトリスクとして提示する対象と、通知する閾値をどう定めるか
10. PMBOK の原則・パフォーマンスドメイン・プロセス群を、どの粒度で進め方へ取り入れるか
11. GitHub Projects の看板、Issue、Codex タスク、PR の間で、どれを各状態の正本とするか（初版の直接連携は見送り）
12. 期限・見積り・基準日程の策定と、既存スケジュールの監視を同じセッションへ持たせるか

## 事実確認（出典付き）

- 現行スキルは、依存タスクを先に解消し、タスク完了または判断要求を契機に次の依存タスクを再開する役割をすでに持つ（出典: `/Users/moritayutaro/.codex/skills/codex-session-orchestrator/SKILL.md`「進行管理」）。
- 現行スキルは、新しい Codex タスクを作るのはユーザーが明示的に依頼した場合だけとし、通常は既存タスクへ続行メッセージを送る（同「この運用の不変条件」）。
- 現行スキルは、依存順、実行順、並行可否、再開・停止、確認の優先順位を運営判断として認める一方、技術的トレードオフの受容はユーザー判断としている（同「技術判断と進行判断の境界」）。
- 現行スキルは、実装タスクのテスト証拠、検討タスクの検討記録、PR の状態、未解決レビュー、残リスクを完了ゲートとして確認する（同「タスク種別ごとの完了ゲート」「PR と完了の確認」）。
- このリポジトリでは、進捗・ステータス・優先度の正本は GitHub Issue と定めている（出典: [ドキュメントの書き方](../README.md)「情報の種類ごとの正本」）。
- このリポジトリの Issue 作業フローは、着手前に assignee、依存 Issue の完了、必須の未決事項を確認する（出典: [Issue の種別と種別ごとの AI 作業フロー](20260808_Issue種別とAI作業フロー.md)「種別ごとの AI 作業フロー」）。
- OpenAI の公開ユースケースには、反復作業をスキルとして保存することや、長期目標を追跡するワークフローが示されている。ただし、公開ページから Codex アプリ内の個別タスク作成・再開に関する詳細な承認規則までは確認できなかった（出典: [OpenAI のユースケース](https://learn.chatgpt.com/use-cases)）。
- 2025 年 11 月公開の PMBOK Guide 第8版は、6つの中核原則と、ガバナンス、スコープ、スケジュール、財務、ステークホルダー、資源、リスクの7パフォーマンスドメインを持つ。特定方式を一律適用するのではなく、プロジェクトの文脈に合わせたテーラリングを重視している（出典: [PMBOK Guide](https://www.pmi.org/standards/pmbok)）。
- PMI のリスク管理ガイドは、目標へ正または負の影響を与える不確実な事象・状態を扱い、機会の獲得と脅威の抑制を事前に計画する考え方を示している（出典: [Risk Management in Portfolios, Programs, and Projects](https://www.pmi.org/standards/risk-management)）。
- PMI の Process Groups: A Practice Guide は、予測型アプローチ向けの補助ガイドとして、立上げ、計画、実行、監視・コントロール、終結の5プロセス群を示す。Codex タスクへ適用する場合は予測型開発を強制せず、オーケストレーション1回の反復サイクルとしてテーラリングする必要がある（出典: PMI [Process Groups: A Practice Guide](https://www.pmi.org/standards/process-groups) の公式製品説明）。
- ユーザーによると、このプロジェクトでは GitHub Projects と看板ボードをすでに使用している。ただし、2026-08-22 の確認時点ではローカル GitHub CLI の認証情報が失効しており、Project の所有者、番号、実際の Status 選択肢、カスタムフィールド、組み込みワークフローは未確認である（出典: 2026-08-22 のユーザー発言、`gh auth status`）。
- GitHub Projects は Issue と PR を表・看板・ロードマップで管理でき、Status、Priority、日付、Iteration、見積りなどのフィールド、組み込みワークフロー、Project 全体の `On track` や `At risk` などのステータス更新を持てる（出典: [About Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects)、[Understanding fields](https://docs.github.com/en/issues/planning-and-tracking-with-projects/understanding-fields)）。
- GitHub Issue は `blocked by` と `blocking` の依存関係を持てる。ブロック中の Issue は Project の看板上にも表示され、GitHub CLI では依存関係を読み取れる（出典: [Creating issue dependencies](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-issue-dependencies)）。
- GitHub Projects には、Issue や PR の close・merge を契機に Status を `Done` へ変更する組み込みワークフローがある。現行 Project の有効なワークフローを確認せずに、オーケストレーターが同じ更新を重複実行すべきではない（出典: [Using the built-in automations](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-built-in-automations)）。

## PMBOK を参考にした構成案

PMBOK をスキルへ取り入れる目的は、管理文書を増やすことではなく、オーケストレーターが横断的に確認すべき観点を漏らさないことである。PMBOK の全プロセスや成果物を再現せず、パフォーマンスドメインを確認観点、プロセス群を実行サイクルとして使う案を推奨する。

### パフォーマンスドメインとの対応

| PMBOK 第8版の領域 | セッションオーケストレーターでの扱い | 責務境界 |
|---|---|---|
| ガバナンス | 正本、承認権限、停止条件、PR・deploy などの権限境界を確認する | 未承認操作や技術決定を代行しない |
| スコープ | Issue の目的、完了条件、対象外、変更範囲を確認する | スコープを新設・拡大・縮小しない |
| スケジュール | 依存関係、Ready キュー、クリティカルパス、期限、再開順を管理する | 事業優先度がなければユーザーへ確認する |
| 財務 | 明示された予算、実行時間、利用上限がある場合だけ逸脱を検知する | 金額を推測せず、費用対効果を代理判断しない |
| ステークホルダー | 判断者、担当者、レビュー先、外部依存を特定し、質問と報告をルーティングする | 元タスクの技術判断へ代理回答しない |
| 資源 | Codex の実行枠、worktree、checkout、共有ファイル、レビュー容量、WIP を管理する | 担当変更や追加コストを勝手に決めない |
| リスク | リスクの兆候、影響、所有者候補、トリガー、残存リスクを継続監視する | リスク受容と技術的対策はユーザーまたは元タスクへ返す |

### 原則から取り入れる振る舞い

- **全体を見る**: 個別タスクだけでなく、Issue、依存、PR、仕様、ADR、実行枠を一つの系として扱う
- **価値へ整合する**: 明示済みの目的と優先度に従い、価値判断が欠けていればユーザーへ確認する
- **品質を工程へ埋め込む**: 最後の報告だけで品質確認せず、再開時と完了時にゲートを適用する
- **説明責任を持つ**: 再開、停止、直列化、差し戻しの理由と証拠を残す
- **チームへ判断を残す**: 各タスクが持つ技術判断と担当範囲を尊重し、オーケストレーターへ集中させない
- **テーラリングする**: 小規模プロジェクトでは必要最小限の状態と報告に絞り、不要な台帳や定例を作らない

### 5段階の反復サイクル

| 段階 | オーケストレーターが行うこと | 主な出力 |
|---|---|---|
| 1. 立上げ | 対象プロジェクト、今回の目的、対象タスク、承認範囲、正本を確定する | 対象範囲と権限境界 |
| 2. 計画 | 状態棚卸し、依存関係、Ready キュー、並行可否、完了ゲート、リスク閾値を整理する | 実行順、停止条件、監視対象 |
| 3. 実行 | 既存タスクを再開し、明示許可された場合だけ新規タスクを開始する | 再開・開始メッセージ |
| 4. 監視・コントロール | 状態変化を待ち、進捗差異、競合、判断待ち、リスクトリガーを確認し、必要なら再計画する | 差し戻し、再順序付け、判断要求、リスク報告 |
| 5. 終結 | 完了ゲート、成果物、検証、PR、残存リスク、引き継ぎを確認し、完了表示を整える | 完了報告、残課題、次の Ready 候補 |

このサイクルはプロジェクト全体で一度だけ行う段階ではなく、オーケストレーションの起動、依存解除、ユーザー回答、PR 状態変更などのイベントごとに必要な段階へ戻る反復ループとする。

## GitHub Projects の看板との直接連携案（初版は見送り）

2026-08-22 第5ラウンドで、GitHub Projects まで直接連携すると初版の制約と責務が増えすぎるため、いったん対象外とすることをユーザーが決定した。以下は検討履歴として残し、初版の責務・完了条件には含めない。

オーケストレーター内部に恒久的な Ready キューや優先度台帳を新設せず、GitHub Projects の看板を計画と進捗の正本として読み取る。Codex タスクの状態は、看板を置き換える正本ではなく、実際にエージェントが動いているかを示す実行時テレメトリとして扱う。

### 情報ごとの正本

| 情報 | 正本 | オーケストレーターの使い方 |
|---|---|---|
| プロジェクト内の状態、優先度、Iteration、期限 | GitHub Projects | Ready 候補、実行順、期限リスクを判断する |
| 目的、完了条件、対象外、担当、依存関係 | GitHub Issue | 着手可否、スコープ、`blocked by` / `blocking` を判断する |
| 現在実行中か、質問待ちか、idle か | Codex タスク | 看板と実行実態の差異を検知する |
| 変更内容、検証、レビュー、CI、merge | PR と CI | 完了ゲートと品質リスクを判断する |
| 技術決定と仕様 | ADR と仕様ドキュメント | タスクが既決事項へ従っているか確認する |

### 看板からセッションへ反映する流れ

1. Project の対象ビューとフィールド定義を取得する。
2. 各 Project item をリポジトリの Issue または PR と対応づけ、Draft item は実行対象から分ける。
3. Status、Priority、Iteration、期限、assignee、Issue 依存関係から Ready 候補を作る。
4. 対応する既存 Codex タスク、branch、PR を照合する。
5. `ブロックなし`、`着手可能な Status`、`必須未決事項なし`、`担当・権限が整合` を満たすものだけを Ready と判定する。
6. 既存 Codex タスクは再開し、新規タスクはユーザーが明示した範囲だけ作る。
7. 実行中は看板、Codex タスク、PR の差異を監視し、状態変化時に再計画する。

Project 固有の Status 名は `Todo`、`Ready`、`In Progress` などへ決め打ちせず、実際の選択肢と運用説明を読んで、`未着手`、`着手可能`、`作業中`、`レビュー待ち`、`完了` の意味へマッピングする。

### 状態不一致をリスクとして扱う例

| Project / Issue | Codex / PR の実態 | 扱い |
|---|---|---|
| 着手可能、ブロックなし | 対応タスクなし | 次の開始候補。新規作成は許可条件を確認する |
| 作業中 | 対応タスクなし、branch・PR もなし | 状態陳腐化または担当不明のリスク |
| 未着手 | Codex タスクが実装中 | 看板と実行状態の不整合。Status 更新候補 |
| ブロック中 | Codex タスクが実装中 | 誤着手または依存情報陳腐化のリスク。停止して確認する |
| 完了 | Issue が open、PR 未merge、完了ゲート不足 | 早すぎる完了状態のリスク |
| レビュー待ち | PR なし | 成果物不足または看板更新誤りのリスク |

### Project への書き込み権限の段階案

| 段階 | 自動で行うこと | ユーザー確認が必要なこと |
|---|---|---|
| A: 読み取り専用 | 状態、優先度、依存、リスクの報告 | すべての Project 更新 |
| B: 運用状態だけ同期（推奨候補） | 実際の開始・レビュー待ち・完了に対応する Status 更新。ただし既存 workflow と競合しない場合だけ | Priority、Iteration、期限、担当、Project 全体の status 更新 |
| C: Project 管理も代行 | 明示された運用ルールに沿うフィールド更新 | 優先度や期限など価値判断を伴う変更 |

見送り前の案では B を推奨候補としていた。ただし初版では A〜C のいずれも実装せず、GitHub Projects の読み取り・書き込みをオーケストレーターの必須動作にしない。将来再検討する場合は、実際のフィールド、Status の意味、組み込み workflow を確認してから再開する。

## スケジュール策定とオーケストレーションの境界案

期限・スケジュールには、基準を作る「計画」と、基準との差異を扱う「監視・コントロール」がある。初版では両者を分け、オーケストレーターは既決の期限・依存順を使った進行管理と差異検知を担当し、見積り、期限設定、基準日程の作成・変更は別の計画セッションへ委ねる案を推奨する。

### 責務分担

| 判断・作業 | セッションオーケストレーター | 別の計画・スケジュールセッション | ユーザー |
|---|---|---|---|
| 既存 Issue の期限・マイルストーン・依存順を読む | 担当 | 参照 | — |
| 依存順と実行枠に基づき、現在の再開順を決める | 担当 | — | 価値判断が必要なら回答 |
| 現在状態と期限を比較し、遅延・余裕消失を検知する | 担当 | 必要に応じて分析 | リスク受容を判断 |
| Issue の作業量・所要時間を見積もる | 観測事実を引き渡す | 担当 | 前提と期待精度を確認 |
| 期限、マイルストーン、バッファ、基準日程を作る | 作らない | 担当 | コミット可能な期限を決定 |
| スコープ・期限・資源のトレードオフを選ぶ | 選ばない | 選択肢と影響を整理 | 決定 |
| 遅延時に基準日程を引き直す | 必要性と影響タスクを提示 | 担当 | 再ベースラインを承認 |
| 確定した新日程に従ってタスクを再順序付けする | 担当 | 計画結果を引き渡す | — |

### オーケストレーターが期限について行ってよいこと

- 期限が近い、期限超過、依存先の遅延で後続期限が危うい、という観測可能な事実を提示する
- 既決の優先度、期限、依存関係の範囲で実行順を調整する
- 現在の進捗から、予定どおり完了できない可能性をリスクとして提示する
- 見積りまたは期限が存在しないためスケジュール評価不能であることを提示する
- 再計画が必要な場合、影響する Issue、完了済み作業、残作業、依存、判明した実績を計画セッションへ引き渡す

### オーケストレーターが行わないこと

- 根拠なく各 Issue の所要時間や完了日を推測する
- ユーザーとの合意なしに期限、マイルストーン、バッファを設定・変更する
- 遅延を隠すために基準日程を自動で後ろ倒しする
- 納期を守るためのスコープ削減、品質基準変更、増員を代理決定する

### 別セッションへ切り出す条件

次のいずれかが起きた場合、オーケストレーターは自分で計画を作らず、プロジェクト単位の計画・スケジュールセッションを新規作成する候補、または既存セッションの再開候補としてユーザーへ提示する。

- プロジェクトまたは主要 Issue 群に期限・マイルストーンが必要だが未設定
- 依存関係やスコープ変更によって既存日程が成立しなくなった
- 期限、スコープ、品質、利用可能な担当・実行枠のトレードオフが必要
- 複数の妥当な日程案からユーザーが選ぶ必要がある
- 遅延リスクの提示だけでは次の実行順を確定できない

計画セッションは Issue ごとに乱立させず、原則として一つのプロジェクトに一つの継続タスクとする。オーケストレーターは、計画セッションの作成を暗黙に行わず、ユーザーが明示的に依頼した場合だけ作成または再開する。確定後は、計画セッションが期限・前提・判断理由を既存の正本へ反映し、オーケストレーターはその結果だけを消費する。

## 役割候補

### 1. 状態の観測と正規化

- 同一リポジトリに属する Issue、Codex タスク、ブランチ、PR を対応づける
- タスクを `実行中`、`Ready`、`依存待ち`、`ユーザー判断待ち`、`PR 待ち`、`完了候補` に分類する
- `idle`、Codex タスク名、Issue の open/closed、PR 状態のいずれか一つだけで完了判定しない
- 状態不一致を検出する。例: Issue は open だが PR は merge 済み、タスクは idle だが判断質問が残る、同じ Issue に複数 PR がある

### 2. 依存解除と Ready キューの管理

- 依存先の完了を検知し、後続タスクを `依存待ち` から `Ready` へ移す
- 対応する既存 Codex タスクがあれば、確定済みの前提と完了条件を添えて再開する
- 対応する Codex タスクがなければ、新規作成候補としてユーザーへまとめて提示する
- ユーザーが今回の依頼で「Ready になった Issue の新規タスクも開始する」と明示した場合に限り、対象を再確認して新規作成する案を検討する

### 3. 実行枠と衝突の管理

- 独立 worktree または読み取り専用タスクだけを並行化する
- 同一 checkout、同一 Issue、同一 PR、共有ファイル、ADR 番号などの競合を検知して直列化する
- 実行枠が空いたら Ready キューから次を進める
- 長時間実行中のタスクを、単に時間が経過したことだけで停止・失敗扱いにしない

### 4. 優先順位の適用と判断のエスカレーション

- GitHub Issue の明示済み優先度、マイルストーン、期限、依存順など、正本に存在する順序はそのまま適用する
- 同順位なら、あらかじめユーザーが採用したタイブレーク規則がある場合だけ自動選択する
- 優先度が未設定、または事業価値・納期・リスク受容で順序が変わる場合は、候補、選択肢ごとの影響、推奨の有無をまとめてユーザーへ確認する
- オーケストレーター自身が Issue の事業優先度を新設・変更しない

タイブレーク規則の候補:

| 規則 | 利点 | 懸念 |
|---|---|---|
| クリティカルパス優先 | 後続を最も多く解放しやすい | 依存グラフが正確である必要がある |
| 期限が近い順 | 納期へ直結する | 期限未設定の Issue を扱いにくい |
| 短時間で終わる順 | 実行枠の回転が速い | 見積もりが不正確になりやすい |
| 古い Ready から順 | 公平で説明しやすい | 価値や緊急度を反映しない |
| 毎回ユーザー確認 | 価値判断を委ねられる | オーケストレーションが頻繁に止まる |

### 5. 停滞の検知と安全な復旧

- 空応答、失敗終了、長時間の idle、実行状態と成果物の不一致を検出する
- ブランチ、差分、コミット、テスト、PR を読み取り確認し、同じタスクを安全に再開できるか判断する
- 同じ失敗を無条件に繰り返さず、環境・権限・未決事項・競合のどれが原因か分類する
- 実装をオーケストレーター自身へ引き取らず、元タスクへ不足情報を添えて返す

### 6. 完了ゲートと状態整合

- Issue 種別ごとの完了条件を確認する
- テスト、lint、build、validate、plan、ドキュメント記録など、必要な証拠を確認する
- PR の重複、CI、レビュー、マージ可能性、残リスクを確認する
- 実質完了した Codex タスク名を `済：` に更新する
- GitHub Issue のクローズや PR マージは別の権限境界として扱い、自動実行しない

### 7. 判断要求の集約とルーティング

- 各タスクに散らばったユーザー判断待ちを、重複排除して一覧化する
- 質問ごとに、対象タスク、止まっている論点、選択肢、影響、回答後に再開するタスクを示す
- 技術判断は元タスクで回答してもらい、オーケストレーターが代理回答しない
- 複数タスクに共通する一つの判断であれば、影響範囲を示して一度だけ確認する

### 8. 変更検知と再計画

- Issue の優先度、依存、スコープ、担当、ADR・仕様が変わったら Ready キューと実行順を再計算する
- 進行中タスクが新しい正本と矛盾した場合は停止し、既決事項へ整合させる
- 廃止、重複、スコープ変更になったタスクを惰性で再開しない

### 9. 進捗と引き継ぎの報告

- `完了`、`実行中`、`ユーザー判断待ち`、`PR 待ち`、`次に開始可能` に分けて報告する
- 実行ログではなく、到達点、検証証拠、ブロッカー、次の再開条件を示す
- 中断しても、次回のオーケストレーションが状態を復元できる最小情報を残す
- オーケストレーション自体の反復的な失敗や成功パターンがあれば、完了後の振り返り候補として提示する。ただし振り返りの保存・反映は専用スキルへ委ねる

### 10. プロジェクトリスクの検知と提示

オーケストレーターは、複数タスクを横断して初めて見えるリスクをユーザーへ提示する。ただし、技術的な重大度、発生確率、リスク受容、対策方式を根拠なく決めない。

検知対象の候補:

| 分類 | 観測可能な兆候 | 想定される影響 |
|---|---|---|
| 納期・進行 | クリティカルパス上の依存待ち、Ready タスクがない、期限直前の未着手 | 後続タスク全体の遅延 |
| 判断待ち | 同じ未決事項で複数タスクが停止、回答期限が近い | 複数の実行枠が同時に遊休する |
| 実行容量 | WIP 過多、実行枠不足、レビュー待ちの滞留 | 着手済み作業が完了せずリードタイムが伸びる |
| 競合・重複 | 同一 Issue、PR、ファイル、ADR 番号を複数タスクが変更 | コンフリクト、二重実装、記録不整合 |
| 品質 | 必須テスト未実行、CI 失敗、検証証拠不足、レビュー未解決 | 不具合を含む完了扱いや手戻り |
| スコープ | Issue の完了条件外の変更、受け入れ条件不足、依存関係の記載漏れ | 過剰実装、完了判定不能、後続の前提崩れ |
| 正本不整合 | Issue、仕様、ADR、実装、PR の内容が矛盾 | 誤った前提による実装継続 |
| 外部依存 | 権限、認証情報、外部サービス、他担当者の回答待ち | オーケストレーターだけでは解除できない停止 |

提示形式の候補:

- **兆候**: 実際に確認できた状態と出典
- **影響範囲**: 影響する Issue、Codex タスク、PR、後続タスク
- **放置時の影響**: 何が止まる、遅れる、衝突する可能性があるか
- **確度**: 確認済み事実か、事実からの推測か
- **必要な対応**: オーケストレーターが行える進行対応と、ユーザー判断が必要な対応を分ける
- **再確認条件**: 依存完了、CI 更新、期限到来など、次に見直す契機

通知レベルの候補:

| レベル | 条件 | 扱い |
|---|---|---|
| 要判断 | ユーザー判断なしでは複数タスクまたはクリティカルパスが止まる | 即時にまとめて提示し、判断を待つ |
| 要対応 | 衝突、CI 失敗、正本不整合など、既決事項に基づく対応が必要 | 対応可能なら元タスクへ差し戻し、結果を報告する |
| 監視 | まだ停止していないが、期限・滞留・外部依存に悪化の兆候がある | 状態変化時または定期報告時だけ提示する |

数値による発生確率や重大度スコアは、プロジェクトで定義済みの基準がある場合だけ使う。基準がない場合は、観測事実、影響範囲、停止条件を示し、「高・中・低」をオーケストレーターの主観で付けない案を推奨する。

## 自動化レベルの選択肢

| 観点 | A案: 報告専用 | B案: 既存タスクは自動再開 | C案: 明示された範囲で新規タスクも開始 |
|---|---|---|---|
| 棚卸し・分類 | 行う | 行う | 行う |
| 既存タスクの再開 | 候補を報告 | 自動 | 自動 |
| 新規 Codex タスク作成 | 行わない | ユーザーへ確認 | 起動時に明示された対象だけ行う |
| 優先度未設定時 | 毎回確認 | 毎回確認または既定規則 | 毎回確認または既定規則 |
| 自律性 | 低 | 中 | 高 |
| 誤着手時の影響 | 小 | 中 | 大 |

現時点の推奨は **B案を既定にし、ユーザーが起動時に範囲を明示した回だけ C案に拡張する**こと。既存タスクの再開は現行責務と整合する一方、新規タスク作成はユーザーが所有するタスク一覧を増やすため、一般的な「オーケストレーション依頼」から暗黙に許可されたとは扱わない。

## 懸念

| 懸念 | 深刻度の感触 | 解消に必要な確認 |
|---|:---:|---|
| オーケストレーターがプロダクトマネージャー化し、優先度やスコープを勝手に決める | 高 | 「既存優先度の適用」と「新規優先度の決定」を明確に分ける |
| 新規タスクを自動作成し、ユーザーのサイドバーや実行枠を意図せず増やす | 高 | 起動時の明示許可を必須にし、対象 Issue を確定してから作る |
| Issue、Codex タスク、PR の対応づけを誤る | 高 | Issue 番号、リポジトリ、worktree、branch、PR head を複数条件で照合する |
| 状態監視が過剰になり、頻繁な読み取りや通知が発生する | 中 | イベント単位のまとまった待機と、状態変化時だけの報告にする |
| リスク候補を毎回すべて報告してアラート疲れを起こす | 中 | 要判断・要対応・監視に分け、状態変化または閾値到達時だけ通知する |
| 根拠のない確率・重大度を付け、ユーザー判断を誘導する | 高 | 観測事実、影響範囲、確度を分け、未定義の数値評価を行わない |
| PMBOK の全プロセスや成果物を移植し、小規模開発に過剰な管理負荷を加える | 中 | 7領域を確認観点、5段階を内部サイクルとして使い、追加台帳は必要性が確認された場合だけ作る |
| PMBOK を根拠に、既存の Issue・ADR・仕様運用と重複する正本を作る | 高 | 既存の正本を参照し、オーケストレーター専用の恒久台帳を原則作らない |
| GitHub Projects とオーケストレーター内部の Ready キューが二重管理になる | 高 | Project を正本とし、内部状態は1回の実行中だけ保持する |
| Project の組み込み workflow と Status 更新が競合する | 中 | workflow を先に確認し、同じ遷移は Project 側へ任せる |
| Project の Status 名だけを見て意味を誤解する | 高 | フィールド定義と運用説明を読み、Issue・PR・Codex の実態で検証する |
| オーケストレーターが日程を作り、同時に自分で進捗評価・再ベースラインまで行う | 高 | 計画策定と実行監視を別セッションへ分け、確定した基準だけを消費する |
| Issue ごとに計画セッションを作って管理対象が増える | 中 | 原則としてプロジェクト単位で一つの継続タスクに集約する |
| 期限がないタスクをすべて問題扱いして通知が増える | 中 | 期限が必要と決まっている範囲だけ評価し、未設定を自動的な異常としない |
| 完了判定と GitHub Issue の close が混同される | 中 | Codex タスクの完了表示と Issue/PR のライフサイクルを別状態として持つ |
| オーケストレーターが不足作業を実装して責務を越える | 中 | 差し戻しと再開指示に限定し、実装は元タスクへ返す |

## 結論

`codex-session-orchestrator` は、既存 Codex タスクの進行、依存解除、再開・停止、並行実行、完了ゲート、横断リスク、既決期限との差異を管理する。PMBOK を参考にした `立上げ → 計画 → 実行 → 監視・コントロール → 終結` を状態変化ごとに反復する。

新規 Codex タスクはユーザーの明示依頼がある場合だけ作る。GitHub Projects の直接連携は初版で見送る。リスク受容、技術的対策、優先度・期限・スコープ・品質・資源のトレードオフはユーザーまたは元タスクへ残す。

期限は既決事項の監視と差異検知だけを担当する。見積り、期限設定、基準日程作成、再ベースラインは、必要になった時点でプロジェクト単位の別の計画・スケジュールセッションへ分ける。今回の決定はユーザー用スキルへ反映・検証済みであり、プロダクト仕様やアーキテクチャの変更ではないため ADR・仕様書への昇格は行わない。
