## 背景・きっかけ

ユーザーからの相談（2026-08-17）。

> 仕様ドキュメントの中に「何日に決定した」という決定ログが残っていたり、「残っている懸念点はここで、これはこっちの Issue が担当する」といった仕様とは直接関係のない情報が、いろいろなところに分散して置かれている。

目指す状態は次の2点。

1. **正本（正しい情報）が1箇所にだけある**
2. **各ドキュメントが自分の役割だけを果たしている** — 仕様ドキュメントからは検討結果・決定ログをできる限り減らし、読みやすくする

決定ログそのものを消したいわけではない。**ログファイル・ADR・検討記録に置くのは適切**であり、問題は「最終的な仕様ドキュメントの中に残っていること」である。

## 論点

1. ドキュメント種別ごとの役割定義（何を書く場所で、何を書かない場所か）と、その定義自体をどこに書くか
2. 情報の種類ごとの正本の所在（仕様 / 決定 / 経緯 / 未確定・懸念 / 進捗 / 作業ログ / 変更履歴）
3. 仕様ドキュメントに「書かないこと」の線引き
4. ディレクトリ構成と命名規則
5. ドキュメント冒頭のメタ情報をどこまで持つか
6. 結論の出た検討記録の扱い（**仕様の正本が検討記録側にある状態**の解消を含む）

## 選択肢の比較

### 論点2: 情報の種類ごとの正本の所在（**本検討の中心**）

まず「どの情報がどこにあるべきか」を1枚の表として定める。これが決まれば論点3以降は適用の問題になる。

**案（推奨）**

| 情報の種類 | 正本 | 他の場所での扱い |
|---|---|---|
| **決まっている仕様**（何を作るか、どう振る舞うか） | **仕様ドキュメント**（`documents/` 配下） | 他文書は参照リンクのみ。値を書き写さない |
| **アーキテクチャ上の決定と、その理由・トレードオフ** | **ADR**（`documents/ADR/`） | 仕様書には**決定の結果**だけを書き、理由は書かない（ADR へリンク） |
| **決定に至る経緯・案の比較・議論** | **検討記録**（`documents/00_検討/`） | 仕様書・ADR からリンクのみ |
| **決定の日付・決定の場**（チーム会議など） | **ADR**（`- 日付:` フィールド） | 仕様書に書かない |
| **未確定事項・懸念・宿題** | **GitHub Issue** | 仕様書は「未確定である事実 + Issue リンク」だけ。理由・選択肢は Issue が持つ |
| **進捗・ステータス・優先度** | **GitHub Issue**（open/closed・ラベル・アサイン） | ドキュメントに書かない |
| **作業ログ・実測結果** | **PR 本文**（凍結済み task-memo は記録として保存） | — |
| **変更履歴** | **git** | ドキュメント内に「新旧対応表」「変更点」節を持たない |

**この表で揉めうる点 = 未確定事項をドキュメントにどこまで残すか**

| 観点 | A案: 完全に Issue へ | **B案: 事実 + リンクだけ残す（推奨）** | C案: 現状維持（章として表を持つ） |
|---|---|---|---|
| 書き方 | ドキュメントには一切書かない | 該当箇所に「**未確定（[#NN](...)）**」と1行だけ添える | 章末に「未確定事項」表（理由・決めるべき場所つき） |
| 読み手の誤読 | **確定事項と誤読する危険がある** | 防げる | 防げる |
| 腐りやすさ | 腐らない | Issue が閉じたら注記を消す必要がある | **表全体が腐る。** 決着後も残り続ける |
| 二重管理 | なし | ほぼなし（リンクのみ） | **あり。** 理由・選択肢が Issue と重複 |
| 移行コスト | 低 | 中 | ゼロ |

推奨は B案（「未確定である」ことは読み手にとって仕様の一部だが、なぜ未確定か・どんな選択肢があるかは Issue の領分）だったが、**決定は C案**。

> **決定（2026-08-17、ユーザー判断）: C案 — 未確定事項は章として一覧表を持つ。**
>
> ドキュメント単体で「何が未確定か」を通読できる形を保つ。**ただし本検討の出発点は「懸念が分散していること」であるため、次の2つを条件として付ける。**
>
> 1. **表の正本は GitHub Issue。** 表は Issue の内容を要約したものであり、**詳細な選択肢・比較・推奨案は Issue 側に書く**（表に書き足さない）
> 2. **決着したら表から消す。** 「解決済みの論点」として残さない（論点3の決定により、決着済みの経緯は仕様書に書かない）。削除漏れを防ぐため、[issue-template.md](../template/issue-template.md) の「種別: 検討」フロー5番（*この決定にブロックされていた Issue の本文を更新する*）を**文書にも拡張する**

### 論点3: 仕様ドキュメントに「書かないこと」の線引き

| 観点 | A案: 完全排除 | **B案: 結果は書く / 過程・時点・担当は書かない（推奨）** | C案: 末尾に「決定の経緯」節としてまとめる |
|---|---|---|---|
| 判断基準 | 決定に由来する記述をすべて排除 | **「この文書が定義する対象の性質」なら書く。「いつ・誰が・どの順で作業するか」なら書かない** | 場所を移すだけで内容は残す |
| 例:「練習モードは画面モックのみ作る」 | 書けない（実装範囲は決定事項のため） | **書く**（対象の性質 = スコープ） | 書く |
| 例:「2026-08-16 のチーム会議で決定した」 | 書かない | **書かない**（→ ADR の日付） | 末尾に書く |
| 例:「当初は将来対応としていたが今回作る」 | 書かない | **書かない**（→ git と ADR） | 末尾に書く |
| 例:「最優先で作り上げる」 | 書かない | **書かない**（→ Issue の優先度） | 末尾に書く |
| 例:「プロフィールを分けない理由」 | 書かない | **書かない**（→ ADR の「理由」節） | 末尾に書く |
| 読みやすさ | 最も読みやすいが、スコープが読めなくなる | 読みやすい | **本文は減らない**（同じ文書の中に残る） |

A案はスコープ（作る / 作らない）まで落ちてしまう。C案は移動が楽だが「仕様書を読みやすくする」という目的を達成しない。

> **決定（2026-08-17）: B案 — 決定の結果は書き、過程・時点・担当は書かない。**
>
> **判断基準**: *その記述を消したとき、**作るものが分からなくなるなら仕様**。**作業の進め方が分からなくなるだけなら仕様ではない**。*
>
> この基準により仕様ドキュメントから外れるもの: 決定の日付と場 / 変更の経緯（「当初は〜だった」）/ 選定理由と却下案 / 実装の優先度・進捗 / 解決済みの論点。
> 残るもの: 実装範囲（作る / 作らない / モックのみ）、仕様そのもの、用語定義。

### 論点1: 役割定義をどこに書くか

| 観点 | A案: issue-template.md に追記 | **B案: `documents/README.md` を新設（推奨）** | C案: CLAUDE.md に全部書く |
|---|---|---|---|
| 人が辿れるか | Issue の話を読みに行く必要がある | **`documents/` を開くと最初に見える** | リポジトリ入口にある |
| AI が読むか | 読まない（Issue 作業時のみ） | **CLAUDE.md から1行リンクすれば読む** | **必ず読む** |
| CLAUDE.md の肥大 | しない | しない | **する。** 現在も技術スタックの重複で問題化（#41） |
| 共有ファイルの衝突 | 中 | **低**（新規ファイル） | **高。** [20260808 検討](20260808_AI向けタスク運用方針.md) 論点4で「共有ファイルは仕上げでのみ触る」と決めている |

> **決定（2026-08-17）: B案 — `documents/README.md` を新設する。**
>
> CLAUDE.md には「**ドキュメントを追加・更新するときは `documents/README.md` に従う**」の1行だけを置き、役割定義・正本表の実体は `documents/README.md` が持つ（**このファイルは是正計画の Issue A で作成する。現時点では未作成**）。
>
> **適用範囲はチーム全体**（2026-08-17 ユーザー判断）。ドキュメントは共有物であり、一部のメンバーだけがルールを守っても正本の割れは防げないため。[20260808 の検討](20260808_AI向けタスク運用方針.md)が「まず自分の作業だけ」としたのとは異なる判断であり、**チームへの周知が必要**（→「チームメンバーと詰めるべき事項」）。

### 論点4: ディレクトリ構成と命名規則

**構成**

| 観点 | **A案: 領域別を正式化（推奨）** | B案: 仕様を `documents/spec/` に集約 | C案: 現状維持 |
|---|---|---|---|
| 配置 | 全体共通の仕様は `documents/` 直下、領域固有は `documents/<領域>/` | 直下は README のみ。仕様は `spec/` 配下へ | ルールなし |
| PR #31/#32 との整合 | **そのまま受け入れられる** | 追加される3件を移動する必要がある | — |
| リンク切れリスク | 低（既存ファイルを動かさない） | **中〜高**（既存3件 + 参照元すべて） | なし |
| 分かりやすさ | 直下に全体仕様と領域ディレクトリが混在する | 揃う | 低い |

> **決定（2026-08-17）: A案 — 領域別ディレクトリを正式化する。**
>
> 全体共通の仕様は `documents/` 直下、領域固有の仕様は `documents/<領域>/` に置く。PR [#31](https://github.com/study-basic-hackathon/hanasu/pull/31) / [#32](https://github.com/study-basic-hackathon/hanasu/pull/32) が追加する `documents/frontend/01_design/` をそのまま受け入れ、**既存ファイルは動かさない**（リンク切れを避ける）。

**`01_design` / `02_spec` の番号プレフィックスについては、両者の違いが未定義**（CLAUDE.md には両方の記載があるが、実体は `01_design` のみ）。**設計（どう見せるか・どう作るか）と仕様（何を満たすか）の線引きを決めるか、片方に統一するか**を論点として残す。

**命名**

- **ファイル名にスペースを使わない** — `必要api .md` を改名する（例: `API一覧.md`）。参照している箇所を同時に更新する
- **日本語ファイル名は許容する** — ADR・検討記録・仕様すべてが日本語で、変更コストが利得を上回る。ただし Issue 本文からリンクする際は URL エンコードが必要（[issue-template.md](../template/issue-template.md) に記載済み）
- ADR は `NNNN-<トピック>.md`、検討記録は `YYYYMMDD_<トピック>.md`（現行どおり）

### 論点5: ドキュメント冒頭のメタ情報

現状の項目は `ステータス / 対象 / 作成日 / 最終更新 / 対応 Issue / 関連`（ユースケースのみ）。

| 項目 | 残す | 理由 |
|---|:---:|---|
| ステータス | **◯** | 確定した仕様か、レビュー前かは読み手に必要。**ただし語彙を統一する** |
| 対象（common / frontend など） | **◯** | どの領域の仕様かは本文から自明でないことがある |
| 関連（リンク） | **◯** | 正本を辿る導線。**「〜が正本」の一言を添える** |
| 作成日 | ✗ | git が持つ。手で更新すると腐る |
| 最終更新 | ✗ | 同上。**現に「最終更新: 2026-08-16（チーム会議での決定を反映）」と決定ログ化している** |
| 対応 Issue | △ | 起票根拠として有用だが、**Issue が閉じたあとも残り続ける。** 「関連」に統合してもよい |

> **決定（2026-08-17、ユーザー判断）: 仕様ドキュメントはメタ情報ヘッダを持たない。**
>
> タイトルの直下から本文を始める。ステータス・対象・作成日・最終更新・対応 Issue・関連のいずれも冒頭には置かない。手で更新する項目をなくすことで、**メタ情報が腐る問題を根本から断つ**（現に「最終更新: 2026-08-16（チーム会議での決定を反映）」がメタ情報の欄で決定ログ化していた）。
>
> 関連ドキュメントへのリンクは、冒頭のメタ情報としてではなく**本文の該当箇所か末尾の「参考」節**で示す（正本を辿る導線は残す）。
>
> **ADR と検討記録は対象外**（下記のとおり種別固有のメタ情報が正本そのものであるため）。

**ADR・検討記録のメタ情報は残す**

| 種別 | メタ情報 | 残す理由 |
|---|---|---|
| ADR | `ステータス` / `日付` / `被依存` | **`日付` は「決定の日付」の正本**（論点2の表）。仕様書から日付を外せるのは ADR が持つため |
| 検討記録 | `ステータス` / `区分` / `開始日` / `最終更新` / `関連` | `ステータス`（検討中 / 結論 / 中断）は再開時の判断に使う。`discuss-proposal` スキルのテンプレートに由来 |

**ステータス語彙の統一案**

| 種別 | 語彙 |
|---|---|
| 仕様ドキュメント | `ドラフト` / `レビュー待ち` / `確定` |
| ADR | `決定` / `廃止（ADR-NNNN で置き換え）` |
| 検討記録 | `検討中` / `結論` / `中断` |

現在「完了」6件 / 「結論」3件に割れている検討記録は `結論` に統一する（出典: `grep -m1 "^- ステータス" documents/00_検討/*.md`）。

## 結論

### 正本表（本検討の中核）

**原則: 検討記録は、いかなる情報についても正本にならない。**

| 情報の種類 | 正本 | 他の場所での扱い |
|---|---|---|
| **決まっている仕様**（何を作るか、どう振る舞うか） | **仕様ドキュメント**（`documents/` 配下） | 参照リンクのみ。値を書き写さない |
| **API の一覧と入出力仕様** | **`documents/backend/API仕様.md`**（新設） | [必要api .md](<../必要api .md>) は**必要な API のメモ**であり正本ではない |
| **アーキテクチャ上の決定と、その理由・トレードオフ** | **ADR**（`documents/ADR/`） | 仕様書には**決定の結果**だけを書き、理由は書かない |
| **決定に至る経緯・案の比較・議論** | **検討記録**（`documents/00_検討/`） | **正本にならない。** 仕様は必ず仕様ドキュメントへ書き出す |
| **決定の日付・決定の場** | **ADR の `日付`** | 仕様書に書かない |
| **未確定事項・懸念・宿題** | **GitHub Issue** | 仕様書は一覧表を章として持ってよい。ただし**詳細・選択肢は Issue 側**。決着したら表から消す |
| **進捗・ステータス・優先度** | **GitHub Issue**（open/closed・ラベル・アサイン） | 仕様書に書かない |
| **作業ログ・実測結果** | **PR 本文** | 凍結済み task-memo は記録として保存（新規作成しない） |
| **変更履歴** | **git** | 仕様書に「新旧対応表」「変更点」節を持たない |
