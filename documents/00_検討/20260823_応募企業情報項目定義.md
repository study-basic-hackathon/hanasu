### 確認できた不整合

| # | 不整合 | 影響 |
|---:|---|---|
| 1 | API 仕様は `company_name` / `company_info` / `motivation` / `resume` の4項目だが、S-07 は9項目である | 5項目に対応がなく、`company_info` と `resume` が何を指すか一意に決まらない |
| 2 | フロントエンドは9項目を持つが、バックエンドは5項目だけを持つ | `job_title`、`documents`、`current_position`、`experience_years` を保存・返却できない |
| 3 | 同じ URL にフロントエンドは `posting_url`、バックエンドは `company_url` を使う | API 連携時に変換または改名が必要。`company_url` は企業サイトの URL とも読め、画面の「募集要項 URL」より意味が広い |
| 4 | 画面では志望動機が任意だが、`CompanyCreate` は `motivation` を必須かつ空文字不可としている。model と出力 schema は NULL を許す | 現行 API では、画面仕様上保存できる「企業名だけ」の入力を受け付けられない |
| 5 | フロントエンドの任意文字列は空文字、バックエンドは主に `null`、API 仕様は未定義である | リクエストとレスポンスの変換、空白だけの値、更新時のクリア方法が定まらない |
| 6 | フロントエンド、バックエンド、API 仕様のいずれにも最大長がない | Issue #17 の完了条件を満たさず、画面・API・DB の検証条件を揃えられない |
| 7 | API 仕様のデータモデルは `applications`、実装は `companies` であり、実装の出力には `created_at` が含まれる | Issue #17 では DB 実装や日時追加を扱わないため、後続実装で仕様との差分を解消する必要がある |

### 2026-08-28 に確定した対象項目

ユーザー判断により、**現行バックエンド API が入出力する応募情報の項目を全項目とし、API に存在しない画面項目は削除する。** Issue #128 の表記 `posting_summary` ではなく、現行 API のフィールド名 `job_summary` を採る。

| 画面上の項目 | API フィールド | 入力型 | Create / Update | Read / List | 備考 |
|---|---|---|---|---|---|
| 企業名 | `company_name` | 文字列 | 必須・空文字不可 | 文字列 | 現行 API では一意制約がある |
| 募集要項 URL | `company_url` | HTTP(S) URL | 任意・未入力は省略または `null` | 文字列または `null` | 画面ラベルと API 名は異なる |
| 志望動機 | `motivation` | 文字列 | 必須・空文字不可 | 文字列または `null` | 入力と出力の nullable 表現は現行 API のままとする |
| 経歴・実績 | `resume` | 文字列 | 任意・未入力は省略または `null` | 文字列または `null` | |
| 備考 | `note` | 文字列 | 任意・未入力は省略または `null` | 文字列または `null` | |
| 募集要項の要約 | `job_summary` | 文字列 | 任意・未入力は省略または `null` | 文字列または `null` | 最新 `main` の PR #139 で追加済み |

`id` と `created_at` は現行 API のレスポンス専用メタデータであり、S-07 の入力項目には数えない。

次の4項目は、現行バックエンド API に存在しないため対象から削除する。

- 職種（`job_title`）
- 応募書類（`documents`）
- 現職 / 直近の所属（`current_position`）
- 経験年数（`experience_years`）

## 確定した最大長

最大長はすべて**前後の空白を除いた文字数**で数える。バイト数では、日本語と英数字で入力可能量が変わり、利用者に説明しづらいためである。

| 項目 | API フィールド | 最大長 | 理由・影響 |
|---|---|---:|---|
| 企業名 | `company_name` | 100文字 | 一般的な企業名には十分な余裕を持ちつつ、一意制約の対象となる値を過大にしない |
| 募集要項 URL | `company_url` | 2,048文字 | 通常の HTTP(S) URL を収めつつ、異常に長い入力を抑える |
| 志望動機 | `motivation` | 4,000文字 | 面接用の長文を許容しながら、質問生成へ渡す入力を抑える |
| 経歴・実績 | `resume` | 10,000文字 | 職務経歴の貼り付けに余裕を持たせる。これ以上は LLM 入力への影響が大きくなる |
| 備考 | `note` | 2,000文字 | 補足・避けたい話題の記載には十分で、プロンプトの肥大化を抑えられる |
| 募集要項の要約 | `job_summary` | 4,000文字 | 要約として十分な量を確保しつつ、元本文相当の長文が保存されることを防ぐ |

任意項目の空文字・空白だけの入力は `null` へ正規化する。`company_name` と `motivation` は現行 API どおり、空文字・空白だけをエラーにする。

## 懸念

| 懸念 | 深刻度 | 解消に必要な確認 |
|---|---|---|
| 長文をそのまま質問生成へ渡すと、LLM の入力制限、コスト、応答時間に影響する | 中 | 後続実装で、最大長内の値を全量渡すかさらに要約するかを確認する |
| Company の `motivation` は既存データ互換のため `null` を許容する一方、CompanyInput では必須である | 中 | 後続実装・テストで Create / Update と Read / List の型差を明示する |
| `job_summary` の手入力・保存と、URL からの自動生成は実装範囲が異なる | 中 | 後続実装 Issue で自動生成（Issue #128 など）を明確に範囲外とする |

## 議論ログ

- **2026-08-23 ラウンド1**: Issue #17 と `main` の画面仕様、画面/API対応表、API仕様、フロントエンド9項目、バックエンド schema / model を照合した。9項目、企業名のみ必須、URL形式、経験年数0〜99は確定済み。フィールド名、任意値の表現、最大長はリポジトリの事実だけでは確定できないため、選択肢と影響を整理してユーザー判断待ちとした。
- **2026-08-28 ラウンド2**: 最新 `origin/main`（`8fea338`）、Issue #128、PR #139 を再確認した。ユーザー判断により、現行バックエンド API の5項目と `job_summary` の計6項目を全項目とし、API にない `job_title` / `documents` / `current_position` / `experience_years` は削除すると決定した。最大長は推奨値を提示し、採用可否の回答待ちとした。
- **2026-08-28 ラウンド3**: ユーザー判断により、6項目の推奨最大長、前後空白を除いた文字数での判定、任意項目の空文字・空白のみを `null` に正規化する方針を承認した。プルリクエスト作成前に最新 `origin/main`（`97445b8`）へ更新し、応募企業情報に関する追加変更がないことを確認した。対象項目と制約の未決を解消し、本検討を完了とした。

## 結論

応募企業情報は `company_name` / `company_url` / `motivation` / `resume` / `note` / `job_summary` の6項目とする。`company_name` と `motivation` は必須、残り4項目は任意である。項目ごとの型・最大長・未入力の扱いは [API仕様](../backend/API仕様.md) 4章を正本とする。これらと画面の差分は後続の実装 Issue で解消する。
