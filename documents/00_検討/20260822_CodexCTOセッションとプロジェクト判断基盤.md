## 背景・きっかけ

現在は Codex 上のオーケストレーションセッションだけで、既存タスクの依存順、再開・停止、並行実行、完了ゲート、横断リスクを管理している。ユーザーから、この運用にリポジトリ内フォルダーを組み合わせる価値と、プロジェクト固有の判断軸に基づいて一部の技術判断を担う CTO 的な Codex セッションの可能性を検討したいとの相談があった。

目的は、AI に無制限の技術裁量を与えることではない。プロジェクトごとに判断の軸、権限、停止条件を明示し、委譲可能な判断だけを再現可能・レビュー可能な形で任せる運用を作れるかを検討する。

## 論点

### 必須

1. リポジトリに永続化する情報と、Codex タスク内だけに保持する実行時状態をどう分けるか。
2. プロジェクト固有の技術判断軸の正本をどこに置き、どのタスクからも同じ内容を参照できるようにするか。
3. CTO セッションが決定してよい技術判断と、推奨だけを示す判断、必ずユーザーへ返す判断の境界をどう定義するか。
4. 現行オーケストレーターの「技術判断は元タスクで回答し、別タスクで代理回答しない」という不変条件を、CTO セッションの導入時にどう変更するか。
5. CTO セッションが出した結果を、実装タスクとオーケストレーターが誤読せずに消費できる受け渡し契約をどうするか。
6. AI の判断品質をどの代表ケースで検証し、どの条件を満たせば判断権限を広げるか。

### 任意

7. フォルダー名、ファイル名、スキル名、CTO タスク名をどうするか。
8. CTO タスクをプロジェクト単位の継続タスクにするか、判断単位で分けるか。
9. 判断結果の報告形式とユーザーへの確認頻度をどうするか。

## 事実確認（出典付き）

- Codex は作業開始時に `AGENTS.md` を読み、グローバル指示とリポジトリルートから作業ディレクトリまでのプロジェクト指示を階層的に結合する（出典: [OpenAI Docs: Custom instructions with AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)）。
- Codex はリポジトリ内で、作業ディレクトリからリポジトリルートまでの `.agents/skills` を走査する。スキルは処理手順、参照資料、任意スクリプトをパッケージ化でき、明示起動または `description` との一致により暗黙起動できる（出典: [OpenAI Docs: Build skills](https://learn.chatgpt.com/docs/build-skills)）。
- `.codex/` 以下の任意のファイルが自動的にプロジェクト指示やスキルとして読まれるとは、確認した OpenAI Docs に記載されていない。そのため `.codex/` を記録保存先にする場合は、対応スキルや `AGENTS.md` から明示的に読む契約が必要と考えられる（出典: 上記 OpenAI Docs からの推論）。
- 現在のリポジトリにはルート `AGENTS.md` と `.agents/skills` は存在せず、`frontend/AGENTS.md` だけがある（出典: `frontend/AGENTS.md`、2026-08-22 のローカル確認）。
- 現在のリポジトリには `.codex/retrospectives/` が存在し、プロジェクト固有の振り返りを保存する実例がある。これは専用の振り返りスキルが読み書きするカスタム運用であり、Codex の自動読み込み先とは確認されていない（出典: `.codex/retrospectives/2026/08/20260822-133931-issue87-deployment-governance.md`、[Codex 振り返り・改善スキル群](20260822_Codexセッション振り返りスキル.md)）。
- 現行の `codex-session-orchestrator` は、アーキテクチャ、ライブラリ、テスト方式などを決めない。技術判断は元タスクで回答してもらい、別タスクで代理回答しないと定めている（出典: `/Users/moritayutaro/.codex/skills/codex-session-orchestrator/SKILL.md`「技術判断と進行判断の境界」「ユーザー判断として停止する条件」）。
- このリポジトリでは、決定済みの仕様は仕様ドキュメント、アーキテクチャ上の決定と理由・トレードオフは ADR、比較と議論は検討記録、未確定事項と進捗は GitHub Issue を正本とする（出典: [ドキュメントの書き方](../README.md)「情報の種類ごとの正本」）。

## 現時点の設計仮説

### 1. 「セッション」と「リポジトリ」の責務を分ける

Codex タスクは、会話、調査中のメモ、直前のやり取り、判断待ちなどの「作業場」として使う。プロジェクトごとに一つの継続 CTO タスクを置く案は、普段の相談窓口を一つにし、直前の会話をそのまま続けられることが利点である。

一方、CTO タスクの会話履歴だけに技術判断を残すと、そのタスクの会話を読まない限り、別の実装タスクや作り直した CTO タスクは決定内容を確実に復元できない。そこで、タスクが変わっても維持すべき情報は、次のようにリポジトリ側へ記録する。

- CTO の判断権限と判断軸: 技術判断方針
- 決定済みのアーキテクチャと理由: ADR
- 現在の仕様: 仕様ドキュメント
- 未決の論点、ユーザー回答待ち、残作業: GitHub Issue や検討記録

ここで「タスクを作り直してもリポジトリから復元できる」とは、新しい CTO タスクが `AGENTS.md`、CTO スキル、技術判断方針、ADR、仕様、Issue を読めば、古い CTO タスクの会話全文を読まなくても、同じ権限と確定済み前提で判断を再開できる状態を指す。OpenAI Docs でも、Codex は各実行の開始時にプロジェクトの `AGENTS.md` を読み直す仕組みとされている（出典: [OpenAI Docs: Custom instructions with AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)）。

例えば、CTO タスクの会話で「認証にサービス X を使う」と決めただけでは、別タスクに伝わらない。これを ADR へ記録し、必要な仕様へ結果を反映して初めて、古い CTO タスクがなくてもプロジェクトの決定として復元できる。

### 2. 永続化するものを 3 層に分ける

| 層 | 候補の置き場 | 内容 | 性質 |
|---|---|---|---|
| 作業手順 | `.agents/skills/project-cto/SKILL.md` またはユーザースキル | 事実確認、判断分類、軸の適用、停止、記録の手順 | AI 向けの再利用可能なワークフロー |
| プロジェクト固有の判断契約 | `documents/技術判断方針.md` など | 目的、ハード制約、優先順位、権限、保留事項、必要証拠 | 人間と AI が共通で読む正本候補 |
| 個別の判断結果 | `documents/ADR/`、仕様、GitHub Issue | 決定、理由、現行仕様、未決事項 | 既存の正本運用を維持 |

`AGENTS.md` は上記を重複転記する場所ではなく、技術判断が発生したときに判断方針と CTO ワークフローへ誘導する短いエントリポイントにする。`.codex/retrospectives/` は学びの候補保存先として使えるが、現行の判断軸や進捗の正本にはしない。

### 3. CTO セッションを「無制限の判断者」ではなく「委譲契約付きの技術判断機関」とする

判断の軸は、模糊な理念の羅列ではなく、次の順で適用できる形にする。

1. **必須制約**: 満たさない案を除外できるイエス・ノー条件。
2. **順位付きの優先軸**: 例えばハッカソンの期限、運用コスト、変更可能性、セキュリティなど。プロジェクトが順序を決め、AI が重みを推測しない。
3. **既定のデフォルト**: 特定条件で常に選ぶ方式。
4. **委譲可能な判断クラス**: 利用範囲が局所的、可逆的、追加コストや外部契約がない、既存 ADR に反しないなどの条件。
5. **人間保留事項**: プロダクト範囲、外部契約、重大なコスト、法務・プライバシー・セキュリティのリスク受容、不可逆変更、判断軸同士が衝突するトレードオフなど。
6. **証拠標準**: 一次情報、リポジトリ上の検証、プロトタイプ、ベンチマークなど、判断種別ごとに必要な根拠。
7. **再検討トリガー**: 前提の変更、コスト閾値の超過、実装不能、重大なインシデントなど。

AI が単独決定できるのは、原則として「明示済みのデフォルトが存在する」または「必須制約と優先軸を適用すると委譲範囲内の一案に絞れる」場合に限る案とする。複数の妥当案が残り、未定義の重み付けやリスク受容が必要な場合は、勝手に解釈せずユーザーへ返す。

### 4. セッション連携は「判断パケット→正本への反映→再開」とする

1. 実装タスクが未決の技術論点で停止する。
2. オーケストレーターが、論点、影響するタスク、確認済み事実と出典、選択肢、可逆性、未確認事項を一つの判断パケットにする。
3. CTO セッションが判断契約を適用し、結果を次のいずれかで返す。
   - `委譲済み判断`: 委譲範囲内で一案に決定できた。
   - `推奨`: 妥当案は示せるが、ユーザー決定が必要。
   - `要ヒアリング`: 結果を変え得る事実または判断軸が不足している。
4. `委譲済み判断` またはユーザーが採用した結果を、決定の性質に合わせて ADR、仕様、Issue の正本へ反映する。
5. オーケストレーターは、会話の要約を独自に確定事項として伝えず、正本の更新を確認して影響タスクを再開する。

この運用にする場合、現行オーケストレーターの「別タスクで代理回答しない」という禁止は、「未承認のタスクが代理判断しない。承認済みの CTO 判断経路は正本への反映後に限り消費できる」と置き換える必要がある。

### 5. 導入は段階的に行う

1. **シャドー運用**: CTO は判断軸を使って推奨と質問を出すが、決定はユーザーが行う。過去にユーザーが判断した代表ケースと比較する。
2. **明示デフォルトの委譲**: プロジェクトに明記されたデフォルトの適用だけを自動決定できる。
3. **境界付き委譲**: 局所的・可逆的な判断など、事前に承認した判断クラスへ拡張する。

段階を上げる条件は、単に経過期間や件数ではなく、代表的な判断において、制約違反を除外できたこと、事実と推測を分けたこと、必要なヒアリングを行ったこと、ユーザー判断との差分が説明可能なことを検証できた場合とする案とする。

## 選択肢の比較

比較軸は未合意。現時点では「復元性、レビュー可能性、自動利用される確実性、保守コスト、判断権限の誤認リスク、既存の正本との重複」を候補とする。

| 観点 | A案: セッションだけ | B案: 判断方針ドキュメントだけ | C案: スキル + 判断方針 + 既存正本 | D案: 独自の進捗・判断台帳 |
|---|---|---|---|---|
| タスクを跨ぐ復元性 | 低い | 中 | 高い | 高い |
| AI が正しい手順で利用する確実性 | プロンプト依存 | 読み忘れがある | スキルと `AGENTS.md` で誘導可能 | 台帳を読む手順が別途必要 |
| 人間のレビュー | 会話の閲覧が必要 | しやすい | しやすい | しやすい |
| 保守コスト | 小 | 小〜中 | 中 | 高 |
| 既存正本との重複 | 小 | 設計次第 | リンク中心なら小 | 大きい |
| 断片化・陳腐化 | 会話が埋もれる | 手動で更新 | 役割分担が明確なら抑制可能 | 二重管理で起きやすい |
| 現時点の推奨 | 見送り | 移行案 | **シャドー運用の候補** | 原則見送り |

## 懸念

| 懸念 | 深刻度の感触 | 解消に必要な確認 |
|---|:---:|---|
| 判断軸が「保守性を重視」のような抽象語にとどまり、AI が独自に重み付けする | 高 | 必須制約、優先順位、デフォルト、保留事項へ分解する |
| CTO セッションの会話内だけで決定し、実装タスクに異なる要約が伝わる | 高 | 正本の更新を再開ゲートにする |
| CTO が複数の妥当案から好みで一つ選ぶ | 高 | 一案に絞れなければユーザーへ返す |
| 判断方針と ADR、仕様、Issue が重複して矛盾する | 高 | 判断方針は「将来の判断方法」に限定し、個別の決定を転記しない |
| オーケストレーターが CTO の推奨を決定として実装タスクへ流す | 高 | `委譲済み判断` / `推奨` / `要ヒアリング` を区別する |
| CTO セッションがボトルネックまたは単一障害点になる | 中 | 判断をリポジトリに永続化し、タスク再作成を可能にする |
| `AGENTS.md` に詳細を詰め込み、すべてのタスクのコンテキストを圧迫する | 中 | 誘導と不変条件に限定し、詳細はスキルと判断方針へ分離する |
| 自動化のために新しい進捗台帳を作り、Issue と二重管理になる | 高 | 実行状態は Codex タスク、進捗は Issue、決定は ADR・仕様を維持する |

## 議論ログ

### 2026-08-22 第1ラウンド

- ユーザーから、現在 Codex 上のセッションだけで行っているオーケストレーション管理に、リポジトリ内フォルダーを使う価値と運用イメージについて相談があった。
- ユーザーから、現行オーケストレーションで禁止している技術判断の一部を、プロジェクト固有の判断軸に沿う CTO 的セッションへ委譲できないかという構想が示された。
- Codex が自動探索する `AGENTS.md` と `.agents/skills`、現在のリポジトリの正本運用、現行オーケストレーターの技術判断禁止を確認した。
- 初期仮説として、リポジトリ内に独自の進捗台帳は作らず、「汎用またはリポジトリ固有スキル」「プロジェクト固有の判断契約」「ADR・仕様・Issue の既存正本」の 3 層に分ける案を推奨候補とした。
- CTO は「委譲済み判断」「推奨」「要ヒアリング」を明確に区別し、正本への反映後にだけ他タスクを再開できる案をたたき台とした。
- 本ラウンドでは結論を確定せず、適用範囲、初期権限、対象とする判断種別、比較軸を残論点とした。

### 2026-08-23 第2ラウンド

- ユーザーから、「CTO タスクの会話を正本にせず、タスクを作り直してもリポジトリから復元できる」の意味が分かりにくいとの質問があった。
- 「プロジェクトごとの継続 CTO タスク」は日常の相談窓口としては使うが、権限、決定、仕様、未決事項の正本にはしないと説明を補った。
- 新しい CTO タスクがリポジトリの指示、判断方針、ADR、仕様、Issue を読むことで、古い会話全文に依存せず再開できる状態を「復元できる」と定義した。
