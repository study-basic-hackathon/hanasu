## 背景・きっかけ

Claude Code のプロジェクトスキルを前提として検討済みの「セッション振り返りによる AI 改善ループ」を、Codex のユーザースキルとしてリポジトリ横断で使える形へ再設計する。

目的は、セッションの記録自体を増やすことではなく、ユーザーによる訂正、手戻り、詰まり、再現したい成功パターンから、次回の作業を改善する介入を抽出し、適切な場所へ反映することである。

スキル本体は特定リポジトリに限定しない。学びは個人・汎用とプロジェクト固有を混同せず、正本を二層に分ける方針を第一の確定事項とする。

## 論点

1. **確定: 学びの正本をどの範囲に置くか**
   - 2026-08-22: 二層に振り分ける。個人・汎用の学びはユーザー領域、プロジェクト固有の学びは各リポジトリに置く。
2. **確定: 何を一つの振り返り対象とみなすか**
   - 2026-08-22: PR や Issue の有無ではなく、ユーザーが区切った論理的な作業単位を対象とする。
3. **確定: 初版でどこまで自動化するか**
   - 2026-08-22: 作業内容が文脈に残っている同じ Codex タスク内で、論理的完了時に明示起動する。`SessionEnd` hook は初版に含めず、打ち忘れが実証された場合のリマインド候補とする。
4. **確定: 何を永続化するか**
   - 2026-08-22: 初版では、ユーザーが承認した学びと、その介入・状態だけを保存する。会話全文、未承認候補、却下候補は保存しない。
   - 2026-08-22: 1 つの論理的作業単位につき、ユーザー層とプロジェクト層へそれぞれ最大 1 ファイルを作る。両層に学びがあれば対応する 2 ファイルを作り、承認済み学びがゼロ件の層にはファイルを作らない。
5. **確定: 個人・汎用とプロジェクト固有の判定基準**
   - 2026-08-22: 明らかな個人の好み、またはリポジトリによらず適用できる作業原則はユーザー領域へ置く。
   - リポジトリの規約・環境・アーキテクチャに依存するものと、判定に迷うものはプロジェクト側へ置く。同じ学びが複数リポジトリで再現した場合は、ユーザー領域への昇格候補とする。
   - 秘密、認証情報、個人情報はどちらにも保存しない。
6. **確定: 二層の既定保存先**
   - 2026-08-22: リポジトリのローカル規約または既存の振り返り保存先があれば、それを優先する。
   - 未指定時は、ユーザー層を `$HOME/.codex/retrospectives/`、プロジェクト層を `$REPO_ROOT/.codex/retrospectives/` とする。スキル本体と生成される振り返りデータは分離する。
7. **確定: 反映工程の担い手**
   - 2026-08-22: 日常の振り返りを行う「記録専用スキル」と、蓄積した記録を棚卸しして改善を反映する「棚卸し・反映スキル」の 2 スキルへ分離する。
   - 記録専用スキルは、反映スキルを自動起動しない。反映スキルも明示起動し、実際の変更は対象タスクの権限・承認境界に従う。
   - 2026-08-22: 棚卸し時期はユーザー判断のみとする。記録専用スキルは、件数・重複・緊急度による起動推奨やリマインドを行わない。
   - 反映先は、機械的強制、作業固有のスキル・テンプレート、スコープに合う `AGENTS.md` の順に検討する。Codex Memories は初版の明示的な反映先にしない。
8. **確定: 振り返りスキルの書き込み境界**
   - 2026-08-22: 初版の振り返りスキルは、ユーザーが承認した学び・分類・介入案を振り返りファイルへ保存するところで停止する。
   - `AGENTS.md`、ユーザースキル、リポジトリスキル、テンプレート、hook、lint、CI などの反映先は変更しない。反映は別工程とする。
   - 振り返りファイル自体の書き込みも、実行中タスクの filesystem permission と承認境界に従う。
9. **確定: 学びの状態**
   - 2026-08-22: `未反映`、`反映済み`、`見送り` の 3 状態で管理する。
   - 記録時は原則 `未反映`。同じ作業単位ですでに介入が適用・検証済みであることを確認できる場合だけ、ユーザー承認のうえ `反映済み` で記録してよい。
   - 棚卸し・反映スキルは、変更を適用して検証できた後に `反映済み`、ユーザーが不要・陳腐化・費用不相応などの理由を承認した場合に `見送り` へ更新する。判断保留や反映失敗は `未反映` のままとする。
10. **確定: 初版の記録形式**
   - 年・月ディレクトリの下に、`YYYYMMDD-HHMMSS-<短いトピック>.md` で保存する。同名が存在する場合は上書きせず連番を付ける。
   - ファイルは YAML frontmatter で記録 ID、スコープ、作成日時、作業単位、任意のリポジトリ・参照元を持つ。本文は学びごとに、状態、型、事象、学び、介入案、反映先候補、解決記録を持つ。
   - ユーザー層とプロジェクト層に対応ファイルがある場合は同じ記録 ID を使う。
11. **確定: 初版のスキル構成と起動方針**
   - 記録専用スキル名は `capture-retrospective`、棚卸し・反映スキル名は `review-retrospectives` とする。
   - どちらも `$HOME/.agents/skills/<skill-name>/` に置くユーザースキルとし、`agents/openai.yaml` で `allow_implicit_invocation: false` を設定する。
   - 初版は各スキルの `SKILL.md` と `agents/openai.yaml` だけで構成する。単純な Markdown の読み書きにスクリプトは導入せず、記録契約は両スキルに必要最小限だけ記載する。
12. **確定: 初版の効果確認**
   - ゼロ件の作業単位は記録しないため、全作業単位を母数とする訂正率・再発率は初版では測定しない。
   - 棚卸し時に `未反映`、`反映済み`、`見送り` の件数と、今回処理した件数を会話上で報告する。別の集計ファイルは作らない。
13. **確定: Git 操作の境界**
   - どちらのスキルも、振り返りファイルや反映先を自動で `git add`、commit、push しない。また `.gitignore` を変更しない。
   - プロジェクト層の記録をバージョン管理するかは、各リポジトリの規約とユーザーの通常の Git 運用に委ねる。

## 事実確認（出典付き）

- Codex のユーザースキルの公式な配置先は `$HOME/.agents/skills`。リポジトリスキルは、作業ディレクトリからリポジトリルートまでの `.agents/skills` から探索される（出典: [OpenAI Docs: Build skills](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills)）。
- スキルは明示起動と、`description` に基づく暗黙起動の両方を利用できる。`agents/openai.yaml` で暗黙起動を無効化できる（出典: [OpenAI Docs: Build skills](https://learn.chatgpt.com/docs/build-skills#how-codex-uses-skills)）。
- Codex は `SessionEnd` を含む lifecycle hooks を設定できる。現時点で実行される hook handler は command hook で、`SessionEnd` は同期実行される（出典: [OpenAI Docs: Configuration Reference](https://learn.chatgpt.com/docs/config-file/config-reference#configtoml)）。
- Codex Memories は設定で有効化できるが、既定では無効である（出典: [OpenAI Docs: Configuration Reference](https://learn.chatgpt.com/docs/config-file/config-reference#configtoml)）。
- Codex はグローバル指示として `$CODEX_HOME/AGENTS.md`（既定は `$HOME/.codex/AGENTS.md`）を読み、プロジェクトルートから作業ディレクトリまでの `AGENTS.md` / `AGENTS.override.md` を階層的に読む（出典: [OpenAI Docs: Custom instructions with AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)）。
- ユーザースキルがユーザー領域にあっても、実行中の Codex が任意のユーザー領域やリポジトリへ無条件に書き込めることを意味しない。書き込みは、そのタスクの filesystem permission と承認境界に従う（出典: [OpenAI Docs: Configuration Reference](https://learn.chatgpt.com/docs/config-file/config-reference#configtoml) の sandbox / permission 設定）。
- 現在のローカル環境には `$HOME/.agents/skills` と `$HOME/.codex/skills` の両方が存在する（出典: 2026-08-22 のローカルファイル確認）。新規設計は公式の現行配置 `$HOME/.agents/skills` を基準とし、既存配置との互換性は実装時に別途確認する。

## 初版のスキル構成

### `capture-retrospective`

論理的な作業単位の完了時に、現在の Codex タスクの文脈から学びの候補を抽出し、ユーザーが承認したものだけを記録する。改善対象そのものは変更しない。

1. 明示起動されたことと、振り返る論理的な作業単位を確認する。
2. 現在のタスクに残る会話・作業結果だけを根拠とする。判断に必要な文脈が失われている場合は、過去タスクのログを自動探索せず、元のタスクでの実行または不足情報の提示を求める。
3. ユーザーによる訂正、手戻り、詰まり、再現したい成功パターンから、高い確度で再利用できる学びの候補を抽出する。特にユーザーの訂正を優先する。
4. 単なる作業履歴、プロダクト知識の正本にすべき内容、具体性のない感想、秘密・認証情報・個人情報を候補から除外する。
5. 各候補を次のいずれかへ分類する。
   - `知識ギャップ`: 必要な知識や事実の確認が不足していた。
   - `既存指示の発見性・曖昧さ`: 指示は存在したが見つけにくい、適用範囲が分かりにくい、または解釈が割れた。
   - `判断ズレ`: 事実は把握していたが、優先順位、意図、粒度、トレードオフの判断がユーザーとずれた。
   - `環境・手順発見`: ツール、権限、ローカル環境、実行順序など、再利用できる実務上の発見があった。
   - `仕組み不備`: 注意書きだけでは再発しやすく、hook、lint、CI、テンプレートなどの機械的な介入が適する。
6. 各候補について、学び、介入案、最も狭い有効範囲、反映先候補を提示する。
7. 保存前に全候補をユーザーへ提示し、採用、修正、除外、およびユーザー層・プロジェクト層の分類について承認を得る。
8. 承認済み候補だけを、1 作業単位につき各層最大 1 ファイルへ保存する。承認済み候補がゼロ件の層にはファイルを作らない。
9. 保存先へ書き込めない場合は、別の層へ黙って代替保存しない。必要な保存先または権限を報告して停止する。

このスキルは、棚卸し時期の推奨、`review-retrospectives` の自動起動、改善対象への変更、Git 操作を行わない。

### `review-retrospectives`

蓄積済みの学びをユーザー指定のタイミングで棚卸しし、承認された改善を適切な正本へ反映して状態を更新する。

1. 明示起動されたことと、棚卸し対象の範囲を確認する。
2. 対象指定がなければ、ユーザー層と現在のプロジェクト層を対象にする。リポジトリ外で起動した場合はユーザー層だけを対象にする。ユーザーは層、期間、型、記録 ID で範囲を狭められる。
3. 既定では `未反映` の学びだけを処理対象とし、3 状態の件数を会話上で報告する。
4. 類似・重複する学びをまとめ、現在の反映先、既存指示、ローカル規約、すでに行われた変更を再確認する。記録内容をそのまま事実とみなさない。
5. 複数リポジトリに由来する同種の学びは、異なる 2 リポジトリ以上での再現が確認でき、ローカル規約と衝突しない場合にユーザー層への昇格候補とする。明示された個人の好みは、初回からユーザー層の候補にしてよい。
6. 変更前に、対象、具体的な変更案、根拠となる記録 ID、検証方法、成功時に更新する状態を一つのバッチとして提示し、ユーザー承認を得る。
7. 承認された変更だけを適用し、変更先に応じた検証を行う。対象タスクの権限・承認境界と、対象リポジトリの規約に従う。
8. 適用と検証の両方に成功した後で、根拠となった学びを `反映済み` へ更新し、解決記録へ反映先と結果を残す。複数の学びを一つの介入で解決した場合は、同じ解決記録を参照させてよい。
9. ユーザーが理由を承認した場合だけ `見送り` へ更新する。判断保留、承認されなかった変更、権限不足、反映失敗、検証失敗は `未反映` のまま残す。
10. 選択した各学びについて、`反映済み`、`見送り`、または未反映のまま残る理由を報告して完了する。

このスキルは、変更対象を無制限に広げない。プロダクト仕様や設計の変更が必要になった場合は、対象リポジトリの通常の仕様化・設計・実装フローへ切り出す。

## 振り返り記録の契約

既定の保存先では、年・月ディレクトリを作り、次の構造で保存する。

```text
<retrospectives-root>/YYYY/MM/YYYYMMDD-HHMMSS-<短いトピック>.md
```

初版の最小形式は次のとおりとする。

```markdown
---
id: 20260822-153012-example
scope: user # user | project
created_at: 2026-08-22T15:30:12+09:00
work_unit: "短い作業単位の説明"
repository: null # project の場合は識別可能な名前
source: null # Issue、PR、Codex タスクなど。分かる場合だけ
---

# 振り返り: 短いトピック

## L-01: 学びの短い見出し

- 状態: 未反映
- 型: 判断ズレ
- 事象: 判断が必要になった具体的な状況
- 学び: 次回にも使える形に一般化した内容
- 介入案: 再発防止または成功再現のための具体案
- 反映先候補: 最も狭い有効範囲の正本または仕組み
- 解決記録: なし
```

- `id` は論理的作業単位を識別する。二層にファイルが分かれた場合も同じ `id` を使う。
- ファイル内の学び ID は `L-01` から連番とし、同じファイル内で一意にする。
- `解決記録` は未反映時には `なし` とし、状態更新時に、日時、判断理由または反映先、検証結果を簡潔に記載する。
- ユーザー層には、必要のないリポジトリ名、絶対パス、内部 URL、固有名詞を持ち込まない。再利用性を損なわない範囲で一般化する。
- プロジェクト固有の学びなのにリポジトリルートを特定できない場合は、ユーザーへ場所を確認するか保存を見送る。ユーザー層へ代替保存しない。
- ユーザー層へ書き込めない場合も、プロジェクト層へ代替保存しない。未保存であることと必要な対応を明示する。

## 反映先の選択原則

学びを増やすことより、同じ問題が起きる経路へ最小の介入を置くことを優先する。

| 学びの性質 | 第一候補 | 選択理由 |
|---|---|---|
| 客観的に判定でき、違反を自動検出できる | hook、lint、テスト、CI など | 注意力に依存せず再発を防げる |
| 特定の作業手順として再利用する | 対応するユーザーまたはプロジェクトのスキル | 必要な作業時だけ詳細手順を読み込める |
| 依頼受付時の情報不足や完了条件の漏れ | テンプレート、チェックリスト | 作業開始前に不足を防げる |
| リポジトリ横断の個人の好み・作業原則 | `$CODEX_HOME/AGENTS.md` | ユーザー全体へ常時適用する指示に適する |
| リポジトリ固有の原則・規約 | 対象ファイルに最も近い有効な `AGENTS.md` または同等のローカル正本 | 適用範囲を必要最小限に保てる |
| プロダクト仕様、設計、ドメイン知識 | 対象プロジェクトの仕様・設計・運用上の正本 | 振り返り記録やエージェント指示を知識の正本にしない |

- すでに明確な指示が存在するのに見落とした場合は、同じ指示を別の場所へ複製しない。発見性、配置、適用範囲を改善するか、可能なら機械的に検出する。
- 指示を読んだうえで繰り返し失敗する場合は、文章を増やすだけでなく、機械的強制またはレビュー工程を優先する。
- 一つの介入で十分なら複数箇所へ重複反映しない。最も狭く、保守される正本を選ぶ。
- Codex Memories は初版の反映先から除外する。ユーザーが後に明示的に採用した場合だけ、レビュー可能性と削除方法を確認して追加検討する。

## 状態遷移と完了条件

| 状態 | 意味 | 遷移条件 |
|---|---|---|
| `未反映` | 有効な学びとして承認されたが、介入が未適用、未検証、判断保留、または失敗中 | 記録時の既定。適用・検証成功で `反映済み`、理由付きの明示判断で `見送り` へ進む |
| `反映済み` | 対応する介入が正本または仕組みへ適用され、必要な検証も完了した | 記録時点ですでに適用・検証済みの場合、または棚卸し時の適用・検証成功後だけ設定する |
| `見送り` | 学びは確認したが、不要、陳腐化、重複、費用不相応などの理由で反映しないと決めた | 理由を記録し、ユーザーがその判断を承認した場合だけ設定する |

初版では状態を戻す専用操作を設けない。反映済みの介入が後に無効になった、または見送り理由が失われた場合は、新しい論理的作業単位の学びとして記録し、履歴を書き換えない。

`capture-retrospective` の完了条件は、候補をユーザーが確認し、承認済み学びが保存されたか、承認済み学びがゼロ件または権限上未保存であることが明示されたことである。`review-retrospectives` の完了条件は、選択した学びのそれぞれについて、状態更新または未反映のまま残す理由と、3 状態の件数・今回処理件数が報告されたことである。

## 懸念

| 懸念 | 深刻度の感触 | 解消に必要な確認 |
|---|---|---|
| ユーザー領域にプロジェクト固有情報や秘密が混入する | 対応済み | 迷えばプロジェクト側へ置き、秘密・認証情報・個人情報は保存しない |
| 振り返りスキル自身が失敗のたびに肥大化する | 対応済み | 反映先の選択原則に従い、機械的強制、作業固有スキル、テンプレート、スコープに合う指示へ振り分ける |
| `SessionEnd` が論理的な作業完了と一致しない | 対応済み | 初版は同じタスク内で論理的完了時に明示起動する |
| ユーザー領域への書き込みで権限確認が発生する | 運用上の制約 | 書き込めない場合は代替保存せず、必要な権限と未保存であることを報告する |
| AI の自己評価だけではユーザーの訂正を取りこぼす | 対応済み | ユーザー訂正を優先して候補化し、保存前に全候補の採用・修正・除外をユーザーが承認する |
| 承認済み学びと反映済みルールが重複して腐る | 対応済み | 3 状態と解決記録で追跡し、棚卸し時に重複と現在の反映先を再確認する。履歴は削除せず状態で残す |
| 記録だけが蓄積し、次回の作業へ反映されない | 許容 | 別の棚卸し・反映スキルへ分離し、ユーザー判断で明示起動する |
| プロジェクト層の記録が Git 管理方針と衝突する | 対応済み | スキルは stage、commit、push、`.gitignore` 変更をせず、各リポジトリの運用へ委ねる |

## 結論

初版は、明示起動のユーザースキル `capture-retrospective` と `review-retrospectives` の 2 つで構成する。前者は現在のタスク文脈からユーザー承認済みの学びだけを二層の記録へ保存し、後者は `未反映` の学びを棚卸しして、承認された介入の適用・検証後に状態を更新する。

学びは `未反映`、`反映済み`、`見送り` で管理する。反映先は、機械的強制、作業固有スキル、テンプレート、スコープに合う `AGENTS.md`、プロジェクトの正本から、最も狭く保守される場所を選ぶ。記録スキルは改善対象を変更せず、反映スキルも変更前のユーザー承認、変更後の検証、Git 操作を行わない境界を守る。

本件は個人用の追加的な仕組みであり、プロダクト仕様やアーキテクチャ判断ではないため、仕様書や ADR への昇格は行わない。設計上の必須判断は完了した。次の作業は、別の実装タスクで 2 スキルを作成し、代表ケースで明示起動、二層保存、状態更新、権限不足時の停止を検証することである。
