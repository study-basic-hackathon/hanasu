# Issue テンプレート

GitHub Issue を起票・更新するときに、下の「テンプレート本体」を本文へコピーして使う。

運用方針の根拠は [検討記録: AI に実装させるためのタスク運用方針](../00_検討/20260808_AI向けタスク運用方針.md)。
**現時点の適用範囲は ytr-33 の担当分のみ**（チーム全体への展開は合意待ち）。

## なぜこの項目なのか

AI に「Issue #N を実装して」と渡すだけで着手でき、**AI 自身が完了を判定できる**ことを基準に選んでいる。
特に **「やらないこと」** は重要。AI は放っておくとスコープを広げるため、明示的な禁止が最も効く。

## 種別

Issue には次の5種別のいずれかを付ける。**GitHub ラベル（`種別: xxx`）と本文冒頭のバナーの両方に書く** — 人はラベルで絞り込み、AI は本文だけで判断できるようにするため。

| 種別 | 何をするか | 成果物 | 完了条件の形 |
|---|---|---|---|
| **検討** | 選択肢を比較して選ぶ | 検討記録（`documents/00_検討/`）+ ADR（`documents/ADR/`） | 決定が記録されている |
| **仕様** | 決まっていることを書き下す | 仕様ドキュメント | ドキュメントが存在しレビュー済み |
| **実装** | アプリのコードを書く | コード + PR | 動作が観測できる（画面が出る / API が 200 を返す） |
| **環境** | 開発環境・インフラを作る | 設定ファイル + PR | 起動する / `terraform plan` が通る |
| **不具合** | 既存の不具合を直す | 修正 + PR | 再現手順で再現しなくなる |

**迷ったら「実装」に倒す。** 起票時の判断で止まらないことを優先する。

親トラッキング Issue（後述）と、日程調整などの非技術タスクは種別を付けなくてよい。

### 本文冒頭のバナー

本文の1行目に、種別に応じて次を置く。

```markdown
> **種別: 検討** — 選択肢を比較して決め、検討記録と ADR に残す。実装はしない。
> **種別: 仕様** — 決まっていることを書き下す。実装はしない。仕様が固まったら実装 Issue を起こす。
> **種別: 実装** — コードを書き、「検証方法」で検証してから PR を出す。
> **種別: 環境** — 開発環境・インフラを作る。仕上げに CLAUDE.md / README を更新する。
> **種別: 不具合** — 先に再現することを確認してから直す。
```

## 粒度の目安（1タスク = 1PR）

**1件に収める条件（すべて満たすこと）**

- 完了条件がチェックボックス 3〜5個以内で書ける
- 触る範囲が `frontend/` `backend/` `infra/` の**いずれか1つに収まる**
- 検証手段が1つに定まる（画面が表示される / テストが通る / API が 200 を返す）
- AI の 1〜2 セッションで実装から検証まで到達する見込み（目安: 新規 300 行 / 変更 200 行程度）

**分割の合図**

| 合図 | 分割の仕方 |
|---|---|
| タイトルに「〜と〜」が入る | 2件に割る |
| 未決事項がある（ライブラリ選定・方式選定など） | 「決める」Issue と「作る」Issue に割り、後者の「前提・依存」に前者を書く |
| フロントとバックの両方を触る | API 契約を決める Issue を先に立て、実装は別 Issue にする |
| 完了条件に「〜など」「一通り」が入る | 粒度以前に仕様が未確定。仕様起案の Issue に格下げする |

**細かすぎる合図** — 1ファイル / 1関数単位、「〜を確認する」だけの Issue。検証は実装 Issue の完了条件に含める。

## 未決事項の扱い

未決事項（ライブラリ選定・方式選定・項目定義など）は、**独立した「決める Issue」にするか、実装 Issue の中に残すか**を次で判定する。

| 条件（いずれかに該当） | 扱い |
|---|---|
| **複数の Issue をブロックする** | **独立した「決める Issue」にする**。ブロックされる側の「前提・依存」にその Issue 番号を書く |
| **後から変えるとやり直しコストが高い**（実装の書き直しになる） | 同上 |
| どちらにも該当しない | 独立させず、実装 Issue の「未決事項（事前決定・任意）」に**推奨案付きで**残し、着手時に決める |

**「決める Issue」の完了条件は「決定が記録されたこと」**であり、実装ではない。記録先は ADR（`documents/ADR/`）や検討記録（`documents/00_検討/`）。論点が大きい場合は検討記録を先に作る。

例:
- 「UI ライブラリを Tailwind のみにするか shadcn/ui を足すか」→ 全画面実装をブロックし、後から変えるとコンポーネントの書き直し → **独立 Issue**（[#16](https://github.com/study-basic-hackathon/hanasu/issues/16)）
- 「ログイン後の遷移先パス」→ 何もブロックせず、後から1行変えれば済む → **実装 Issue に推奨案付きで残す**

## 親トラッキング Issue

1 Issue = 1PR に収まらない大きなまとまりは、**親トラッキング Issue** にする。

- 親 Issue は **PR を持たない。** 子 Issue がすべて閉じた時点で閉じる
- **「1タスク = 1PR」の例外であることを本文冒頭に明記する**（読んだ人・AI が混乱しないため）
- 本文に子 Issue のチェックリストを置く
- 階層は原則1段まで。例: [#1 フロントエンドモック作成](https://github.com/study-basic-hackathon/hanasu/issues/1)

## 記法のきまり

- タイトルは `[<領域>]<日本語の要約>`（`frontend` / `backend` / `infra` / `common`）— 現行の運用どおり
- ブランチは `feature/issue-<番号>-<英語スラッグ>`（例: `feature/issue-2-login-page`）
- PR 本文に `Closes #<番号>` を必ず書く
- 完了条件は**観測可能な形**で書く。「ログイン画面ができる」ではなく「`/login` にアクセスするとメール・パスワード入力欄が表示される」
- **リポジトリ内ドキュメントへのリンクは完全 URL で書く。** GitHub の Issue 本文では**相対リンクが機能しない**（Issue はファイルツリー上の位置を持たないため）。`https://github.com/study-basic-hackathon/hanasu/blob/main/<パス>` の形式を使い、日本語ファイル名は URL エンコードする

  ```bash
  # 完全 URL の作り方（パスを渡すとリンクを出力する）
  python3 -c 'import sys,urllib.parse; print("https://github.com/study-basic-hackathon/hanasu/blob/main/" + urllib.parse.quote(sys.argv[1]))' documents/ADR/0004-Nextjsプロジェクト初期構成.md
  ```

## 種別ごとの AI 作業フロー

「Issue #N をやって」と渡されたときに AI がたどる手順。

> 括弧内は Claude Code のスキル名。**スキルは各自の環境にしかないため、無くても手順どおりに進められる形で書いてある。**

### すべての種別に共通

**着手前**

1. `gh issue view <N>` で本文を読み、**完了条件を TodoWrite に展開する**
2. **assignee が自分か確認する。** 他人の Issue には着手しない
3. **「前提・依存」の Issue がすべて閉じているか確認する。** 開いていれば着手せず、その旨を報告して止まる
4. **「未決事項（事前決定・必須）」が残っていないか確認する。** 残っていれば着手せず報告する
5. `feature/issue-<N>-<スラッグ>` でブランチを切る

**完了時**

1. Issue の完了条件を `- [x]` に更新する
2. PR 本文に `Closes #<N>` と**検証結果**（実行したコマンドとその結果）を書く

### 種別: 検討

1. `CLAUDE.md`・関連 ADR・既存コード・公式ドキュメントに接地する。**事実には出典を付け、推測と区別する**
2. `documents/00_検討/` に検討記録を作成する（`YYYYMMDD_<トピック>.md`）（`discuss-proposal`）
3. 選択肢を比較し、ユーザーと議論して決定する。**AI が単独で決めない**
4. `documents/ADR/` に ADR を作成する（`NNNN-<トピック>.md`、連番、1 ADR = 1 決定）（`add-adr`）
5. **この決定にブロックされていた Issue の本文を更新する**（未決事項を消し、決定内容と ADR リンクを反映）← 忘れやすい
6. ドキュメントのみの PR を出す

### 種別: 仕様

1. 依存する ADR・検討記録を読み、決定済みの方針を確認する
2. 仕様ドキュメントを作成する（`add-specification`）
3. ユーザーのレビューを受ける（**コマンドで検証できないため、レビューが唯一の検証手段**）
4. **仕様から実装 Issue を起票する**（`decompose-issue`）← 仕様を書いて終わりにしない
5. ドキュメントのみの PR を出す

### 種別: 実装

1. 適用 ADR と、**既存コードの書き方**（命名・構成・コメントの粒度）を読む
2. 実装する。**「やらないこと」に書かれた範囲に手を出さない**
3. Issue の「検証方法」のコマンドを実行する
4. 完了条件を1つずつ確認する。**満たせない条件があれば、隠さず報告する**
5. PR を出す

### 種別: 環境

1. 対応するスキルがあれば使う（Dev Container → `devcontainer-ai-setup`、Terraform → `iac-development` → `iac-security-check`）
2. 実装する
3. 検証する。**「起動して動く」ことの確認が中心**（`docker compose up` → 応答確認、`terraform plan` が通る）
4. **仕上げに CLAUDE.md / README を更新する。** 共有ファイルでコンフリクトしやすいため、**この Issue の最後にまとめて触る**
5. PR を出す

### 種別: 不具合

1. **再現手順どおりに操作し、再現することを先に確認する。** 再現しなければ、そこで止まって報告する ← ここを飛ばさない
2. 原因を特定し、Issue にコメントで残す
3. 修正する
4. **同じ再現手順で再現しなくなったことを確認する**
5. PR を出す

### 親トラッキング Issue の場合

**実装しない。PR も出さない。** 子 Issue の状態を確認し、次に着手すべき子とブロッカーを報告する。子がすべて閉じたら、親自身を閉じる。

## テンプレート本体（ここから下をコピー）

````markdown
> **種別: <検討 / 仕様 / 実装 / 環境 / 不具合>** — <上記「本文冒頭のバナー」から該当する一文をコピーする>

## 目的

<なぜやるか。1〜2行。AI が実装中の判断に迷ったときの拠り所になる>

## 完了条件

- [ ] <観測可能な形で書く>
- [ ] <3〜5個以内。超えるならタスクを分割する>

## やらないこと

- <このIssueで手を出さない範囲を明示する>

## 触る範囲

- `<ディレクトリ / ファイル>` — frontend / backend / infra のいずれか1つに収める

## 検証方法

```bash
<実行するコマンド>
```

## 前提・依存

- 依存Issue: #<番号>（先に完了している必要がある / なければ「なし」）
- 適用ADR: [ADR-XXXX](<相対パス>)（決定済みの方針。なければ「なし」）

## 未決事項

<未決がなければこのセクションごと削除する>

- 事前決定（必須）: <決めないと着手できない、または後から変えるとやり直しコストが高いもの>
- 事前決定（任意）: <後から変更が容易なもの>（推奨: <デフォルト案>）

## 参考

- [<ドキュメント名>](<リンク>) — <このタスクにどう効くかの一言>
````
