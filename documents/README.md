# ドキュメントの書き方

**`documents/` 配下にドキュメントを追加・更新するときは、本書に従う。** 適用範囲はチーム全体。

決定の根拠は [ADR-0013 ドキュメントの役割と正本の所在](ADR/0013-ドキュメントの役割と正本の所在.md)、検討の経緯は [検討記録: ドキュメント管理方針](00_検討/20260817_ドキュメント管理方針.md) にある。

## 1. 情報の種類ごとの正本

**同じ情報を2箇所に書かない。** 書きたい情報の正本が他にあるなら、そこへリンクするだけにして値を書き写さない。

**原則: 検討記録は、いかなる情報についても正本にならない。**

| 情報の種類 | 正本 | 他の場所での扱い |
|---|---|---|
| 決まっている仕様（何を作るか、どう振る舞うか） | **仕様ドキュメント**（`documents/` 配下） | 参照リンクのみ。値を書き写さない |
| API の一覧と入出力仕様 | **[documents/backend/API仕様.md](backend/API仕様.md)** | [必要api.md](必要api.md) は**必要な API のメモ**であり正本ではない |
| アーキテクチャ上の決定と、その理由・トレードオフ | **ADR**（`documents/ADR/`） | 仕様ドキュメントには**決定の結果**だけを書き、理由は書かない |
| 決定に至る経緯・案の比較・議論 | **検討記録**（`documents/00_検討/`） | **正本にならない。** 仕様は必ず仕様ドキュメントへ書き出す |
| 決定の日付・決定の場（チーム会議など） | **ADR の `日付`** | 仕様ドキュメントに書かない |
| 未確定事項・懸念・宿題 | **GitHub Issue** | 仕様ドキュメントは一覧表を章として持ってよい。ただし詳細・選択肢は Issue 側に置き、決着したら表から消す |
| 進捗・ステータス・優先度 | **GitHub Issue**（open / closed・ラベル・アサイン） | 仕様ドキュメントに書かない |
| 作業ログ・実測結果 | **PR 本文** | 凍結済みの `task-memo/` は記録として保存する（新規作成しない） |
| 変更履歴 | **git** | 仕様ドキュメントに「新旧対応表」「変更点」の節を持たない |

## 2. ドキュメント種別ごとの役割

| 種別 | 置き場所 | 役割 | メタ情報ヘッダ |
|---|---|---|---|
| **仕様ドキュメント** | `documents/` 直下、`documents/<領域>/` | 決まっている仕様を書く | **持たない** |
| **ADR** | `documents/ADR/` | 決定と、その理由・トレードオフを1件ずつ記録する | `ステータス` / `日付` / `被依存` |
| **検討記録** | `documents/00_検討/` | 決定に至る経緯・案の比較を残す | `ステータス` / `区分` / `開始日` / `最終更新` / `関連` |
| **テンプレート** | `documents/template/` | Issue・タスクメモの雛形 | — |
| **タスクメモ** | `documents/task-memo/` | **凍結済み。** 過去の作業記録として保存する（新規作成しない） | — |

### 仕様ドキュメント

**冒頭のメタ情報ヘッダを持たない。** ステータス・対象・作成日・最終更新・対応 Issue のいずれも置かず、タイトルの直下から本文を始める。手で更新する項目を持たないことで、記載が腐るのを防ぐ。関連ドキュメントへのリンクは、本文の該当箇所か末尾の「参考」節で示す。

### ADR

**1 ADR = 1 決定。** `ステータス` は `決定` / `廃止（ADR-NNNN で置き換え）`。`日付` は**決定の日付の正本**であり、仕様ドキュメントから日付を外せるのは ADR が持っているためである。構成は [ADR-0001](ADR/0001-フロントエンド実行環境.md) を雛形とする。

### 検討記録

`ステータス` は次の3語のみを使う。**表すのは議論そのものの状態だけである。** ADR 化・仕様への反映・実装が残っていても `完了` としてよく、**それらの残作業は検討記録では管理しない**（正本表のとおり Issue が持つ）。

| ステータス | 意味 |
|---|---|
| `検討中` | 議論の途中 |
| `完了` | 議論が終わり、結論が出た |
| `中断` | 結論に達しないまま止めた（残論点と再開に必要な情報を残す） |

結論が出た検討記録の冒頭には、昇格先と仕様の正本を明示する。

```markdown
- ステータス: 完了
- **昇格先**: [ADR-000X <トピック>](../ADR/000X-<トピック>.md) — 決定内容はこちらが正本
- **仕様の正本**: [<仕様ドキュメント名>](../<領域>/<ファイル名>.md) — 現行仕様はこちらを見る。本記録は決定に至る経緯であり、現行仕様ではない
```

## 3. 仕様ドキュメントに書かないことの基準

**判断基準: その記述を消したとき、作るものが分からなくなるなら仕様。作業の進め方が分からなくなるだけなら仕様ではない。**

| | 例 |
|---|---|
| **書かない** | 決定の日付と場（「2026-08-16 のチーム会議で決定した」）/ 変更の経緯（「当初は将来対応としていた」）/ 選定理由・却下した案（「〜にした理由」）/ 実装の優先度・進捗（「最優先で作る」「実装済み」）/ 解決済みの論点 |
| **書く** | 実装範囲（作る / 作らない / モックのみ）/ 仕様そのもの / 用語定義 |

**未確定事項は章として一覧表を持ってよい。** ドキュメント単体で「何が未確定か」を通読できるようにするため。ただし次の2つを守る。

1. **表の正本は GitHub Issue。** 詳細な選択肢・比較・推奨案は Issue 側に書き、表に書き足さない
2. **決着したら表から消す。** 「解決済みの論点」として残さない

## 4. ディレクトリ構成

```
documents/
├── README.md              本書（ドキュメントの書き方）
├── <全体共通の仕様>.md      サービス全体にかかる仕様
├── <領域>/                領域固有の仕様（例: backend/、frontend/01_design/）
├── ADR/                   確定した意思決定
├── 00_検討/                検討記録
├── task-memo/             凍結済みの作業記録
└── template/              Issue・タスクメモの雛形
```

- **全体共通の仕様は `documents/` 直下、領域固有の仕様は `documents/<領域>/` に置く**
- **既存ファイルは動かさない。** 参照元の一斉更新が必要になり、リンク切れの原因になるため
- `documents/frontend/01_design/` を正式な置き場所とし、**実体のない `02_spec` は作らない**

## 5. 命名規則

- **ファイル名にスペースを使わない**（参照側で `<>` 囲みや URL エンコードが必要になるため）。**日本語のファイル名は許容する**
- ADR は `NNNN-<トピック>.md`（連番）
- 検討記録は `YYYYMMDD_<トピック>.md`
- **ADR の番号は、起票の直前に main を確認して採る。** 並行するブランチが同じ番号を取ると衝突する

## 6. リンクの書き方

- **リポジトリ内のドキュメント同士は相対リンクで結ぶ**
- **GitHub の Issue 本文では相対リンクが機能しない。** Issue から参照するときは `https://github.com/study-basic-hackathon/hanasu/blob/main/...` の完全 URL を使い、日本語ファイル名は URL エンコードする
- 正本ではないドキュメントから正本を指すときは、**「〜が正本」の一言を添える**
