# ADR-0012: ドキュメントの正本を情報の種類ごとに定め、仕様書には決定の結果だけを書く

- ステータス: 決定
- 日付: 2026-08-17
- 被依存: [#44](https://github.com/study-basic-hackathon/hanasu/issues/44) ドキュメント管理ルールを決める、および本決定にもとづく是正 Issue（検討記録の「是正計画」A〜E）

## コンテキスト(背景と課題)

仕様ドキュメントに、仕様以外の情報が混ざっている。

- **決定の日付と場** — [ユースケース・ユーザーフロー.md](../ユースケース・ユーザーフロー.md) 2.2「2026-08-16 のチーム会議で、期間内に作る範囲を次のとおり決定した」
- **変更の経緯** — 同「当初は将来対応としていたが、今回作ることにした」が**4箇所に重複**
- **選定理由** — 同「チュートリアルをこの形にした理由」「プロフィールを分けない理由」
- **実装の優先度・進捗** — 同「最優先で作り上げる」、[必要api .md](<../必要api .md>)「**実装済み**」「※実装最優先」
- **未確定事項と担当 Issue の割り当て** — 同 1章「本書で決めないこと」表、8章「未確定事項」表

同時に、**同じ情報の正本が複数箇所に割れている**。評価指標は ADR-0009 / 必要api / ユースケース2箇所 / 検討記録の**4箇所**にあり、技術スタックは [技術スタック.md](../技術スタック.md) と [CLAUDE.md](../../CLAUDE.md) の2箇所にあって**既に食い違っている**（[#41](https://github.com/study-basic-hackathon/hanasu/issues/41)）。**API の入出力仕様に至っては、1546 行の検討記録 [20260816_会話セッションAPI構成.md](../00_検討/20260816_会話セッションAPI構成.md) 1.3 が事実上の正本になっていた。**

[ADR 0001〜0011](.) と検討記録の2層は機能しているが、**「どの情報がどこにあるべきか」を定めた文書は存在しない**。[CLAUDE.md](../../CLAUDE.md) の「規約」節は検討記録と ADR の置き場所だけを定めており、仕様ドキュメントの規約はない。ルールがないまま同じ書式が未マージの PR [#31](https://github.com/study-basic-hackathon/hanasu/pull/31) / [#32](https://github.com/study-basic-hackathon/hanasu/pull/32) にも横展開されている。

## 決定

### 1. 情報の種類ごとに正本を1箇所に定める

**原則: 検討記録は、いかなる情報についても正本にならない。**

| 情報の種類 | 正本 |
|---|---|
| 決まっている仕様 | **仕様ドキュメント**（`documents/` 配下） |
| API の一覧と入出力仕様 | **`documents/backend/API仕様.md`**（新設）。[必要api .md](<../必要api .md>) はメモであり正本ではない |
| 決定と、その理由・トレードオフ | **ADR** |
| 決定の日付・決定の場 | **ADR の `日付`** |
| 決定に至る経緯・案の比較 | **検討記録**（`documents/00_検討/`） |
| 未確定事項・懸念・宿題 | **GitHub Issue** |
| 進捗・ステータス・優先度 | **GitHub Issue**（open/closed・ラベル・アサイン） |
| 作業ログ・実測結果 | **PR 本文** |
| 変更履歴 | **git** |

### 2. 仕様ドキュメントには「決定の結果」だけを書く

**判断基準: その記述を消したとき、作るものが分からなくなるなら仕様。作業の進め方が分からなくなるだけなら仕様ではない。**

- **書かない**: 決定の日付と場 / 変更の経緯 / 選定理由・却下した案 / 実装の優先度・進捗 / 解決済みの論点
- **書く**: 実装範囲（作る / 作らない / モックのみ）/ 仕様そのもの / 用語定義
- **未確定事項は章として一覧表を持ってよい。** ただし正本は Issue であり、詳細な選択肢・比較は Issue 側に置く。**決着したら表から消す**
- **冒頭のメタ情報ヘッダを持たない**（ステータス・対象・作成日・最終更新・対応 Issue のいずれも置かない）。関連リンクは本文か末尾の「参考」節で示す

**ADR と検討記録はメタ情報を維持する** — ADR の `日付` は決定日の正本であり、検討記録の `ステータス` は再開判断に使うため。

### 3. 配置と命名

- 全体共通の仕様は `documents/` 直下、領域固有の仕様は `documents/<領域>/`
- `documents/frontend/01_design/` を正式な置き場所とし、**実体のない `02_spec` は作らない**
- **ファイル名にスペースを使わない。** 日本語ファイル名は許容する
- ADR は `NNNN-<トピック>.md`、検討記録は `YYYYMMDD_<トピック>.md`（現行どおり）

### 4. ルールの置き場所と適用範囲

- ルール本体は **`documents/README.md`** に置く。[CLAUDE.md](../../CLAUDE.md) には「ドキュメントを追加・更新するときは `documents/README.md` に従う」の**1行だけ**を置く
- **適用範囲はチーム全体**

## 検討した選択肢

- 未確定事項の扱い: A案 完全に Issue へ移す / B案 事実とリンクだけ残す / **C案 章として一覧表を持つ（採用）**
- 仕様書の線引き: A案 完全排除 / **B案 結果は書き過程は書かない（採用）** / C案 末尾に経緯節としてまとめる
- API 仕様の正本: X案 必要api .md / Y案 検討記録 / Z案 両方に書く / **W案 仕様ファイルを新設（採用）**
- 検討記録の扱い: A案 仕様を仕様書へ移す / B案 結論だけに縮約 / **C案 現状のまま動かさない（採用）**
- ディレクトリ: **A案 領域別を正式化（採用）** / B案 `documents/spec/` へ集約 / C案 現状維持
- ルールの置き場所: A案 issue-template.md / **B案 `documents/README.md` 新設（採用）** / C案 CLAUDE.md 本体

## 決定要因

- **正本が1箇所であること**（同じ情報を2箇所に持たない）
- **各ドキュメントが自分の役割だけを果たすこと**（仕様書を読みやすくする）
- **手で更新する項目を増やさないこと**（メタ情報・Issue 番号は放置すると腐る）
- **既存ファイルを動かさずに済むこと**（ハッカソン期間中のリンク切れリスクを避ける）
- **既に機能している ADR / 検討記録の2層を壊さないこと**

## 理由

- **検討記録を正本にしない**: 検討記録は「検討の記録」であり、そこを参照させると仕様を探す場所が定まらない。現に API 仕様が 1546 行の記録の中にあり、実装者が読む場所として機能していなかった。
- **仕様書から過程を外す**: 「いつ・誰が・どの順で作業するか」は Issue と git が持つ情報であり、仕様書に置くと更新されずに腐る。実際に「最終更新: 2026-08-16（チーム会議での決定を反映）」のようにメタ情報の欄が決定ログ化していた。
- **未確定事項の表は残す**: ドキュメント単体で「何が未確定か」を通読できないと、読み手が未確定部分を確定仕様と誤読する。詳細を Issue に寄せることで、分散は防ぎつつ誤読も防げる。
- **メタ情報を全廃する（仕様書のみ）**: 一部だけ残しても手で更新する項目が残る限り腐る。git と GitHub が持つ情報を書き写さない。
- **既存ファイルを動かさない**: `documents/spec/` への集約は構成として綺麗だが、参照元の一斉更新が要る。得られる利得よりリンク切れのリスクが上回る。
- **ルールを `documents/README.md` に置く**: CLAUDE.md に書くと肥大し、複数 PR が同時に触って衝突する（[20260808 の検討](../00_検討/20260808_AI向けタスク運用方針.md) 論点4で「共有ファイルは仕上げでのみ触る」と決めている）。

## 影響・トレードオフ

- 良い影響:
  - **仕様書を読む人が、決定の経緯を読み飛ばさずに済む**（そもそも書かれていない）
  - 同じ情報を2箇所に書かないため、**片方だけ直して食い違う事故が起きない**
  - メタ情報を持たないため、**更新漏れによる嘘の日付・ステータスが生じない**
- 受け入れたトレードオフ・残るリスク:
  - **仕様書から「いつ決まったか」が直接読めなくなる。** ADR を辿る必要がある
  - **仕様書に確定 / ドラフトの区別が付かなくなる**（メタ情報のステータスを廃止したため）
  - **未確定事項の表と Issue の同期は手作業。** 決着後に表から消す運用が守られないと腐る
  - **API 仕様は検討記録から書き出すため、一時的に内容が二重に存在する。** 書き出し後、検討記録側には「正本はこちら」の注記を付けるが、記録本体は残る
  - **適用範囲がチーム全体のため、周知しなければ従来の書き方が混ざり続ける**
