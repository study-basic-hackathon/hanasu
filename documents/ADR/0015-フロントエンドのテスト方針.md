# ADR-0015: フロントエンドのUT・コンポーネントテストにVitestとReact Testing Libraryを採用し、E2EにPlaywrightを使う

- ステータス: 決定
- 日付: 2026-08-22
- 依存:
  - [ADR-0004 Next.jsプロジェクト初期構成](0004-Nextjsプロジェクト初期構成.md) — Next.js 16.3 / App Router / TypeScript の構成を前提とする
  - [ADR-0006 開発用Dockerベースイメージ](0006-開発用Dockerベースイメージ.md) — ローカルの UT・コンポーネントテストを Docker で実行する前提とする
- 被依存: [#88](https://github.com/study-basic-hackathon/hanasu/issues/88) フロントエンドのUT基盤と主要モジュールのテストを実装する

## コンテキスト(背景と課題)

フロントエンドにはテストツール・テストスクリプト・テストコードがなく、共通ロジックや UI の変更による退行を自動検出できない。Next.js 16.3 / React 19.2.8 / TypeScript の App Router 構成で、UT、コンポーネントテスト、E2E の役割と実行環境を先に固定する必要がある。

また、動的パラメータを受け取る async Server Component のページが存在する。Next.js の公式ガイドでは Vitest / Jest は async Server Component をサポートせず、E2E テストを推奨しているため、UT 用ランナーだけでは画面遷移を含む動作を保証できない。

## 決定

| テストレベル | 採用するツール | 対象・責任範囲 |
|---|---|---|
| UT | **Vitest** | `frontend/src/lib/` の純粋関数、データ変換、境界値、バリデーションなどを隔離して検証する |
| コンポーネントテスト | **Vitest + React Testing Library** | UI 部品と Client Component の表示、props、ユーザー操作、入力エラーを DOM 上で検証する |
| E2E | **Playwright** | async Server Component、ページ遷移、主要な利用者フローを実ブラウザで検証する |

- **Jest は導入しない。** Vitest と Jest は同じテストランナーの役割を担うため、二重に使わない。
- React Testing Library はテストランナーではなく、Vitest 上で React の画面部品を利用者に近い形で検証するためのライブラリとして使う。
- UT・コンポーネントテストは既存の `web` サービス内で実行する。E2E はブラウザと OS 依存を含むため、`web` サービスには同居させず、Playwright 用の Docker 実行環境を使う。
- 初回はカバレッジレポートを出力するだけとし、閾値による CI 失敗は設けない。対象と実測値を確認してから、必要なら別 Issue で閾値を決める。

## 実行コマンド

後続の実装 Issue で、次の npm スクリプトと Docker 実行環境を整備する。

| 用途 | npm スクリプト | Docker ローカル | 将来の CI |
|---|---|---|---|
| UT・コンポーネントテスト（開発時） | `npm run test` | `docker compose run --rm web npm run test` | 使用しない |
| UT・コンポーネントテスト（単発実行） | `npm run test:run` | `docker compose run --rm web npm run test:run` | `npm run test:run` |
| カバレッジレポート | `npm run test:coverage` | `docker compose run --rm web npm run test:coverage` | レポートの出力のみ。閾値では失敗させない |
| E2E | `npm run test:e2e` | `docker compose up -d web` の後に `docker compose run --rm e2e npm run test:e2e` | `npm run build` / `npm run start` と Playwright ブラウザ依存の準備後に `npm run test:e2e` |

`e2e` サービスは Playwright のバージョンとブラウザイメージのバージョンを一致させ、`web` サービスを対象に実行する。Playwright の E2E 実装は #88 の対象外とし、別の実装 Issue で行う。

## 検討した選択肢

- UT ランナー: **Vitest（採用）** / Jest
- コンポーネントテスト: **React Testing Library を Vitest と組み合わせる（採用）** / テストランナーのみで検証する
- E2E: **Playwright を導入する（採用）** / UT・コンポーネントテストだけで開始し、E2E は後回しにする
- カバレッジ: **レポートのみで開始する（採用）** / 初回から閾値を CI の失敗条件にする

## 決定要因

- Next.js 16.3 の公式手順があり、同期の関数・Client Component を検証できること
- async Server Component と実際のページ遷移を自動検証できること
- Docker ローカル環境と将来の CI で同じコマンド体系を使えること
- 初期導入で不確かなカバレッジ閾値を強制せず、後続の実装を妨げないこと

## 理由

- **Vitest を採用する**: Next.js の公式ガイドに Next.js 向けの設定手順があり、React Testing Library と組み合わせた UT・コンポーネントテストの手順が示されている。`vitest run` により、CI 用に監視なしの単発実行もできる。
- **React Testing Library を併用する**: React の DOM を利用者に近い方法で操作・検証できる。ランナーの Vitest と役割が重ならず、表示・入力・クリックなどの UI の退行を検出できる。
- **Jest を見送る**: Next.js の `next/jest` による公式対応はあるが、Vitest と同じランナーの役割である。2つのランナーを併用する理由がなく、設定・記法・保守対象を増やすだけになる。
- **Playwright を採用する**: Next.js の公式ガイドは async Server Component を E2E で検証するよう案内している。実ブラウザでサインイン、企業情報の登録・編集、練習・面接・評価などの主要フローを確認できる。
- **カバレッジ閾値を設けない**: テストが存在しない状態では妥当な基準値がない。まずレポートで対象と実測値を把握し、必要なら次の判断で閾値を設ける。

## 影響・トレードオフ

- 良い影響:
  - UT と UI 操作のテストを役割分担して追加でき、既存ロジック・主要 UI の退行を自動検出できる
  - async Server Component と画面をまたぐ利用者フローも E2E の対象として明確になる
  - `test` / `test:run` / `test:coverage` / `test:e2e` のコマンド体系をローカルと CI で共通化できる
- 受け入れたトレードオフ・残るリスク:
  - Vitest / Jest のいずれでも async Server Component は UT・コンポーネントテストの対象にできないため、E2E テストの整備が別途必要になる
  - Playwright はブラウザバイナリと OS 依存を必要とし、専用 Docker 実行環境の整備・維持コストが増える
  - カバレッジ閾値がない間は、カバレッジ低下だけでは CI を失敗にできない

## フォローアップ

- **[#88](https://github.com/study-basic-hackathon/hanasu/issues/88) で実装する**: Vitest、React Testing Library、設定ファイル、UT とコンポーネントテスト、`test` / `test:run` / `test:coverage` を導入する。Playwright の E2E 実装は #88 に含めない。
- Playwright の `e2e` サービス、E2E シナリオ、CI 実行は別の実装 Issue で扱う。実装時は Playwright パッケージと Docker イメージのバージョンを一致させる。
- カバレッジ閾値の再検討トリガー: #88 のテスト追加後にレポートの対象・実測値が得られ、CI の失敗条件にできる基準をチームが合意できたとき。
