# ADR-0007: 会話音声はブラウザで取得してターンごとに送信し、サーバーに永続化しない

- ステータス: 決定
- 日付: 2026-08-16
- 被依存: **本 ADR には会話機能の各 ADR が依存する。本 ADR が覆る（Chime SDK を使う / 音声を保存する）場合は、以下も再検討が必要。**
  - [ADR-0008](0008-会話用APIの構成.md)（会話用 API の構成）— 音声をターンごとに送ることが前提
  - [ADR-0009](0009-評価方式.md)（評価方式）— 音声を保存しないため、評価はセッション中に蓄積した値で行う

## コンテキスト(背景と課題)

hanasu の中核である会話練習機能について、音声をどう取得し・どう送り・どこに保持するかが未決だった。[必要api .md](../必要api%20.md) の「会話用API」は `TODO：調べる` のままで、会話画面（[#27](https://github.com/study-basic-hackathon/hanasu/issues/27) / [#9](https://github.com/study-basic-hackathon/hanasu/issues/9)）もバックエンド実装も着手できない状態だった。

[技術スタック.md](../技術スタック.md) には AWS Chime SDK を利用する想定が書かれており、[#29 Chime SDK基盤の構築](https://github.com/study-basic-hackathon/hanasu/issues/29) も起票済み。一方で同ファイルには **S3 は「現状想定では使わない」**（音声データの置き場として）とあり、音声の扱いに関する前提が固まっていなかった。

会話相手が AI であることは 2026-08-15 にチームで決定済み。ハッカソン期間内に動かすことを最優先とし、比較軸は**「既存実装への乗せやすさ」1本**に絞ることでユーザーと合意した。

## 決定

- **音声取得はブラウザの `MediaRecorder`** を使う。**Chime SDK は使わない。**
- **発話終了の検出は VAD（無音判定の閾値 2〜3秒）と手動停止ボタンを併用**する。VAD による自動停止の実装自体は優先度低とする。
- **音声はターンごとに `multipart/form-data` でサーバーへ送る。**
- **音声はクライアントの IndexedDB に一時保持し、サーバーは処理後に破棄する。永続化しない。**
- **OpenAI Realtime API（speech-to-speech）は使わない。**

## 検討した選択肢

- A案: ブラウザの `MediaRecorder` + ターンごと送信（**採用**）
- B案: 音声はブラウザが保持し、セッション終了時に一括送信
- C案: Amazon Chime SDK
- D案: OpenAI Realtime API

## 決定要因

- 既存実装（FastAPI + JWT）への乗せやすさ（**ユーザーと合意した唯一の比較軸**）
- インフラの新規構築が必要か
- [技術スタック.md](../技術スタック.md) の「S3 は使わない」前提を維持できるか
- 話し方分析（話速・フィラー）に必要な音声が取れるか

## 理由

- **A案を採用**: 追加のインフラを必要とせず、既存の FastAPI にそのまま乗る。`python-multipart` が既に `backend/pyproject.toml` の依存に入っており、ファイルアップロードを受ける下地がある。
- **B案を見送り**: 会話中の文字起こしをブラウザ側（Web Speech API 等）に頼ることになり、**精度と対応ブラウザが読めない**。
- **C案 Chime SDK を見送り**: 本質は「複数人の人間をリアルタイムに繋ぐ SFU」であり、**1対1かつ相手が AI の今回は代替不能な機能が1つもない**。エコーキャンセル・ノイズ抑制は `getUserMedia` のオプションで足りる。決定的な問題として、**面接官 AI をアテンディーとして参加させるには ECS 上にヘッドレスクライアントを常駐させる必要**があり、HTTP POST 1本で済む処理をサーバー常駐プロセス + WebRTC トラック操作に置き換えることになる。
- **D案 Realtime API を見送り**: **音声はテキストの約10倍のトークンを消費**するため、`gpt-realtime` の 32,768 トークン窓では15〜20分程度の面接で上限に達しうる。上限超過時はプレフィックスが変わりキャッシュも壊れる。
- **音声を永続化しない**: 過去セッションの再評価は**優先度が低い**とユーザーが判断したため。保存しないことで [技術スタック.md](../技術スタック.md) の「S3 は使わない」前提をそのまま維持できる。

## 影響・トレードオフ

- 良い影響:
  - **S3 が不要**。技術スタックの前提を変更せずに済む
  - **[#29 Chime SDK基盤の構築](https://github.com/study-basic-hackathon/hanasu/issues/29) が不要**になる（チーム確認済み）
  - 音声の受け口が `multipart/form-data` だけで済み、既存の FastAPI に素直に乗る
  - VAD の無音区間データは「間の長さ」指標にそのまま使える
- 受け入れたトレードオフ・残るリスク:
  - **過去セッションの再評価ができない。** 評価ロジックを改善しても過去分には適用できない
  - **セッション途中のリロード・タブクローズで会話が失われる**（IndexedDB への保存で軽減する）
  - 面接練習は考え込む間が長いため、**VAD の閾値を一般的な 800ms ではなく 2〜3秒**にする必要がある。誤検知で発話が途中で切れるリスクは残る

## フォローアップ

- **[#29 Chime SDK基盤の構築](https://github.com/study-basic-hackathon/hanasu/issues/29) の扱いを決める**（不要でチーム合意済み。Issue のクローズ判断は担当者）
- [技術スタック.md](../技術スタック.md) の Chime SDK に関する記載を見直す
- フロント側で MediaRecorder / VAD / IndexedDB を実装する
- 再検討のトリガー: **グループディスカッション練習への拡張**（複数人同時参加になると自前 WebRTC は破綻するため Chime SDK が有力）、または**「人間の面接官 × AI 評価」構成**（AI が参加者ではなく観測者になるため常駐プロセス問題が消える）
