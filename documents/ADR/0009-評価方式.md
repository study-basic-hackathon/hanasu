# ADR-0009: 評価は定量をクライアントで算出し、定性のみ LLM に任せる

- ステータス: 決定
- 日付: 2026-08-16
- 依存: [ADR-0007](0007-会話音声の取得と保存方式.md)（音声を永続化しない）、[ADR-0008](0008-会話用APIの構成.md)（API の構成と非同期評価）

## コンテキスト(背景と課題)

hanasu は会話を録音・文字起こしし、**話し方を分析して評価とアドバイスを返す**ことがサービスの核となる。しかし評価指標そのものが資料間で食い違っていた。

- [必要api .md](../必要api.md): 抑揚・フィラー・声の大きさ・スピード
- 外部で作成された設計メモ: 話速・文章の構成・話の内容・フィラー数

**共通しているのは話速とフィラーだけ**であり、どの指標を採るかを決めないと、音声からどんなデータを取ればよいかも決まらない状態だった。あわせて、指標を誰が算出するか（サーバー / クライアント）も未決だった。

## 決定

- **評価指標は次の3つとする。** ①話の速さ ②フィラーの数 ③構成・内容。**「間の長さ」は優先度「できたら」**として任意で加える。**「抑揚」「声の大きさ」は採らない。**
- **定量はコード、定性は LLM で評価する。** 数値は LLM に渡すが**採点はさせない**。
- **定量指標（話速・フィラー数・間）はクライアントが算出**し、`POST /evaluations` に `scores` として渡す。**DB に保存するだけで LLM には渡さない。**
- **話速は「文字数 ÷ 発話時間」で算出する。** モーラ数（形態素解析）は使わない。
- **DB に残すのは評価結果のみ。** 会話履歴・音声・transcript・会話サマリは保存しない。
- **評価結果テーブルの主キーは `evaluation_id` 単体**とし、`company_id` は FK + インデックスとする。**`session_id` は持たない。**

## 検討した選択肢

- 評価の方式
  - A案: 全指標を LLM に採点させる
  - B案: 定量はコードで算出し、定性のみ LLM（**採用**）
- 定量指標の算出場所
  - サーバー（ブラウザは発話時間だけ送る）
  - クライアント（**採用**）
- 話速の単位
  - 文字数 ÷ 発話時間（**採用**）
  - モーラ数 ÷ 発話時間（形態素解析が必要）

## 決定要因

- 評価結果の再現性（同じ会話で点数がブレないか）
- 依存ライブラリを増やさずに済むか
- ECS のリソース制約（CPU 256 / メモリ 512MB）
- 音声入力とテキスト入力が混在しても破綻しないか

## 理由

- **B案（定量はコード、定性は LLM）を採用**: 全部 LLM に投げると**同じ会話でも点数がブレ、ユーザーが納得しない**。話速・フィラー数は機械的に数えられるため、コードで算出すれば**同じ会話なら必ず同じ値になる**。
- **クライアント算出を採用**: ① `POST /interviews/stt` が「音声 → テキスト」の純粋な変換 API になり、[ADR-0008](0008-会話用APIの構成.md) で API を分割した意図と整合する。②**テキスト入力のターンでは話速もフィラーも原理的に測れない**ため、指標が取れるターンと取れないターンの管理はクライアントが持つほうが素直。
- **モーラ数を不採用**: 漢字比率による文字数のブレを排除できる利点はあるが、**読み仮名の取得に形態素解析（kuromoji.js / Sudachi 等）が必要**になる。文字数ベースでも目安値が存在し（アナウンサー約300〜350、日常会話250〜300文字/分）、面接の回答は漢字とかなが混ざるため極端にはブレない。**この判断により形態素解析がサーバー・クライアントのいずれからも不要になった。**
- **抑揚・声の大きさを不採用**: 抑揚の評価には**ピッチ（基本周波数）抽出**が必要で、サーバーで行うなら現在の ECS（CPU 256 / メモリ 512MB）では負荷が厳しい。加えて**「抑揚が良い / 悪い」の判定基準を作ることが難しい**。
- **DB に評価結果のみを残す**: [ADR-0007](0007-会話音声の取得と保存方式.md) で音声も transcript も保存しないと決めたため。会話サマリも含めない。
- **主キーを `evaluation_id` 単体とする**: `GET /evaluations/{evaluation_id}` で引く以上、**これ単体で一意に特定できる必要がある**。`session_id` は1セッション = 1評価のため `evaluation_id` と 1:1 になり、概念が重複する。

## 影響・トレードオフ

- 良い影響:
  - **定量スコアの再現性が保証される**（同じ会話なら必ず同じ値）
  - **形態素解析ライブラリが不要**になり、ECS のメモリを圧迫する懸念も消えた
  - `POST /interviews/stt` の責務が「音声 → テキスト」に収まる
  - DB に残すのが評価結果だけになり、テーブルが1つで済む
- 受け入れたトレードオフ・残るリスク:
  - **点数化の基準（「284文字/分は何点か」）がフロント側に置かれる。** 定量部分はフロント、定性部分はサーバー（プロンプト設計）と分担が分かれる
  - 漢字比率により**話速の値が実際の発話速度から多少ずれる**
  - **抑揚・声の大きさを評価しないため、[必要api .md](../必要api.md) の記載と実態が食い違う**（同ファイルの更新が必要）
  - 音声を保存しないため、**評価ロジックを改善しても過去セッションに適用できない**

## フォローアップ

- **評価の点数化ロジックを決める**（「284文字/分は何点か」の基準、`structure_content` を LLM にどう評価させるか）— **実装時に検討する**
- [必要api .md](../必要api.md) の「音声分析: 抑揚・フィーラー・声の大きさ・スピード」を実態に合わせて更新する
- フィラーの定義範囲（「なんか」「まあ」等を含めるか）を、AmiVoice の実装後に確かめて決める
- 「間の長さ」を実装する場合は、VAD の区間記録から算出して `scores` に `pause` を足す
- 再検討のトリガー: **抑揚や声の大きさを評価対象に戻す**場合、**過去セッションの再評価が必要になった**場合（音声・transcript の保存が前提になる）
