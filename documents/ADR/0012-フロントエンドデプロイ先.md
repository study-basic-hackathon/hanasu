# ADR-0012: フロントエンドのデプロイ先を AWS Amplify Hosting とする(ADR-0001 を置き換え)

- ステータス: 決定
- 日付: 2026-08-17
- 置き換え: **[ADR-0001](0001-フロントエンド実行環境.md)(デプロイ先を Vercel とする)を置き換える。** ADR-0001 のステータスは「ADR-0012 により置き換え」に更新済み。
- 被依存:
  - **[ADR-0002](0002-Nodeバージョン.md)〜[ADR-0006](0006-開発用Dockerベースイメージ.md) は ADR-0001 に依存していたため、本 ADR で再検討した。** 結果は下記「ADR-0002〜0006 の再検討結果」を参照。各 ADR の本文は本 ADR では書き換えない(改訂が必要なものは別 Issue で扱う)。
  - [#19](https://github.com/study-basic-hackathon/hanasu/issues/19) Amplify Hosting へのデプロイ設定(本 ADR が前提を与える構築 Issue)

## コンテキスト(背景と課題)

[ADR-0001](0001-フロントエンド実行環境.md) では、ECS (Fargate) / Amplify Hosting / Vercel の3案から **Vercel** を選んでいた。決め手は「Vercel を使って簡単にデプロイする」というチーム方針であり、[検討記録](../00_検討/20260804_フロントエンド実行環境.md) の比較では**コスト軸で Amplify(B案)が最優位**と評価され推奨されていたものを、方針を優先して見送った形だった。ADR-0001 は残るリスクとして「Vercel Hobby プランは個人・非商用利用限定で、会社ドメインでの利用が規約に収まるかは未確認」を挙げ、**再検討のトリガーとして「Hobby の非商用制約に抵触すると判明した場合(Pro 化または B案 Amplify を再検討)」「フロントも AWS 内完結が要件になった場合」**を明記していた。

その後チームの話し合いで、フロントエンドのデプロイ先を **AWS Amplify Hosting に変更する**ことが決まった([#18](https://github.com/study-basic-hackathon/hanasu/issues/18) の起票時点、2026-08-08)。ADR-0001 は「本 ADR が覆る場合は ADR-0002〜0006 もすべて再検討が必要」と定めているため、本 ADR ではその再検討結果までを示し、後続の構築作業([#19](https://github.com/study-basic-hackathon/hanasu/issues/19))の前提を確定させる。

なお本 ADR は決定の記録であり、Amplify Hosting の実構築(アカウント設定・リポジトリ連携・`amplify.yml` の追加)は #19 で行う。

## 決定

フロントエンド(Next.js)の本番デプロイ先は **AWS Amplify Hosting** とする。ローカル開発は従来どおり Docker 上で `next dev` を実行する(変更なし)。

## 検討した選択肢

ADR-0001 と同じ3案。今回は ADR-0001 で見送った B案への切り替えである。

- A案: ECS (Fargate)
- B案: Amplify Hosting
- C案: Vercel(ADR-0001 の決定)

## 決定要因

- コスト(検討記録での重視軸)
- Vercel Hobby プランの非商用制約という未解消リスクの扱い
- AWS 内完結(バックエンドとプラットフォームを一元管理できるか)
- 構築の速さ・簡単さ(ハッカソン期間内に確実に動かす)
- 既存 ADR(0002〜0006)への波及の小ささ

## 理由

- **B案 Amplify Hosting を採用**: 検討記録の比較表のとおり、ハッカソン規模なら**無料枠内でほぼ $0** とコスト軸で最優位。Git リポジトリ連携で CI/CD 込みの自動デプロイが得られるため構築の手間も小さく、ECS のような常時課金・消し忘れリスクもない。バックエンド(FastAPI / ECS)と同じ AWS 内に収まり、プラットフォームが分かれる問題も解消する。
- **C案 Vercel を見送り**: 機能面(Next.js との相性)では最良だが、**Hobby プランの非商用限定という規約リスクが ADR-0001 の時点から未確認のまま残っていた**。Pro($20/ユーザー/月)にすればリスクは消えるが、コスト軸で B案に明確に劣る。
- **A案 ECS (Fargate) を見送り**: 理由は ADR-0001 から変わらない。月 $25〜40 程度の常時課金と、Dockerfile / ECR / ALB / パイプラインの構築の手間がハッカソン期間には重い。

### ADR-0002(Node バージョン) — 一部変更

- **維持する部分**: Node.js を **24.x** とする決定は維持する。選定理由は「Node 20 は EOL 済み・22 も Active LTS 終了・**Active LTS は 24.x のみ**」という Node.js 本体のサポート期間にもとづくもので、デプロイ先には依存しない。
- **変更する部分**: **バージョン固定の「正」を `package.json` の `engines.node` とする根拠は失効する。** `engines.node` は「Vercel が読む固定方法」として選ばれていたが、**Amplify のビルド環境がこれを読むという記載は AWS 公式ドキュメントにない**。Amplify が案内している Node バージョンの指定方法は次の2つである。
  1. Amplify コンソールの**ライブパッケージ更新**(内部で NVM を使い、各ビルドの前に Node.js のバージョンを変更する)。`latest` ではなく `24` のように具体的なバージョンを指定する必要がある
  2. ビルド設定(`amplify.yml`)の `preBuild` で `nvm install` / `nvm use` を実行する
- **加えて失効する根拠**: 「Vercel の新規プロジェクトのデフォルトが 24.x なので設定を触り忘れても食い違わない」という論拠も使えない。Amplify の既定ビルドイメージ(Amazon Linux 2023)のプリインストール版は 24.x とは限らないため、**明示指定を省略できない**。
- **本 ADR での扱い**: `package.json` の `engines.node: "24.x"` は**削除しない**(ローカル/Docker 側の宣言として有効)。Amplify 側は上記いずれかの方法で 24.x を明示指定し、**初回ビルドのログで実際に使われた Node バージョンが 24.x であることを実測して確定する**(#19)。ADR-0002 の改訂は [#42](https://github.com/study-basic-hackathon/hanasu/issues/42) で扱う。

### ADR-0003(パッケージマネージャ) — 維持(根拠の差し替え)

- 結論(**npm**)は維持する。
- 判断軸だった「Vercel が lockfile からパッケージマネージャを自動検出する」は、「**Amplify も `package.json` を検査してフレームワークとビルド設定を自動検出し、Next.js アプリ向けに生成される既定のビルド設定は `npm ci` を使う**」に読み替える。`package-lock.json` を必ずコミットする運用も変わらない。
- npm を選んだもう一方の根拠(node 公式イメージに同梱されており Docker 側の準備が不要、`node_modules` を named volume に分離する構成と相性が良い)は、デプロイ先に依存しないためそのまま有効。

### ADR-0004(Next.js 初期構成) — 維持(新たなリスクあり)

- 初期構成そのもの(Next.js 16.3 / TypeScript / App Router / ESLint / Tailwind CSS / `src/` / import alias `@/*`)は**変更しない**。生成時にしか選べない項目の判断はデプロイ先に依存しない。
- **新たに顕在化したリスク**: AWS 公式ドキュメントによれば、**Amplify Hosting compute(SSR)がサポートする Next.js は 12〜15** であり、本プロジェクトの **16.3 は公式サポート対象外**である。検討記録で「Amplify の Next.js 新メジャーバージョン対応が遅れることがある」として挙げていた懸念が現実になった形で、[#19](https://github.com/study-basic-hackathon/hanasu/issues/19) が「事前決定(必須)」としていた確認事項への回答でもある。
- **緩和策**: 検討記録の分析どおり、本プロジェクトは全画面が認証後で SEO 不要・データ取得はバックエンド API 経由のため **SSR は不要見込み**。`next.config.ts` の `output: 'export'` による静的出力にすれば Amplify の静的ホスティングで配信でき、compute 側の Next.js バージョンサポートに依存しない。
- **#19 への申し送り**: #19 の任意事前決定「Amplify 既定の SSR 対応のままデプロイするか、静的エクスポートにするか」は、**既定の SSR 対応が Next.js 16.3 では成立しない可能性が高い**という前提で判断すること。まず既定のままビルドを試し、失敗する場合は静的出力に切り替える手順が現実的。
- ADR-0004 の「Linter がビルドをブロックしない」という論拠は、Next.js 16 で `next build` が lint を実行しない仕様にもとづくものであり、デプロイ先に依存しないためそのまま有効。

### ADR-0005(開発バンドラ) — 維持(根拠の差し替え)

- 結論(**Turbopack のまま**)は維持する。開発時のみの決定であり、2026-08-06 に Docker 上でのホットリロードが実測で確認済みという事実も変わらない。
- 「本番ビルドが Vercel 側で行われるため、ローカルの開発バンドラを切り替えても成果物に影響しない」という論拠は、「**本番ビルドが Amplify のビルドコンテナ側で行われるため**」に読み替える。プラットフォーム側でビルドされる構造は同じであり、判断は変わらない。

### ADR-0006(開発用 Docker ベースイメージ) — 維持

- 結論(**`node:24-bookworm-slim`**、ポート 3000、`node_modules` は named volume に分離)は維持する。
- 「本番ビルド・実行がプラットフォーム側で行われるため、このイメージは**開発専用**でありイメージサイズの最適化は判断軸にならない」という前提は Amplify でもそのまま成り立つ。
- イメージタグのメジャーバージョン `24` は ADR-0002 の 24.x に従うため、24.x が維持される以上タグの変更もない。
- ただし ADR-0002 の固定方法変更に伴い、**「イメージタグと `engines.node` を揃える」だけではプラットフォーム側と揃わない。**揃える対象に「Amplify 側の Node バージョン指定」が加わる。

## 影響・トレードオフ

- 良い影響:
  - ハッカソン規模では無料枠内でほぼ $0 に収まり、コストの懸念が解消する
  - Vercel Hobby の非商用制約という**未確認のまま残っていた規約リスクがなくなる**
  - フロントもバックエンドも AWS 内に収まり、アカウント・請求・権限管理が一元化される
  - Git 連携による CI/CD(ブランチデプロイ)は Vercel と同様に得られる
- 受け入れたトレードオフ・残るリスク:
  - **Node バージョン指定を Amplify 側で明示的に行う必要があり、Vercel より設定項目が1つ増える**(ADR-0002 の再検討結果)
  - **Next.js 16.3 は Amplify Hosting compute の公式サポート外**のため、静的出力での配信になる可能性が高い。SSR が必要になった時点で再検討が必要(ADR-0004 の再検討結果)
  - 本番がコンテナ実行でない点は Vercel と同じで、ローカル Docker との完全な dev/prod 一致は引き続き得られない
  - `documents/技術スタック.md` / `CLAUDE.md` / ADR-0001 のドキュメント修正が発生する(#18 で対応)
  - AWS アカウント・IAM ロールの準備が必要で、Vercel の Git 連携のみと比べると初期セットアップの手数は増える

## フォローアップ

- Amplify Hosting の実構築(AWS アカウント設定、リポジトリ連携、モノレポ設定、サービスロール)を [#19](https://github.com/study-basic-hackathon/hanasu/issues/19) で行う
- `amplify.yml` を追加し、**Node 24.x を明示指定**する(ライブパッケージ更新 または `preBuild` の `nvm use`)。**初回ビルドのログで実際の Node バージョンが 24.x であることを確認する**(#19)
- Next.js 16.3 でのビルド可否を #19 で実地に確認し、必要なら静的出力(`output: 'export'`)に切り替えて `baseDirectory` を出力先に合わせる。結果は #19 側に記録する
- **ADR-0002 の改訂(バージョン固定方法の再決定)を [#42](https://github.com/study-basic-hackathon/hanasu/issues/42) で行う**
- 画面仕様の確定([#27](https://github.com/study-basic-hackathon/hanasu/issues/27))時に SSR 要否を最終確認する
- 再検討のトリガー: Amplify の無料枠を超える規模になった場合、SSR が必須と判明し Amplify の Next.js 16 対応が間に合わない場合、またはフロントを AWS 外に置く方針に戻る場合
