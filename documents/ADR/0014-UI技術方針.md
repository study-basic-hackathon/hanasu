# ADR-0014: UI は Tailwind CSS のみで実装し、デザイントークンを `@theme` に持つ

- ステータス: 決定
- 日付: 2026-08-18
- 依存:
  - **[ADR-0004](0004-Nextjsプロジェクト初期構成.md)(Next.js プロジェクトの初期構成)に依存する。** Tailwind CSS v4 を有効にして生成済みであることが本 ADR の前提であり、本 ADR はその上に何を足すかを決める。
- 被依存: なし

## コンテキスト(背景と課題)

画面仕様が確定し([#9](https://github.com/study-basic-hackathon/hanasu/issues/9) / [#27](https://github.com/study-basic-hackathon/hanasu/issues/27))、画面モックの実装に入れる状態になった。しかし **UI ライブラリが決まっていないため、[#51](https://github.com/study-basic-hackathon/hanasu/issues/51)(共通レイアウトとデザイン基盤)とその先の画面モック Issue 11本がブロックされていた。** 後から UI ライブラリを入れ替えるとコンポーネントの書き直しになるため、実装の着手前に決める必要があった。

レスポンシブ対応の要否は #9 で決着しており(PC のみ・基準幅 1440px・最小幅 1280px)、残る論点は UI ライブラリの選定だった。あわせて、**画面モック Issue が11本並ぶことから、決めておかないと Issue ごとに書き方が割れる事項**(デザイントークンの持ち方・共通部品の切り出し基準)も同時に決めることとした。

判断の土台になったのは次の2つの事実である。

- **設計書に現れる UI 部品は素朴なものに限られる。** カード / ボタン / 入力欄 / チップ / トグル / 選択欄 / スケルトン / スコアバー / 円グラフ / 確認 のみで、**モーダル・トースト・タブ・コンボボックス・ポップオーバー・アコーディオン・日付選択は1つも登場しない**([画面詳細仕様](../frontend/01_design/screens/) 全画面)
- **配色はアクセント `#0f766e` を軸にした独自値であり、既製テーマの色ではない**([共通仕様](../frontend/01_design/screen_common.md) 11.1)

## 決定

| 項目 | 決定 |
|---|---|
| UI ライブラリ | **Tailwind CSS のみ。** shadcn/ui 等のコンポーネント集・ヘッドレス UI(Radix / Headless UI)・チャートライブラリを追加しない |
| デザイントークン | **`frontend/src/app/globals.css` の `@theme` に定義**し、ユーティリティクラスとして使う。値は [共通仕様](../frontend/01_design/screen_common.md) 11章(色12種・文字7種・部品の高さと角丸3種)から採る |
| 共通部品 | **全画面で確実に使うものだけ #51 で先に作る**(グローバルヘッダー・カード・ボタン・入力欄・チップ・スコアバー)。それ以外は各画面 Issue で書き、**2度目に必要になった時点で切り出す** |
| 共通部品の置き場所 | `frontend/src/components/ui/`(画面をまたぐ汎用部品)と `frontend/src/components/layout/`(ヘッダーなど骨格)。**1画面でしか使わないものは切り出さず、その画面の中に置く** |

## 検討した選択肢

- UI ライブラリ: Tailwind CSS のみ / Tailwind + shadcn/ui / Tailwind + ヘッドレス UI(Radix・Headless UI)
- デザイントークン: `@theme` でトークン化 / 任意値を都度書く(`bg-[#0f766e]`) / `:root` の CSS 変数を任意値から参照
- 共通部品: 先に一式を作り切る / 2度目に出たら切り出す / 全画面で確実に使うものだけ先に作る

## 決定要因

- ハッカソン期間内に**画面モック11本を作り切れること**
- **デザイン原本を正確に再現できること**(見た目の正本は原本であり、ライブラリの既定デザインではない)
- 画面モック Issue を**並行して進められること**、かつ Issue ごとに書き方が割れないこと
- 後から変更したくなったときのコスト

## 理由

- **コンポーネント集を入れない**: shadcn/ui やヘッドレス UI が引き受けてくれる複雑さ(フォーカストラップ・キーボード操作・重ね合わせ)が、**この画面群にはそもそも発生しない**。フォーカス管理が要る確認も S-06 の削除と S-08 の面接終了の2箇所だけである。さらに配色が独自値のため、入れても既定テーマを上書きする作業が別途乗る。**足すのは Tailwind の上に載せるだけで容易**なため、部品の自作が負担になった時点で再検討すればよい。
- **shadcn/ui を見送ったもう1つの理由**: React 19 / Tailwind v4 には公式対応しているが、**Next.js 16 での動作は公式ドキュメントに明記がなく**(2026-08-18 時点)、自分たちで検証する手間が乗る。
- **トークンを `@theme` に持つ**: 画面モック Issue が11本あり、任意値を都度書くと**同じ色に別の書き方が生まれ、原本を直したときに全画面を追うことになる**。トークン化する値は22個と有限で、書き写す手間は一度きりで済む。`@theme` は Tailwind CSS v4 の標準機能であり、`:root` の CSS 変数を任意値から参照するより素直に書ける。
- **共通部品を「確実に使うものだけ先に」作る**: 先に一式作り切ると使うか分からない部品まで作ることになり #51 が重くなる。逆にすべてを後追いで切り出すと、**先行する画面 Issue の切り出し結果を待つことになり、11本を並行させられない。** 全画面に確実に出るものに絞ることで、両方の不都合を避ける。

## 影響・トレードオフ

- 良い影響:
  - **依存を1つも増やさずに画面実装へ入れる**(Tailwind CSS は導入済み)。バージョン相性の検証が不要
  - デザイン原本の値を上書きなしにそのまま書けるため、原本との差が出にくい
  - トークンがクラス名の語彙になり、画面モック Issue をまたいでも書き方が揃う
- 受け入れたトレードオフ・残るリスク:
  - **ボタン・カード・入力欄などを自作する手間がかかる**(shadcn/ui なら生成コマンドで済んだ)
  - **アクセシビリティ(キーボード操作・スクリーンリーダー対応)を自分たちで担保することになる**
  - トークンの語彙を覚える必要があり、原本の値をそのまま貼るより一手間かかる
  - 「2度目に必要になったら切り出す」の判断が実装者に委ねられるため、**切り出し漏れが起きうる**

## フォローアップ

- **[#51](https://github.com/study-basic-hackathon/hanasu/issues/51) で実装する**: `globals.css` を書き換える(**現状は `create-next-app` の生成時のままで、Geist フォント変数の参照と `prefers-color-scheme: dark` の配色定義が残っており、原本(ライトのみ・Noto Sans JP)と食い違っている**)。`@theme` にトークンを定義し、共通部品を作る
- [共通仕様](../frontend/01_design/screen_common.md) 12章と [画面一覧](../frontend/01_design/screen_list.md) 6章の未決事項から「UI ライブラリの選定」の行を消す
- 再検討のトリガー: **共通部品の自作が負担になった場合**(shadcn/ui の追加を再検討)、または設計に**モーダル・コンボボックス等の複雑な部品が必要になった場合**
- **円グラフの描画手段(S-14 の総合スコア)とアイコンの扱いは本 ADR で決めない。** 使用箇所が限られ後から変更が容易なため、必要になった実装 Issue で判断する
