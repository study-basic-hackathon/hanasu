# ADR-0008: 会話用 API を7本に分割し、サーバーは会話状態を持たない

- ステータス: 決定
- 日付: 2026-08-16
- 依存: [ADR-0007](0007-会話音声の取得と保存方式.md)（音声をターンごとに送り、サーバーに永続化しない）
- 被依存: [ADR-0009](0009-評価方式.md)（評価方式）— 評価 API の入出力が本 ADR の構成に依存する

## コンテキスト(背景と課題)

[ADR-0007](0007-会話音声の取得と保存方式.md) で音声の扱いが決まったことを受け、会話セッションの開始から終了・評価までに必要な API の構成を決める必要があった。

バックエンドは既に `backend/` に FastAPI で実装されており、**JWT Bearer 認証（`POST /token` / `GET /users/me`）と `Depends(get_current_user)` による保護 API の形が確立済み**（[#7](https://github.com/study-basic-hackathon/hanasu/issues/7) 完了）。インフラも ECS / ALB / ECR が構築済み（[#5](https://github.com/study-basic-hackathon/hanasu/issues/5) 完了）。一方 **RDS は未構築**（[#8](https://github.com/study-basic-hackathon/hanasu/issues/8) は Open）。

検討の過程で、外部から「Next.js の API Routes のみで構成し、DB・認証を持たない」という設計案も提示されたが、**チームが構築済みの資産を活かすかどうか**が論点になった。

## 決定

- **既存の `backend/`（Python / FastAPI / ECS）に実装する。** 全 API に **JWT Bearer 認証**を課す（[必要api .md](../必要api%20.md) の「認証ユーザーのみ実行可能」制約を満たす）。
- **サーバーは会話状態を持たない。** 会話履歴はクライアントが保持し、毎回リクエストに含めて送る。
- **API は次の7本とする**（うち2本は任意）。

| # | エンドポイント | 役割 | 優先度 |
|---|---|---|---|
| 1 | `POST /interviews/start` | 最初の質問を生成 | 任意（低） |
| 2 | `POST /interviews/stt` | 文字起こし + フィラー + 話速 | **最優先** |
| 3 | `POST /interviews/chat` | 次の質問を生成 | 高 |
| 4 | `POST /interviews/tts` | 発言の音声化 | 任意 |
| 5 | `POST /evaluations` | 評価の実行（非同期） | 高 |
| 6 | `GET /evaluations/{evaluation_id}` | 評価結果の取得 | 高 |
| 7 | `GET /evaluations?company_id={id}` | 評価履歴の一覧 | 中 |

- **`POST /interviews/chat` はストリーミングしない。** `{ "text": "..." }` を1回の JSON で返す。
- **評価は非同期にする。** `POST /evaluations` は `evaluation_id` のみを返し、`GET /evaluations/{id}` でポーリングする（`processing` / `completed` / `failed`）。
- **面接の進行は自由会話とする。** 半構造化（主質問リストの事前生成・深掘り管理・質問単位の評価）は今回見送り、拡張として残す。
- **終了判定はユーザーの終了操作のみ。** API に終了フラグは持たせず、**ターン数の上限はフロント側で管理する**。

## 検討した選択肢

- 分割粒度
  - A案: ターン API 1本に STT → LLM → TTS を統合した4本構成
  - B案: `stt` / `chat` / `tts` を分離した7本構成（**採用**）
- 会話状態の持ち方
  - パターン1: サーバーが会話履歴を DB に保持し、クライアントは `session_id` だけ送る
  - パターン2: サーバーは持たず、クライアントが履歴を運ぶ（**採用**）
- サーバー実装
  - 既存の `backend/`（FastAPI / ECS）（**採用**）
  - Next.js API Routes のみ（DB・認証なし）

## 決定要因

- 既存実装（FastAPI + JWT）・既存インフラ（ECS）への乗せやすさ
- 未構築の RDS（[#8](https://github.com/study-basic-hackathon/hanasu/issues/8)）に依存せずに実装・動作確認できるか
- 実装が間に合わない機能を切り離せるか
- チームの他メンバーの成果物との整合

## 理由

- **7本への分割を採用**: ①**文字入力でもチャットを返せる**ようにするため、STT が毎ターン使われるとは限らず `stt` と `chat` を分けたい。②**TTS は実装が間に合うか不明**なため、チャット応答を最優先にし、分離して開発を分けられるようにしたい。
- **パターン2（状態を持たない）を採用**: パターン1 を選ぶ理由は「評価系が同じ DB を読むから」だったが、[ADR-0007](0007-会話音声の取得と保存方式.md) で**音声も transcript も保存しないと決めた時点でこの理由が消滅した**。状態を持たなければ **[#8 RDS構築](https://github.com/study-basic-hackathon/hanasu/issues/8) の完了を待たずに会話機能を実装・動作確認できる**。
- **既存 `backend/` への実装を採用**: [#5](https://github.com/study-basic-hackathon/hanasu/issues/5)・[#7](https://github.com/study-basic-hackathon/hanasu/issues/7) の成果を活かせる。Next.js API Routes 案は DB・認証を持たない前提であり、**チームが構築済みの ECS と認証 API が会話機能では使われなくなる**ため見送った。
- **ストリーミングしない**: ストリーミングの利点は「文字が早く出始める体感」と「句点単位で TTS に投げられる」の2つだったが、**後者を実装しないと決めたため理由が半減**した。SSE の実装を省ける。
- **非同期評価**: 評価は LLM 呼び出しを伴い時間がかかるため。**`failed` 状態を用意しないと、LLM が落ちたときフロントが永久にポーリングし続ける**。
- **自由会話**: まずシンプルに実装して動くことを確認するため。半構造化はその後の拡張とする。

## 影響・トレードオフ

- 良い影響:
  - **RDS がなくても会話機能が動く**ため、[#8](https://github.com/study-basic-hackathon/hanasu/issues/8) と並行して進められる
  - **TTS を落としても、面接官の発言を文字表示するだけでチャットは成立する**
  - 既存の `Depends(get_current_user)` をそのまま付けるだけで認証要件を満たせる
  - SSE・分割再生のキュー管理・相槌キャッシュがいずれも不要になり、実装が一段軽くなる
- 受け入れたトレードオフ・残るリスク:
  - **会話履歴を毎ターン全量送るため、リクエストが会話の長さに比例して大きくなる**（LLM に渡す範囲はフロントの裁量で調整可能）
  - **リロードで会話が失われる**（[ADR-0007](0007-会話音声の取得と保存方式.md) と同じトレードオフ）
  - ストリーミングしないため、**LLM の生成完了まで2〜3秒間なにも表示されない**
  - **自由会話のため、評価を質問単位で構造化できない**（セッション全体で1つの評価になる）

## フォローアップ

- [必要api .md](../必要api%20.md) の「会話用API: TODO」を本 ADR の内容で埋める
- パス命名を実装時に確定する（既存 API が `/token` / `/users/me` とプレフィックスなしのため）
- 非同期処理の実装方式を決める（ECS タスクが1つのため、まずは FastAPI の `BackgroundTasks` で足りる見込み）
- 会話用 API の実装 Issue を起票する
- 再検討のトリガー: **半構造化面接に拡張する**場合（`question_id` / 質問リスト / 進行判断フラグが必要になる）
