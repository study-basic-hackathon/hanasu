# ADR-0005: 開発時のバンドラを Turbopack のままとする

- ステータス: 決定
- 日付: 2026-08-06
- 依存:
  - **[ADR-0004](0004-Nextjsプロジェクト初期構成.md)(Next.js 16.3 を採用)に依存する。** Turbopack が既定バンドラであることは Next.js 16 系の仕様であり、採用バージョンが変われば前提が変わる。
  - **[ADR-0001](0001-フロントエンド実行環境.md)(デプロイ先を Vercel とする)に依存する。** 本番ビルドが Vercel 側で行われるため、ローカルの開発バンドラを切り替えても成果物に影響しないという判断が成り立っている。
- 関連: 本 ADR の決定は **未実測の前提**を含む(下記「フォローアップ」参照)。

## コンテキスト(背景と課題)

ADR-0001 でローカル開発は Docker 上で `next dev` を実行する方針としている。Docker の bind mount 越しにファイル変更を検知できるかは開発体験を大きく左右するため、着手前に前提を整理した。

調査の結果、次の2点が判明した。

1. **Next.js 16 から Turbopack が既定バンドラになっており、webpack はオプトイン(`--webpack`)扱いになっている。**
2. **Turbopack にはファイル監視のポーリング設定が公式には存在せず**、Docker / WSL コンテナ内でファイル変更を検知しない問題が未解決の issue として残っている([#80665](https://github.com/vercel/next.js/issues/80665) は Open)。

タスクメモには「効かない場合は `WATCHPACK_POLLING=true` 等で対応」と書かれていたが、これは **webpack(watchpack)向けの環境変数**であり Turbopack には作用しない。つまり Turbopack で問題が起きた場合、環境変数の追加では解決できずバンドラの切り替えが必要になる。

この前提のもとで、最初から webpack を使うか、Turbopack で始めるかを決める必要があった。

## 決定

開発時のバンドラは **Turbopack(Next.js 16 の既定)のまま**とする。

- Docker 上でホットリロードが効かないことが**実測で確認できた場合に限り**、開発コマンドのみ `next dev --webpack` + `WATCHPACK_POLLING=true` にフォールバックする
- フォールバックする場合も `next build` は Turbopack のままとする

## 検討した選択肢

- A案: Turbopack のまま(既定)
- B案: 最初から開発時のみ `next dev --webpack`

## 決定要因

- Docker 上での動作確実性
- 開発体験(ビルド速度・メモリ使用量)
- 将来の保守性(公式デフォルトへの追従)
- 問題が起きた場合の切り替えコスト

## 理由

- **Turbopack を採用**: 公式デフォルトに追従でき、Next.js 16.3 では dev サーバーのメモリ使用量が最大 90% 削減されている。何より**フォールバックのコストが小さい**(開発コマンドのフラグを切り替えるだけ)ため、問題が起きてから切り替えても遅くない。本番ビルドは Vercel 側で行われるため、ローカルの選択が成果物に影響しない点も後押しになった。
- **最初から webpack を使う案を見送り**: Docker でのファイル監視は確実になるが、Turbopack の性能と将来性を捨てることになる。webpack はオプトイン扱いでいずれ非推奨になる可能性もあり、問題が確認されていない段階で選ぶ理由がない。

## 影響・トレードオフ

- 良い影響:
  - 公式デフォルトのまま進められ、将来の Next.js アップグレードで追加対応が発生しにくい
  - dev サーバーのメモリ使用量とビルド速度で優位
- 受け入れたトレードオフ・残るリスク:
  - **Docker bind mount 越しのホットリロードが効くかは未実測。** macOS の Docker Desktop で問題を踏む可能性がある
  - Turbopack にポーリング設定がないため、効かない場合は環境変数では解決できず webpack への切り替えが必要
  - フォールバックした場合、開発は webpack・Vercel のビルドは Turbopack という差異が生まれる(既知の差異: CSS Modules の順序、Lightning CSS の小数精度)

## フォローアップ

**本 ADR は「Docker 上でホットリロードが効く」ことを未検証のまま決定している。** タスクメモ [0805-Frontend動作検証用初期構築](../task-memo/0805-Frontend動作検証用初期構築.md) フェーズ1 で次の順に検証する。

1. `docker compose up` で `next dev`(Turbopack)を起動し、ホストでファイルを編集してホットリロードが効くか実測する
2. 効かない場合、Docker Desktop のファイル共有方式(VirtioFS など)を確認する
3. それでも効かない場合、開発用スクリプトを `next dev --webpack` に切り替え、`WATCHPACK_POLLING=true` を compose の環境変数に追加する
4. どの段階で解決したかを検討記録とタスクメモの作業ログに追記する

- 再検討のトリガー: 上記の実測でホットリロードが効かず、Docker 設定でも解決しなかった場合(フォールバックを発動し、本 ADR に結果を追記する)
