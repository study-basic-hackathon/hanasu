## 仕様書作成タスクの分解案
大きく「前提を固める」→「全体像を決める」→「各画面を書く」の3段階に分けるのが良いです。

段階1: 仕様の前提を固める(ブロッカー解消)
 ユースケース・ユーザーフローの言語化 — 「誰が・何のために会話練習するのか」(企業情報があるので面接練習と推測しますが、明文化されたドキュメントがありません)。全画面仕様の土台になるため最優先です
 会話機能の方式検討 — 会話相手は AI か人か、音声取得は Chime SDK かブラウザの MediaRecorder か、音声送信はストリーミングかファイルアップロードか。必要api .md でも「会話用API: TODO」のままで、会話画面仕様のブロッカーです。検討が必要なら documents/00_検討/ に記録を残す対象です
 UI 技術方針の決定 — UI ライブラリ(Tailwind / shadcn など)、レスポンシブ対応の要否。ハッカソンなので軽く決めるだけで十分です
段階2: 全体像を決める
 画面一覧・画面遷移図の作成 — 想定される画面: ログイン / 企業情報一覧・登録・編集 / 会話(録音)/ 分析・評価結果表示 / (履歴・プロフィール)。ここで画面のスコープを確定させます
 画面と API の対応表作成 — どの画面がどの API を呼ぶかを 必要api .md と突合。API 側の不足(例: 履歴取得)もここで洗い出せます
 共通仕様の定義 — 認証済みユーザーのみ操作可能という制約の画面側の扱い(未認証時のリダイレクト)、エラー表示、ローディング表示、マイク許可が拒否された場合の挙動
 画面仕様書テンプレートの用意 — documents/template/ には task-memo 用しかないため、画面名・レイアウト・表示項目・入力バリデーション・API 呼び出し・エラー時挙動、程度の雛形を1つ作る
段階3: 各画面の仕様書を書く
CLAUDE.md に記載の配置(documents/frontend/01_design/・02_spec/)に沿って、優先度順に:

 会話(録音)画面 — サービスの核。段階1の方式検討が完了してから
 分析・評価結果画面 — 抑揚・フィラー・声量・テンポの見せ方(グラフ等)を含む
 ログイン画面 — 簡易認証なので薄くて良い
 企業情報 CRUD 画面
 ADR-0001 のフォローアップ「フロントエンド仕様書にデプロイ先決定を反映する」の消化
